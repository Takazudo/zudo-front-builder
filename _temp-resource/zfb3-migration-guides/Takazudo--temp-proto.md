Generated 2026-10-04 by an automated diagnosis of `main` @ `a795005`; the `zfb wind audit` census was taken with the zfb 3.1.0 CLI and re-taken with 3.2.0 the same day (both sets of numbers are given). zfb 3.2.0 was released (npm `latest`, https://zfb.takazudomodular.com/changelog/zfb/v3.2.0/) while this diagnosis was being written, so every pin and label below targets 3.2.0. ## Verdict

**retire-candidate (archive); if kept as a v3 showcase, re-create rather than migrate — effort XL as a migration, L for `proto-site` alone.** The repository is a sanitised export of a client prototype: three commits on 2026-07-11/12 ("Add zfb UI-framework prototyping example", "Repurpose content-guard for the dummy example", "Replace content with dummy placeholder text and purge derived references"), README calls it a *サンプル* with all-fictional content, zero issues, zero PRs, private, deployed only to `*.takatsudo.workers.dev` behind a password gate whose password is the placeholder `changeme`. Its tooling still references two sibling sites (`proto-prod`, `proto-doc`) that are not in the repo (`scripts/run-b4push.sh:84,100`, `packages/proto-design-system/CLAUDE.md:11-12`). It pins `@takazudo/zfb 0.1.0-next.60` (2026-06-23), Preact, Tailwind 4 via a hand-built tight-token `@theme` design system, **`@takazudo/zudo-doc 0.2.21` used as a component library (not a preset)** in the styleguide, and `@takazudo/zdtp 0.3.3`. The styleguide half depends on three things with no v3 path today (zudo-doc 0.2.x components, `preact-render-to-string`, a Tailwind-`@theme` parser feeding CodeMirror completions). The sample-site half (`proto-site`) is unusually clean — 9 `useEffect`-only enhancer islands plus 2 effect-free client modules, zero `useState`, zero `className`, 375 `class=` — and its design-system `@theme` is already a token manifest, so it would make a good v3 example if re-scaffolded. Recommendation: archive the repo on GitHub (or tag `zfb-0.1.0-next.60-snapshot`), and if a v3 prototyping template is wanted, start from the v3 scaffold and port `proto-site` + `packages/proto-design-system` using §2–3 below.

## Sequencing and blockers

1. **Decide retire vs rebuild first.** Nothing external blocks a migration (no zudo-doc *preset*, no zudo-sg), but the styleguide's zudo-doc 0.2.21 library imports have no straight upgrade: the same subpaths exist in zudo-doc 5.28.2 (`doclayout`, `sidebar-resizer`, `theme`, `theme-toggle`, `theme/color-scheme-provider`, `transitions`, `safelist.css`), yet 0.2.21 → 5.x is a ~5-major API gap, 5.x is still Preact, and the zudo-react versions arrive only with zudo-doc 6.0.0 (zudolab/zudo-doc#4430, root PR #4477 still draft; its zfb blockers #3569/#3570 shipped in zfb 3.2.0 on 2026-10-04, but 6.0.0 itself is unreleased). A styleguide migration therefore waits on **zudo-doc 6.0.0**, or drops zudo-doc and rebuilds its chrome.
2. **Pre-1.0 → 2.22.1 breaking notes that apply here** (if anyone takes the incremental route): https://zfb.takazudomodular.com/changelog/zfb/v0.1.0-next.90/ — relative imports that resolve above the project root hard-fail. `proto-styleguide/tsconfig.json:18` maps `@/*` → `../*` and the generated story glob imports `@/proto-site/components/...`; `src/styles/global.css:38-41` `@source` the sibling. The styleguide must consume `proto-site` as a declared workspace package with `exports` (`"./components/*": "./components/*"`) — `proto-styleguide/CLAUDE.md:9` already names this undeclared coupling. next.25 (`admonitionsPreset`), next.38 (`linkValidation.allowExternal`), 2.0.0 (`githubAutolinks`) do not apply (keys unused).
3. **v3 cut-over** per https://zfb.takazudomodular.com/guides/migrating-to-v3/: `proto-site` + design system first (self-contained), styleguide last or never.
4. **Shipped in zfb 3.2.0 (npm `latest` since 2026-10-04 15:30 UTC; https://zfb.takazudomodular.com/changelog/zfb/v3.2.0/), so nothing below waits on an unreleased zfb:** `wind.utilities.placement: "before-authored"` (the styleguide `global.css:97-105` relies on unlayered rules beating layered preflight — order semantics change either way), `zfb wind audit --json` / `zfb wind explain --stdin --json` (replaces `scripts/generate-tw-classes.ts` as the completion source), `order-*`/`content-*`/`appearance-*` ZW014 warnings naming the declaration to author, `wind.strict`, `wind.sources.packageRoots`, and authored `@import` of package `exports` subpaths (#3364). The audit below was run with the 3.1.0 binary and re-run with 3.2.0 after the release (both sets of numbers are given); 3.1.0's `file:NNN` positions are byte offsets, 3.2.0 prints `file:line:col`.

## Risks and open questions

- **Is this repo meant to live?** README and commit history say "example"; the gate password is a placeholder; CI secrets may not even be set. If the answer is no, archiving costs nothing and avoids an XL rewrite of a Preact catalog that depends on zudo-doc 0.2.21.
- **Styleguide has no v3 landing zone yet.** zudo-doc 6.0.0 is in progress (39/51 topics merged at the 2026-10-02 checkpoint per zudolab/zudo-doc#4430; `base/zfb3-migration` @ 70e0875 is pushed and root PR #4477 carries 102 commits, only the #4467 integration topic is still local); the zfb bugs it was blocked on (#3569/#3570) shipped in 3.2.0 on 2026-10-04, so the zudo-doc side is unblocked, but 6.0.0 is not published and its component API will differ from 0.2.21 anyway.
- **Tight-token discipline vs v1 catalog.** The design system banned numeric spacing and default colours; v1 enforces the same by construction (no `spacingUnit` → `p-4` is an error, no implicit palette). Logical-property utilities (`ps-`/`pe-`/`ms-`/`me-`/`start-`/`end-`) are the one real catalog gap — 9 sites.
- **`md:` breakpoint** is used 4× but never defined — a latent bug today; decide `lg` or add `md: { minWidthPx: 768 }`.
- **Placement semantics** (`content.css` unlayered-by-design, styleguide `dialog:modal { margin: auto }` reset fix) flip under zudo-wind's default; `wind.utilities.placement: "before-authored"` (3.2.0) restores the Tailwind order for equal-specificity ties only — an authored rule inside a layer still loses to every utility under either setting.
- **Open question:** should `@proto/design-system` become a `definePreset()` package exporting the `wind` tokens for both sites (https://zfb.takazudomodular.com/api/define-preset/), and publish a `wind.json` candidate manifest if it ever ships components (https://zfb.takazudomodular.com/zudo-wind/sources-and-candidates/#adding-explicit-candidates-publishing-candidates-from-a-package)?
