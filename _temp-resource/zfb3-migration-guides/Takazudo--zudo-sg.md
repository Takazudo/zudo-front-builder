## Verdict

**Blocked, effort XL.** zudo-sg is not one host but a published zfb preset/engine (`@takazudo/zudo-sg` 0.4.1, `packages/styleguide`) plus six zfb project dirs and a ~77-component Preact library, all pinned to zfb 2.21.1 / zudo-doc 5.28.0 / Preact / Tailwind 4. Three things gate the start: (1) **zudo-doc 6.0.0** — every engine route imports zudo-doc chrome (`@takazudo/zudo-doc/chrome`, `doclayout`, `sidebar-tree-island`, `sidebar-prepaint`, `content-admonition`, `color-scheme-utils`) and the root, `doc/`, both fixtures and the `create-zudo-sg` template compose `zudoDocPreset()`/`zudoDoc()`; the migration guide says presets upgrade first (zudolab/zudo-doc#4430, draft PR #4477, consumer guide #4473). (2) **zdtp stays Preact** (zudo-doc decision DD3, zdtp#1002) but `packages/styleguide/src/token-dashboard/create-token-dashboards.tsx:4` value-imports and *server-renders* `TokenDashboard` from `@takazudo/zdtp/dashboard` on the injected `/tokens` route — a Preact component rendered by zudo-react is unsupported, so `/tokens` needs a redesign. (3) The engine's shipped `safelist.css` (`@source inline(...)`) and its own Tailwind compiler (`src/preview-css/compile.ts` on `@tailwindcss/node` + `oxide`) must become a `wind.json` manifest and a `zfb css`-based compile; the generator `zfb wind manifest`, `wind.sources.packageRoots` and `--plan build` audits are on zfb `main` but **next zfb release** only. No v3 branch, PR or issue exists yet (`git ls-remote --heads origin`: `main` + 6 dependabot branches; 7 open items are 6 dependabot PRs and #908). Effort is XL because the engine (94 `.ts` + 36 `.tsx` files, 10 islands, 13 pragma files, 85 `[color:var()]` hints), `@zudo-sg/demo-ui` (221 `.tsx`, 589 dead utility candidates, 10 hook files), three deployed sites, two npm publish pipelines, 153 vitest files on `@testing-library/preact` and 71 Playwright tests all move together, and every consumer (zudolab/zzmod PR #2906, zudo-composer) waits on the resulting engine release.

## Sequencing and blockers

1. **Wait for zudo-doc 6.0.0** (zudolab/zudo-doc#4430 / #4477; consumer guide #4473). It will ship a `wind.json` manifest, a `zudoDoc({ wind })` override, keep zdtp as an opaque Preact bundle, and drop the `preact` peer. Nothing in this repo can build on zfb 3 before it, because `zudoDocPreset`/`zudoDoc` 5.x still emit `framework`/`tailwind` keys (preset failure, migration guide "Before you start"). zudo-doc's plan explicitly lists zudo-sg as "a downstream v3 migration after zudo-doc 6" (`_temp-resource/4430-zfb3-migration/explore/pkg-build.md:175`).
2. **Wait for the next zfb release after 3.1.0** for: `zfb wind manifest` (engine manifest generator), `wind.sources.packageRoots` (scan `packages/demo-ui/src` and a host's `ui/` corpus without `@source`), `zfb wind audit --plan build --json` (host-side CI gate including injected routes), `visible`/`invisible` and `underline-offset-<n>` utilities (used in `site-nav.tsx:137` and the engine), ZW014 warnings for `order-*`/`content-*`/`appearance-*`, underscore class names as ordinary (#3365), and the authored-CSS package `exports` import extension (#3364; 3.1.0 already resolves `@import "@scope/pkg/x.css"` through `exports` per changelog v3.1.0 `215da300`, verify each of the 8 package imports in `src/styles/global.css`).
3. **zdtp decision** (Takazudo/zudo-design-token-panel#1002): the preview token panel already loads zdtp lazily (`src/token-tweak/token-panel-native-bootstrap.ts:15`), which matches the v3 widget pattern; the `/tokens` dashboards (`create-token-dashboards.tsx`, `routes/tokens.tsx`) do not. Decide before engine work starts: client-mount the dashboards inside an island host element, or ask zdtp for an HTML-string renderer.
4. **Do now, on zfb 2.21.1 (behaviour-preserving prep; each item is verifiable with the audit recipe above):** bump to zfb 2.22.1 / zudo-doc 5.28.2 (2.22.x changelogs carry no breaking notes); remove every Tailwind-only spelling that zudo-wind rejects while Tailwind 4 still compiles the replacement (§2 list); replace `cloneElement` in `field.tsx`; move browser reads out of render into effects; make `useId`-derived ids deterministic (`code-panel.tsx:60` already prefers `slug`); write the `wind.tokens` table (§2 draft) and the engine-chrome token decision as an ADR amendment; prototype the manifest JSON from `gen-safelist.mjs` output and validate it with `zfb wind explain` on 3.1.0 in a scratch project.
5. **Then migrate in this order, one branch:** engine package (`packages/styleguide`) → `packages/demo-ui` → root host → `apps/demo` → `fixtures/engine-host` (+ `pnpm sync:create-template`) → `fixtures/descriptor-host` → `doc/` (re-scaffold with create-zudo-doc 6 following `ZUDO_DEPS_PINS.md`). Release the engine as a breaking minor under the 0.x stable-only scheme (`packages/styleguide/RELEASE.md`) or an explicit 1.0.0; consumers (zzmod #2906, zudo-composer) can only start after that release.

## Risks and open questions

- **zdtp coupling is the hard blocker inside the engine.** `/tokens` SSR-renders a Preact component; whether zdtp#1002 ships a Preact-bundled, CSS-import-safe build decides if the route can keep server markup at all or becomes client-only (SEO/no-JS regression for the dashboards).
- **Engine token contract.** Shipping a manifest that depends on host token names (option a) makes every consumer's `wind.tokens` part of the engine API; moving chrome to `--sg-*` authored CSS (option b) is more work now but removes the coupling. Decide before writing the manifest generator.
- **Source-plan coverage without `packageRoots`.** On 3.1.0 the root and demo builds scan only conventional roots; `packages/demo-ui/src` was previously reached via `@source`. The workspace-sibling "mirror root" rule (concepts/styling "Monorepo") may or may not cover a package consumed through `exports` `./src/*`; measure the emitted CSS, keep a `wind.safelist` fallback, and switch to `wind.sources.packageRoots` on the next release.
- **Preview compile fidelity.** Replacing the in-process Tailwind compile with a spawned `zfb css` changes dev recompile latency and the `:root` rescoping regex (`compile.ts:51-56`) depends on zudo-wind's emitted selector shape; the two `preview-fidelity` e2e tests are the gate.
- **Hydration strictness.** v3 islands fail closed on identity/props mismatch; the engine's `ConfiguredPreviewApp` (no props, registry in-bundle) and the function-call `Island({...})` style in `_body-end-islands.tsx` need re-verification under the "one component child, JSON props" rule; `displayName` tricks no longer apply.
- **Utility placement and `group-*` specificity** flip ties against authored rules (`.zd-content` flow layer, `styles.css` chrome, demo `@layer base`); `before-authored` placement is next-release only.
- **Breakpoints in px**: `max-sm:` etc. no longer follow root font size (W02) — acceptable for this design system (640/768/1024/1280) but note it in `STORIES.md`.
- **Version skew in consumers**: zzmod #2906 adopts 0.3.6 on zfb 2.20.3; zudo-composer pins 2.22.0 — the engine's last 2.x-compatible line (0.4.x) should be documented as frozen once the v3 minor ships (stable-only, no `next` tag per `RELEASE.md`).
- **Audit noise**: the 1180/1118 ZW005 "invalid slash modifier" and 554/857 ZW001 auditInfo lines in demo-ui/engine come from non-class string literals (paths, selectors, test fixtures); only class-position errors above are actionable. `--json` audits (next release) will make this filterable.
