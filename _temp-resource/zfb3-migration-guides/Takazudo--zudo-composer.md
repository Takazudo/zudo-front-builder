## Sequencing and blockers

1. **Now (no upstream dependency):** the prep items marked *now* in "Required changes":
   - rename the nine `sg-home__*` BEM classes (or wait for the next zfb release);
   - replace the four `charSet` / `dangerouslySetInnerHTML` / hand-authored `Island()` constructs;
   - inventory the pack utilities with a local `pnpm gen && zfb wind audit`;
   - draft `wind.tokens` for the four packs' `@theme` blocks;
   - settle the styleguide architecture question in step 4.
   Keep every host on exact `2.22.0` / `5.28.0` / `0.4.1` meanwhile; all five lockfiles (root `pnpm-lock.yaml` for `doc/`, `styleguide/<host>/pnpm-lock.yaml` ×4) install with `--frozen-lockfile` in CI.
2. **zudo-doc 6.0.0** (zudolab/zudo-doc#4430, root PR #4477 draft, consumer guide #4473; see `zudolab--zudo-doc.md`) unblocks `doc/`. Its own blockers (#3569, #3570) are fixed on zfb `main` but ship only in the **next zfb release** after 3.1.0, so 6.0.0 will pin that release, not 3.1.0.
3. **Next zfb release** also carries three items this repo needs:
   - underscore class names become ordinary (#3365) — on 3.1.0 `sg-home__main` is a ZW001 build error, verified with `zfb wind explain`;
   - `wind.sources.packageRoots` / `exclude` (#3367) to scan the git-installed `@zudo-composer/ui` source the way `@source "../../node_modules/@zudo-composer/ui/src/**"` does today, **and** to reach the gitignored `src/generated/` pack bundles in blog/landing/shop (a package root is walked without gitignore rules; every other root honours them — https://zfb.takazudomodular.com/zudo-wind/sources-and-candidates/#exclusions-and-updates) — https://zfb.takazudomodular.com/zudo-wind/configuration/#the-wind-key-source-exclusions-and-package-roots;
   - `zfb wind manifest` for shipping pack candidates — https://zfb.takazudomodular.com/api/cli/#zfb-wind-manifest.
4. **v3-compatible zudo-sg** (Takazudo/zudo-sg; repo pins zfb 2.21.1, npm latest 0.4.1, no v3 branch on `origin`). The four styleguides import 9 distinct `@takazudo/zudo-sg/*` subpaths (`stories` ×105, `token-dashboard` ×9, `config` ×8 — 4 `zfb.config.ts` imports + 4 `zudo-sg.config.mjs` JSDoc types, `token-tweak` ×4, `token-tweak/preview-token-panel-bootstrap` ×4, `islands` ×4, `plugins/zdtp-apply-proxy` ×4, `styles.css` ×4, `safelist.css` ×4) and `withZudoSg()` composes zudo-doc's preset fragment, so nothing moves before zudo-sg does. The decisive design question is upstream: zfb 3's zudo-react renders no Preact VNode (https://zfb.takazudomodular.com/zudo-react/coming-from-preact-hooks/#what-does-not-exist), yet every story here returns Preact VNodes from packs that **must stay Preact** for the tool. A v3 zudo-sg must either mount stories as an opaque Preact widget inside its preview iframe (https://zfb.takazudomodular.com/concepts/islands/#embedding-a-third-party-widget) or require zudo-react packs — the latter is not an option for this repo. Raise this on Takazudo/zudo-sg before it designs its v3 preview.
5. **zdtp** (`@takazudo/zdtp` 0.8.5; `bundleZdtp: true` in all four styleguide `zfb.config.ts`): stays a Preact bundle under zudo-doc 6 (decision DD3, zdtp#1002). Nothing to do here beyond following zudo-doc 6's `bundleZdtp` contract.
6. **Staggered rollout is natural here:** `doc/` is a root-workspace member (`pnpm-workspace.yaml:5`); the four styleguides are standalone lockfiles outside the workspace. `doc/` can move to zudo-doc 6 / zfb 3 while the styleguides stay on 2.22.0 indefinitely. The only coupling is `styleguide/sample`'s md-wasm version matching `packages/ui`'s (§4).

## Risks and open questions

- **Preact packs vs zudo-react previews** is the architectural fork of this repo; it is zudo-sg's decision and nothing here can be finished before it is made. If zudo-sg v3 requires zudo-react components, the four styleguides either stay on zfb 2.x permanently or need a second component implementation per pack — the latter contradicts `CLAUDE.md`'s single-pack contract and is not recommended.
- **Dual-consumer CSS** (`packages/ui/styles/composer.css`, `packages/demo-*/styles/base.css`) cannot satisfy both Tailwind (tool) and zudo-wind (zfb) from one file; whichever option is chosen is a pack byte change with handoff cost.
- **3.1.0 vs next release**: the nine ZW001 `sg-home__*` errors, `wind.sources.packageRoots` (needed to scan the git-installed `@zudo-composer/ui` source and the gitignored `src/generated/` pack bundles) and `zfb wind manifest` are all **next zfb release**; a migration attempted on 3.1.0 would need renames, a copied-source workaround and either un-ignoring `src/generated/` or committing the bundles.
- **`check-sg-computed-styles.mjs` / island selector** and the exact-string CSS tests will go red on the first 3.x build; budget time for them, do not weaken them.
- **Five `minimumReleaseAgeExclude` lists** across five `pnpm-workspace.yaml` files; a partial update breaks frozen installs on another OS (UPSTREAM-NOTES item 5).
- **Open:** does zudo-doc 6 still peer-depend on `preact` for zdtp bundling (`bundleZdtp: true`)? Does zudo-sg v3 keep `withZudoSg()`, `chromeBindingsModule`, `zdtpApplyProxy.tabsModule`, and the `@takazudo/zudo-sg/stories` contract? Does `create-zudo-sg` v3 regenerate `pages/lib/*` so the 12 starter-file edits above are a re-scaffold rather than hand edits?
- **Not tested:** no `pnpm install`, `zfb check`, or build was run on this clone (preset imports need `node_modules`); the audit saw host trees only, not the generated pack bundles or `node_modules/@zudo-composer/ui`; hook and utility counts are greps, not an AST census.
