## Sequencing and blockers

1. **Upstream gate: `@takazudo/zudo-doc` 6.0.0 on zfb 3** (epic zudolab/zudo-doc#4430, root PR zudolab/zudo-doc#4477, consumer migration guide zudolab/zudo-doc#4473). Until it is on npm, `zudoDoc()` 5.x supplies `framework`/`tailwind` and any `@takazudo/zfb@3` install fails config loading. Do not bump zfb alone.
2. **Upstream dependency of that gate: the next zfb release after 3.1.0** (zudo-doc's integration floor is blocked on Takazudo/zudo-front-builder#3569/#3570, fixed on zfb `main`, unreleased). Expect zudo-doc 6.0.0 to pin that release, not 3.1.0.
3. **Doable now, independent of both:** remove the unused `tailwindcss` devDependency (verify with `cd doc && pnpm install && pnpm build`), keep content free of JSX (it already is), and make `scripts/bootstrap_doc.sh` read its `create-zudo-doc` version from one place so the 6.x re-pin is a one-line change.
4. **After 6.0.0:** regenerate the host files with `create-zudo-doc@6` (the repo already has the regeneration script) rather than hand-porting `global.css`; then verify with the checklist below.

Optional, not required: stepping 2.20.2 -> 2.22.1 / 5.27.0 -> 5.28.2 first. `grep -ci breaking docs/src/content/docs/changelog/zfb/v2.*.mdx` in zfb main matches only v2.0.0, and zudo-doc's `CHANGELOG.md` has no `Breaking Changes` heading between 5.8.0 and 5.28.2, so the intermediate hop is low-risk but buys little for this host.

## Required changes

### 1. Dependencies, config, tsconfig, env

- **`doc/package.json`** (`dependencies`/`devDependencies`): when 6.0.0 ships, set `@takazudo/zfb`, `@takazudo/zfb-runtime`, `@takazudo/zfb-md-wasm` to the zfb version zudo-doc 6.0.0 pins (lockstep, exact), `@takazudo/zudo-doc` to `6.x`; remove `preact`, `preact-render-to-string` and `tailwindcss` (the runtime ships inside `@takazudo/zfb/zudo-react`, https://zfb.takazudomodular.com/guides/migrating-to-v3/#components-and-islands). Keep `zfb-md-wasm` only if zudo-doc 6 still lists it as a peer.
- **`doc/zfb.config.ts`** (lines 1-15): the host adds no `framework`/`tailwind`/`wind` keys itself, so nothing is deleted here. zudo-doc 6.0.0 is planned to carry a package-owned `wind` fragment (tokens, `reset`, a candidate manifest exported by the package) inside `zudoDoc()`; if you need host tokens, the planned shape is a `wind` override merged user-wins (https://zfb.takazudomodular.com/zudo-wind/configuration/#strict-validation-and-merging). Confirm the exact override key in zudolab/zudo-doc#4473 before writing it.
- **`doc/tsconfig.json`**: delete the three `paths` entries `react`, `react/jsx-runtime`, `react-dom` (lines 7-9). `jsx`/`jsxImportSource` come from `@takazudo/zudo-doc/tsconfig.base.json`, which 6.0.0 is planned to switch to `@takazudo/zfb/zudo-react`; if the shipped base does not, add `"jsx": "react-jsx", "jsxImportSource": "@takazudo/zfb/zudo-react"` locally (https://zfb.takazudomodular.com/guides/migrating-to-v3/#components-and-islands).
- **Env**: no `ZFB_TAILWIND_BIN`/`ZFB_TAILWIND_OXIDE_WARMUP` anywhere (`grep -rn ZFB_TAILWIND .` -> 0). Nothing to remove.
- **`scripts/bootstrap_doc.sh:9`**: `create-zudo-doc@5.27.0` -> the 6.x generator; the copied `doc/zfb.config.ts` must already be the 6.0-compatible one, otherwise the fresh scaffold inherits a 5.x config.

### 2. CSS and utilities

`doc/src/styles/global.css` is 10 lines and every one of them is either removed or package-owned in v3:

```css
@layer zd-preflight, zd-flow;                                  /* 1: keep or drop per 6.0 template */
@import "tailwindcss/preflight" layer(zd-preflight);           /* 2: ZW009 in v3 */
@import "tailwindcss/utilities";                               /* 3: ZW009 in v3 */
@import "@takazudo/zudo-doc/theme.css";                        /* 4-8: package-owned, 6.0 decides */
@import "@takazudo/zudo-doc/safelist.css";                     /*    safelist.css is a Tailwind @source inline() file -> planned removal */
...
@source "src/content/**/*.{mdx,md}";                           /* 9: ZW009 in v3 */
@source "pages/**/*.{tsx,ts,jsx,js}";                          /* 10: ZW009 in v3 */
```

- Lines 2, 3, 9, 10 are `ZW009` errors in v3 even under `wind: false` (https://zfb.takazudomodular.com/zudo-wind/coming-from-tailwind/#directives). Replace the whole file with the `global.css` that `create-zudo-doc@6` emits; do not hand-edit around the imports.
- There is no `@theme`, no `@apply`, and no authored rule in this file, so the host contributes **no tokens and no `authoredClasses`**. The reset (planned `owned-v1` plus a preflight-delta block in zudo-doc's `theme.css`) and the cascade order are package decisions; verify the five items the official guide names (headings, lists, `code`/`pre` font stacks, `sub`/`sup`, `::placeholder`, `[hidden]`) on the components index and one record page (https://zfb.takazudomodular.com/zudo-wind/coming-from-tailwind/#differences-from-tailwind-preflight).
- Audit result (`zfb wind audit --project-root doc` with a temporary `{ wind: { spec: 1 } }` config, zfb 3.1.0): `unrecognized classes: (none)`, `dead classes: (none)`, `dynamic constructions: (none)`, `diagnostics: (none)`. The standalone plan scans `pages components layouts content src`; zudo-doc's own classes will arrive through its 6.0 manifest, which this audit cannot see (https://zfb.takazudomodular.com/api/cli/#zfb-wind).
- `public/prototype/scope-ui.js`, `public/models/*.js` and `offline/style.css` are static assets served verbatim and are outside zfb's CSS pipeline; unaffected.

### 3. Components and islands

None owned by the host. `doc/` has no `pages/`, no `src/components/`, no `chromeBindingsModule`, and the 47 MDX files contain no JSX (`<CategoryNav>` style package components are not used either). All chrome, islands (`imageEnlarge`, `assetViewer`, search) and routes are `@takazudo/zudo-doc` code and move to zudo-react inside the 6.0.0 package.

If you later add MDX JSX, note the v3 dialect: `class` not `className`, `style={{ "background-color": ... }}`, no `on[A-Z]` props (https://zfb.takazudomodular.com/guides/migrating-to-v3/#components-and-islands). The generator `scripts/build_docs.py` currently emits only Markdown constructs (headings, tables, lists, links), which is the safest shape.

## Risks and open questions

- **Preset-first ordering is non-negotiable.** Installing `@takazudo/zfb@3` while `@takazudo/zudo-doc` is 5.x fails at config load with the `framework`/`tailwind` migration errors; there is no partial state.
- **Reset differences.** Content is generated tables/lists; `owned-v1` removes list markers and heading sizes, which zudo-doc's `content.css` is expected to restore. Check `## Pin map` tables and bullet lists in `components/records/*.mdx` after the port.
- **`zfb check` could not be run in this diagnosis** (preset imports need `node_modules`); the audit and greps are the only measured facts.
- **Hand-added `tailwindcss` devDependency**: harmless today, but if someone later imports from it directly it becomes a ZW009 trap. Remove it now.
- Does the handoff still want a native zudo-doc build at all? The `offline/` mirror is self-contained; if the audience only reads `offline/index.html`, the cheapest path is to retire `doc/` from CI until 6.0.0 lands rather than keep a 2.x build alive.
