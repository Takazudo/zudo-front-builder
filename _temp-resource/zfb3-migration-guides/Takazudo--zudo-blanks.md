# zfb v3 migration guide: Takazudo/zudo-blanks

Generated 2026-10-04 by an automated diagnosis of `main` @ `b1a3ef9`, audited with the zfb 3.1.0 CLI. zfb 3.2.0 shipped during the diagnosis (2026-10-04 15:30 UTC; https://zfb.takazudomodular.com/changelog/zfb/v3.2.0/), so every release label below was checked against its notes. Counts come from the commands listed; re-run them locally before relying on them.

## Verdict

**Blocked (upstream), effort S.** `doc/` is a create-zudo-doc 5.26.5 scaffold (README.md:35) with a stock host stub `pages/docs/[[...slug]].tsx`, a 74-line `global.css` whose last 44 lines are ordinary authored CSS, and 35 content pages. The one host-side v3 break that is not template-owned is **75 `className=` attributes in raw MDX JSX** (70 in `src/content/docs/catalog/index.mdx`, generated by `doc/scripts/generate_panel_catalog.py:122,125`, plus one `<img className="design-preview">` in each of the five `designs/*.mdx`); zudo-react rejects React-style spellings, so these must become `class=` and the generator and its checker (`check_panel_catalog.py:22`) must follow. That change is safe on 5.x today. Everything else waits for `@takazudo/zudo-doc` 6.0.0, because 5.x's `zudoDoc()` still supplies `framework`/`tailwind` and a preset carrying a removed key fails configuration loading (https://zfb.takazudomodular.com/guides/migrating-to-v3/#before-you-start). The repo also contains a **second zfb config**, `artwork-resources/pcb-art/docs-overlay/zfb.config.ts`, which is planning material for a site that was never scaffolded (no `package.json`, no `pages/`, no CSS, not built by any workflow); it needs a disposition decision, not a port.

## Sequencing and blockers

1. **Upstream gate:** `@takazudo/zudo-doc` 6.0.0 (epic zudolab/zudo-doc#4430, root PR #4477, consumer guide #4473). The zfb side is done: zfb 3.2.0 (npm `latest`, published 2026-10-04 15:30 UTC, https://zfb.takazudomodular.com/changelog/zfb/v3.2.0/) ships the fixes zudo-doc's integration floor was waiting for (Takazudo/zudo-front-builder#3569/#3570), so expect 6.0.0 to pin 3.2.0 or later. No zfb bump before the preset bump.
2. **Now, independent of the gate:** change `className` -> `class` in the generator, the checker and the five design pages (section 3); optionally bump 2.20.1 -> 2.22.1 and 5.26.5 -> 5.28.2 to shorten the jump (`grep -ci breaking` over zfb's `changelog/zfb/v2.*.mdx` matches only v2.0.0; zudo-doc's CHANGELOG has no `Breaking Changes` heading between 5.8.0 and 5.28.2). zudo-doc 5.28.0 changed heading extraction around multiline JSX, which affects `check:links` on `catalog/index.mdx`; run `pnpm check:links -- --strict-anchors` after the bump.
3. **Now:** decide the overlay's fate (section 4). Its `bootstrap_zudo_doc.py` is unpinned, so on the day 6.0.0 is `latest` it will scaffold a v3 project automatically, but the overlay's `zfb.config.ts` keys must then match 6.x `zudoDoc()`.
4. **After 6.0.0:** regenerate the four host-owned files from `create-zudo-doc@6` (`package.json`, `tsconfig.json`, `pages/docs/[[...slug]].tsx`, `src/styles/global.css`), re-append the authored CSS block, re-run the Netlify pipeline.

The only lockfile is `doc/pnpm-lock.yaml` (there is no root workspace); regenerate and commit it, because `.github/actions/build-zudo-doc/action.yml:39` installs with `--frozen-lockfile`.
- **`doc/zfb.config.ts`**: the spread form `{ ...zudoDoc({...}), copyPublicWithBase: false }` stays valid; the host adds no removed key. Two details inside the kept block:

- `global.css:41` and `:43` read `var(--color-border, #d5d9dd)` and `var(--color-surface, #fff)`. Only `--color-surface` is a zudo-doc 5.x `@theme` variable (`packages/zudo-doc/src/theme.css:94`, `--color-surface: var(--zd-surface)`); `--color-border` is defined nowhere in zudo-doc 5.28.2, so the `#d5d9dd` fallback is what renders today. In v3 configured tokens are emitted as `--zw-color-*` (https://zfb.takazudomodular.com/zudo-wind/tokens/#emitted-variables); zudo-doc 6.0 plans to keep its theme as authored `:root` custom properties, so `--color-surface` may or may not survive. The fallbacks make this non-fatal; check the catalog cards' border/background in both schemes after the port and switch to whichever variable 6.0 documents.
- Utilities move **after** authored CSS by default in v3. None of the kept selectors shares an element with a utility class (the catalog markup uses only `panel-grid`/`panel-card`), so the tie flip does not apply here (https://zfb.takazudomodular.com/zudo-wind/coming-from-tailwind/#utility-placement-and-ties).

Reset: zudo-doc 6.0 is planned to select `owned-v1` plus a preflight-delta block. The catalog relies on default `h3`, `p`, `small`, `code` styling inside `.panel-card`; `owned-v1` resets heading size/weight and list markers, so compare `/docs/catalog` and the five design pages (tables, `<img>` sizing, `<small><code>`) before/after (https://zfb.takazudomodular.com/zudo-wind/coming-from-tailwind/#differences-from-tailwind-preflight).

### 3. Components and islands

**Host JSX in MDX (the real work item).** zudo-react accepts HTML spellings only; `className` is rejected with a dialect error that names the authored file, line and column (https://zfb.takazudomodular.com/guides/migrating-to-v3/#components-and-islands, https://zfb.takazudomodular.com/zudo-react/server-rendering/#read-a-render-failure). Change:

- `doc/scripts/generate_panel_catalog.py:122` `'<div className="panel-grid">'` -> `'<div class="panel-grid">'`; `:125` `'<article className="panel-card">'` -> `'<article class="panel-card">'`.
- `doc/scripts/check_panel_catalog.py:22` `CATALOG.count('className="panel-card"')` -> `CATALOG.count('class="panel-card"')`.
- Regenerate `doc/src/content/docs/catalog/index.mdx` (`python3 doc/scripts/generate_panel_catalog.py`, per `workflow/panel-previews.mdx:11`) and edit the five `designs/*.mdx` lines (`coral-vault.mdx:34`, `spider-nest.mdx:34`, `fault-line.mdx:35`, `kumiko-void.mdx:41`, `woven-maze.mdx:35`): `<img className="design-preview" ...>` -> `<img class="design-preview" ...>`.
- The `<a href>`, `<img src alt loading="lazy">`, `<h3>`, `<p>`, `<small>`, `<code>` attributes used in the catalog are all in zudo-react's finite vocabulary (`loading` is in the 3.1.0 and 3.2.0 attribute list; https://zfb.takazudomodular.com/zudo-react/components-and-jsx/), so no other rewrite is expected.

Do this now: the 5.x MDX pipeline accepts `class` as well, so the change is forward-compatible; verify with `pnpm build` and a look at `/pj/zblanks/docs/catalog` in `pnpm preview`.

**`pages/docs/[[...slug]].tsx`** (67 lines) and **`pages/index.tsx`**: template-owned stubs. Do not port by hand; take the 6.x generator's versions (planned: pragma removed, `JSX` type import replaced, same `createRouteContext`/`createChrome` seams). The `docHistory` patch (static `DocHistory` import, lines 34 and 42) is applied by the generator when the feature is on.

No host `chromeBindingsModule`, no `src/components/`, no `"use client"` modules, no form controls: nothing in the hooks-to-signals map applies (https://zfb.takazudomodular.com/zudo-react/coming-from-preact-hooks/).

## Risks and open questions

- **Preset ordering**: `@takazudo/zfb@3` with `@takazudo/zudo-doc@5.26.5` fails at config load (`framework`/`tailwind` migration errors). Bump the preset first, always.
- **`--color-border` / `--color-surface` names** in the authored card CSS may change with zudo-doc 6.0's token emission; fallbacks hide a mismatch visually only partly (border grey vs theme border). Verify in dark mode.
- **Reset delta** (`owned-v1` vs Tailwind preflight): `h3`/`p`/`small` inside `.panel-card` set their own sizes, but `img` display/`sub`/`sup`/`::placeholder` differences are package-level; watch the search input.
- **`check:links` and multiline JSX**: zudo-doc 5.28.0 changed heading extraction around JSX; the catalog page is the largest JSX-bearing MDX in the repo (34 KB). Re-run with `--strict-anchors` after each bump.
- **Overlay config drift**: an unmaintained second `zfb.config.ts` with `zudoDoc()` 5.x keys will silently rot; `bootstrap_zudo_doc.py` floats on `pnpm create zudo-doc` latest.
- **Not run here**: `zfb check` (needs `node_modules`), the Netlify build, any browser comparison. The audit and greps are the measured part.
