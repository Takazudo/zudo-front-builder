- **Data-type hints are not supported** (https://zfb.takazudomodular.com/zudo-wind/coming-from-tailwind/#variants-and-grammar, https://zfb.takazudomodular.com/zudo-wind/utility-grammar/): 13 `[color:…]` candidates in the host — `text-[color:var(--sg-muted)]` ×6, `text-[color:var(--sg-fg)]` ×2, `hover:text-[color:var(--sg-fg)]`, `text-[color:var(--sg-accent)]`, `border-[color:var(--sg-border)]` ×2, `border-[color:var(--sg-border-strong)]`. On 3.1.0 the audit reports 9 of them as ZW005 errors ("value is not valid for font-size" / "… border-top-width") and the 4 inside the `TAB_ON`/`TAB_OFF` constants (`ui-variant-workbench.tsx:23-24`) only as `auditInfo`; on 3.2.0 all 13 are errors with the clearer message "data-type hint `color:` is not supported; zudo-wind v1 has no type-hint grammar, so write the value without it". **Do not just strip the hint**: `text-[var(--x)]` and `border-[var(--x)]` are *ambiguous* between families (3.2.0 reports `border-[var(--sg-border)]` as "value is ambiguous across catalog entries"; 3.1.0 silently resolved it to a width). Name the zudo-sg shell variables as color tokens instead and rewrite the 13 class strings:

  ```ts
  // packages/styleguide-next/zfb.config.ts — add to the host's wind fragment
  wind: {
    tokens: {
      colors: {
        "sg-fg": "var(--sg-fg)", "sg-muted": "var(--sg-muted)", "sg-accent": "var(--sg-accent)",
        "sg-border": "var(--sg-border)", "sg-border-strong": "var(--sg-border-strong)",
        "sg-surface": "var(--sg-surface)", "sg-surface-2": "var(--sg-surface-2)",
      },
    },
  }
  // then: text-[color:var(--sg-muted)] → text-sg-muted, border-[color:var(--sg-border)] → border-sg-border,
  //       bg-[var(--sg-surface)] → bg-sg-surface (optional; the arbitrary form already resolves)
  ```

  Verified on 3.1.0 and 3.2.0 with exactly this snippet: `text-sg-muted`, `border-sg-border`, `hover:text-sg-fg`, `bg-sg-surface-2` all resolve (`value status: categoryUnverified`, the documented outcome for `var()` token values — https://zfb.takazudomodular.com/zudo-wind/tokens/, "Validating values"). `colors` and `fontSizes` names must stay disjoint because both feed `text-*` (same page); zudo-doc's `heading`/`small`/`caption` font sizes and these `sg-*` colors do not collide. - **`underline-offset-2`** (`pages/ui/[slug].tsx:59`) is ZW006 on 3.1.0 (no `underline-offset-<n>` utility) and resolves as a utility on **3.2.0** (spec revision 4; verified with `zfb wind explain`: `outcome: resolved utility`, `value status: verified`). No change needed once the pin is ≥ 3.2.0.
- **`TAB_BASE`/`TAB_ON`/`TAB_OFF`** (`src/ui/ui-variant-workbench.tsx:22-24`) are `const` strings concatenated into `class=` at `:69`. 3.2.0 traces a same-module constant that is declared once with `const` and never reassigned as a class position (https://zfb.takazudomodular.com/zudo-wind/sources-and-candidates/), which is why its four `[color:…]` hints turn into errors there; the five token-less classes on `:22` (`rounded-sm`, `px-hsp-sm`, `py-vsp-3xs`, `text-caption`, `leading-normal`) are still reported as ZW006 `auditInfo` on both versions, but a build resolves them like direct classes (https://zfb.takazudomodular.com/guides/migrating-to-v3/#stylesheets) — they need the same tokens as the direct uses.
- The 9 `sg-*` classes in `pages/ui/index.tsx:28-39` are ordinary class text (verified: `zfb wind explain -- sg-tile` → "ordinary class"); no `authoredClasses` entry needed (https://zfb.takazudomodular.com/zudo-wind/coming-from-tailwind/#classes-that-used-to-emit-nothing).

## Risks and open questions

- **`doc/` and `manual/` wait on one upstream release** (zudo-doc 6.0.0 — zfb 3.2.0, which unblocks zudo-doc's integration floor, shipped 2026-10-04), the pilot on a second (zudo-sg v3). 39 of zudo-doc's 51 topics exist only on the maintainer's local branch; the timeline is unknown.
- **The pilot's roadmap predates zfb 3.** `docs/styleguide-migration/next-phases.md` schedules Phase 2 engine work (E1–E7) and Phase 3 catalog adoption on a Preact-only zudo-sg; zudo-sg must now also be rewritten on zudo-react/zudo-wind before any of that. Re-decide whether `packages/styleguide-next` is kept frozen at 2.20.3 (it is not deployed, so it can stay red for a while), re-planned, or retired.
- **Token ownership between zudo-doc 6, zudo-sg v3 and the host** (`vsp-*`/`hsp-*`, `text-heading`/`small`/`caption`, `--sg-*` colors). Preset and host `wind` objects merge recursively with the host's value winning (https://zfb.takazudomodular.com/zudo-wind/configuration/, "Strict validation and merging"), so a host token with a preset's name silently overrides it rather than failing; `colors`/`fontSizes` (and `fontFamilies`/`fontWeights`) names must additionally be disjoint (https://zfb.takazudomodular.com/zudo-wind/tokens/). Wait for both presets' token sets, then add only the names neither preset declares.
- **Package CSS subpath imports** (`@takazudo/zdtp/dashboard/styles.css`): resolve through zdtp's `exports` map (https://zfb.takazudomodular.com/concepts/styling/); zdtp 0.8.3/0.8.5 export the subpath as a plain string target and the `exports` resolution fix (#3364) shipped in zfb 3.1.0, so this is expected to work — verify on the first v3 build rather than treating it as a blocker.
- **Reset differences**: today both sites load Tailwind preflight in `@layer zd-preflight`; zudo-doc 6 moves to `owned-v1` + an authored delta. Form controls (search input), `[hidden]`, `::placeholder` and `sub`/`sup` are the documented gaps — a pixel diff on a page without them will not catch regressions.
- **CI blind spot**: doc/manual builds run only in deploy workflows. Until an explicit check is added to `pr-checks.yml`, a v3 regression reaches the `develop` preview before anyone sees it.
- **`zfb check` could not be run on this clone** (preset imports need `node_modules`); the 0-error audit for `doc/`/`manual/` covers utility classes only, not type or config validity.
- Open question for the owner: should `doc/` and `manual/` be re-scaffolded with `create-zudo-doc@6` and the content directories copied in (both hosts are pure scaffold output plus `zfb.config.ts` options), or migrated in place? Re-scaffolding is cheaper here and is what `ZUDO_DEPS_PINS.md`'s three-way-merge procedure already anticipates.
