Generated 2026-10-04 by an automated diagnosis of `main` @ `4a833e2`; the `zfb wind audit` census used the zfb 3.1.0 CLI. zfb 3.2.0 was released (npm `latest`, https://zfb.takazudomodular.com/changelog/zfb/v3.2.0/) while this diagnosis was being written, so every pin and label below targets 3.2.0. ## Verdict

**Blocked** on zudo-doc 6.0.0 (zudolab/zudo-doc#4430, root PR zudolab/zudo-doc#4477, consumer guide zudolab/zudo-doc#4473), whose zfb-side blockers (zfb #3569/#3570) shipped in zfb 3.2.0 (released 2026-10-04, https://zfb.takazudomodular.com/changelog/zfb/v3.2.0/) — the zudo-doc side is unblocked and only its 6.0.0 release is outstanding. Every zfb usage in this repo goes through `@takazudo/zudo-doc` 5.28.1: the developer doc site (`doc/`), the hosted generator that emits a zudo-doc project per customer publish (`packages/zudo-doc-cloud/src/core/hosted-generator/`), and the container that runs `zfb check`/`zfb build` on that project (`packages/zudo-doc-cloud-builder`). Effort **XL**: beyond the usual host edits, the generator's five route/CSS templates are Preact- and Tailwind-specific, the builder image ships a root-owned adapter for the removed `ZFB_TAILWIND_BIN` hook and derives three attested identities from the pin, and the SPA's preview frame mounts zudo-doc's Preact chrome components in-process with `preact.render()` (41 `@takazudo/zudo-doc/*` imports across 13 frame files), which cannot host zudo-react components. Nothing here can ship before 6.0.0, because zfb 3 + zudo-doc 5.28.1 fails config loading (the preset still supplies `framework`/`tailwind`; https://zfb.takazudomodular.com/guides/migrating-to-v3/#before-you-start). The SPA's own Tailwind (Vite) and Preact are **unaffected** by zfb 3.

## Sequencing and blockers

1. **zfb side: done — pin 3.2.0.** zudo-doc's integration floor (zudolab/zudo-doc#4467) was blocked on zfb #3569 (Wind extractor UTF-8 offsets) and #3570 (quoted island markers in highlighted code); both shipped in zfb 3.2.0 (released 2026-10-04, https://zfb.takazudomodular.com/changelog/zfb/v3.2.0/), as did the two items that matter to the builder image: the Linux glibc floor lowered to 2.34 (#3584) and the Cloudflare worker dangling source-map refs (#3480, `@takazudo/zfb-adapter-cloudflare` 3.2.0). Pin 3.2.0 exactly — 3.2.0 is a minor, so a `^3.1.0` range still admits the 3.1.0 build panic (#3569).
2. **zudo-doc 6.0.0 published** (zudolab/zudo-doc#4430; PR #4477 draft with 102 commits — `base/zfb3-migration` @ 70e0875 is pushed, only the #4467 integration topic is still local; 39/51 topics merged as of the 2026-10-02 checkpoint; with #3569/#3570 released the zudo-doc side is unblocked, but 6.0.0 is not published). Its consumer guide (#4473) is the authority for the exact `global.css`, `tsconfig`, and chrome-binding API changes; this guide names the surfaces, not the final bytes.
3. **One lockstep pin bump in this repo** (CLAUDE.md:296-301 "Keep these exact pins in lockstep"): `doc/package.json`, `packages/zudo-doc-cloud/package.json`, `packages/zudo-doc-cloud-builder/package.json` + its own `pnpm-lock.yaml`, `contract.ts` `packages`/`toolVersions`, then `generate:release-policy`, then the attestor-before-builder rollout (`ops/hosted-sites/rollout.md:204-262`). Use the repo's own tooling: `/dev-bump-zudo-deps`, `/l-follow-zudo-doc-update` (checked SHA `7151a5f5`, fetched 2026-09-27 per `references/upstream-review-efcc346f-7151a5f5.md` — the review range to 6.0.0 will be large), `/l-env-update production deploy`.
4. **Multi-version question (5.x and 6.x hosted sites).** The platform already separates *retained artifacts* from *new builds*:
   - Published artifacts are immutable static `dist/` objects; `artifact-build-policy.json` retains one policy entry per past release (`zudo-doc-5.21.0-v2-current` … `5.28.1-v2-current`, `policies[]`), and `freeze.ts:717-735` `storedGeneratorContract` maps every historical `generatorVersion` to its contract id, so 5.x sites keep serving and keep validating unchanged after the cutover. Nothing has to be rebuilt.
   - New builds run on exactly one runtime: `HOSTED_BUILD_RUNTIME.builder` is a single frozen constant (`builder/src/limits.ts:73`), `HostedBuilderWorkflow` refuses a mismatched `BUILDER_RUNTIME_VERSION` (`src/index.ts:91`), the sandbox handshake re-checks it (`sandbox-build.ts:126`, `builder-runtime`), and the manifest says `activeDeployment: "exactly one version at 100 percent"`.
   - A customer project's *source* (markdown, outline, preset JSON) is framework-neutral; the generator synthesizes the zfb project per build. The first publish after the cutover therefore moves a site from 5.x to 6.x with no customer action; until then it serves its retained 5.x artifact.
   - Recommendation: **single cutover, no dual-runtime builder.** CLAUDE.md:12-23 ("Development status") explicitly rejects mixed-version compatibility gates pre-release. Running 5.x and 6.x builds side by side would need a second container image, a per-request runtime selector in `HostedBuildRequestV1`, a second `BUILDER_RUNTIME_VERSION`, and two active attestor policies — a product decision outside today's contracts. Re-open it only if the service is declared released before 6.0.0 ships.
5. **Can be done now:** inventory and design only (this guide; a prepared branch for the builder runtime-identity change and the generator template rewrite, left unmerged). Nothing can be verified or merged before 6.0.0 because the container image, the doc site and the generated site all load the zudo-doc preset.

## Risks and open questions

- **Canonical injection on the home route** (`ROOT_ROUTE_SOURCE`) relies on Preact VNode cloning with no zudo-react equivalent; needs a zudo-doc 6 hook or a different mechanism (e.g. `siteUrl` already passed to `zudoDoc()` at `generate.ts:493`). Raise on zudolab/zudo-doc before 6.0.0 freezes its public types (#4465).
- **Preview-frame runtime split** (Preact SPA hosting zudo-react chrome) is the biggest unknown: `mount()` needs an `IslandIdentity`/wrapper contract designed for zfb islands, and `renderToString` plus script replay changes how `frame-lifecycle.ts` drives `zfb:after-swap`. Budget it as its own epic.
- **Attestor CSS scanner vs wind output** (`@property`, layer prelude, unlayered utilities) — a mismatch blocks all publishing; test against a real 6.0 `dist/` first.
- **Binary loads in the container:** the glibc floor fix (#3584) shipped in zfb 3.2.0; a 3.1.0 image may fail to start zfb on `cloudflare/sandbox:0.12.5`, so build the first candidate image on 3.2.0. `proof:networkless` tells you in one run.
- **Policy hash churn:** `javascriptObjectHashes`/`moduleObjectHashes` (zudo-react client runtime replaces the Preact islands bundle), `wasmObjectHashes`, `inlineScriptHashes`, `styleObjectHashes` (fonts) all rotate; `styleObjectHashes` already carries documented legacy drift (README #1532), so expect `release-policy-pin-drift` until regeneration.
- **zudo-doc 6 output-file contract** (`search-index.json` keys, `llms.txt` layout, route counts in `validateExpectedTree`/`HOSTED_RENDER_LIMITS.maxGeneratedOutputs`) is promised parity but unverified until `generated:proof:localized` runs; the public-mcp parser is strict.
- **No tracking issue yet.** zudo-doc-cloud has no issue for zfb 3 / zudo-doc 6 (search of 194 issues finds only 5.x follow epics, latest #2272). Open an `[Epic]` when 6.0.0 is near, with the preview frame, the generator templates, and the builder runtime identity as separate subs.
