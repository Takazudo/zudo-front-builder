## hardProblems
  - ISLAND BOUNDARY READS THE CHILD DESCRIPTOR. packages/zfb/src/island.ts derives the marker name from `children.type.displayName ?? children.type.name` (:267-290) and serialises `children.props` minus `children` via JSON.stringify, silently dropping functions/undefined and swallowing cycles/BigInt (:311-366). This only works if zudo-react's `jsx()` returns an inert description exposing `type` and `props` and does NOT invoke the child component eagerly. The handoff (03 s2, s6) does specify a description model, but it also demands the opposite serialisation policy: REJECT unsupported values rather than drop them, and carry schema/protocol/build identity per island. docs/src/chrome-bindings.tsx:12-16 additionally calls `Island({...})` as a plain function, so Island must stay callable outside JSX.
  - MARKER NAME DEPENDS ON FUNCTION.name. The SSR marker comes from the runtime function name while the client manifest key comes from the scanner's static analysis (esbuild.rs:2925-2950 comments; the code already records that esbuild minification renames functions). Today they agree because SSR bundles are not minified in a way that breaks it. The handoff asks for a build-assigned stable identity. Changing this touches scanner.rs, esbuild.rs glue, island.ts, crates/zfb-islands/src/hydration.rs (lol_html rewrite of `div[data-zfb-island=""]` skeletons :484-559), crates/zfb/src/commands/island_marker_check.rs and docs/scripts/assert-island-markers.mjs.
  - TWO RENDER MODES IN ONE TREE. zfb renders a whole `<html>` document in one synchronous pass and hydrates only island subtrees. zudo-react hydration needs deterministic comment markers (handoff 03 s7) but static pages must not carry them. The switch has to happen at the `<Island>` boundary inside a single server render, with per-render isolated counters and a root identity supplied by zfb. Nested islands are already treated as an error case by runtime.ts (:542-564 self-wrapping guard) and need an explicit rule.
  - BYTE-EXACT CONSUMERS OF SSR OUTPUT. (a) The render-artifact extractor is an exact-byte state machine over `<template data-zfb-render-region="start|end" data-zfb-region-id="..."></template>` (crates/zfb/src/commands/render_artifact.rs:17-19, crates/zfb-types/src/render_region.rs; content.ts:526-534 requires NO text nodes between the three fragment children). Attribute order, quoting and void/non-void serialisation of `<template>` must match or the extractor must change in lockstep. (b) 18 committed HTML snapshots (crates/zfb-build/tests/snapshots/e2e_routing_rendering/). (c) About 84 `contains("<tag` assertions across 30 Rust test files. (d) render_artifact_determinism_build asserts a byte-identical dist tree across builds. (e) head_inject.rs:145-175 prepends the doctype host-side because the renderer emits `<html>` first with no doctype - the new serializer must keep that shape or the sniff must change.
  - MINIFIED HTML VERSUS FAIL-CLOSED HYDRATION. crates/zfb/src/commands/html_minify.rs sets `keep_comments = true` (:56), so comment markers survive, but minify-html 0.18.1 collapses text whitespace and unquotes attributes. Preact's hydrate tolerates that; the zudo-react contract is fail-closed on structural or initial-content mismatch (handoff 03 s8). Either the preflight compares against a normalised form or minification must be proven not to touch island subtrees. Needs a real `minifyHtml: true` browser test, not a unit test.
  - MDX EMITTER CONTRACT IS REACT-SHAPED. crates/zfb-content/src/mdx_jsx_emit.rs emits (1) a hard-coded `react/jsx-runtime` Fragment import (:609), (2) elements whose type is looked up in a `_components` map where each value is EITHER a string tag OR a user component function, (3) `dangerouslySetInnerHTML` for highlighted code (14 lines; visible in the md-wasm golden outputs as `_jsx("span", { dangerouslySetInnerHTML: { __html } })`), (4) style OBJECTS with camelCase keys (`clipPath`, `whiteSpace` in the footnote sr-only heading) and table-alignment style, (5) both `class` and `className` attribute spellings, (6) `data-*`/`aria-*` string attributes. In development mode SWC emits `jsxDEV` with the 6-argument signature. zudo-react/jsx-runtime and jsx-dev-runtime must accept all of this, or the emitter must be changed and every golden regenerated.
  - RAW HTML INSERTION IS EXCLUDED FROM zudo-react v1 BUT REQUIRED BY zfb. The handoff (03 s3, s6) excludes 'generic raw HTML insertion' and says a trusted-HTML escape hatch needs separate design. zfb depends on it in four places: MDX syntax highlighting (static, server-only), `<ClientRouter>`'s `<style>` (client-router-component.ts:196), the template's pre-paint `<script>` (templates/basic-blog/layouts/default.tsx), and two REACTIVE uses where state drives innerHTML after a wasm call (tests/md-wasm-browser-smoke/.../md-wasm-highlighter.tsx:22, docs/src/components/playground/highlight-playground.tsx). Static and reactive cases need different answers; `<script>`/`<style>` raw-text elements also cannot host comment markers.
  - COMPONENT RETURN SHAPES OUTSIDE 'ONE ELEMENT'. `ClientRouter()` returns a bare array of keyed elements, not a fragment (client-router-component.ts:185-247), and passes `key` as jsx's third argument (:129). Page default exports may be `async` (11 fixture pages) and may return a STRING, which the router passes through without rendering (packages/zfb-runtime/src/router.ts:523-547). Pages use member-expression components (`<post.Content />`). templates/basic-blog/components/callout.tsx holds JSX fragments in a module-level const reused by every render, so descriptions must be safely reusable and must never be mutated or consumed by a render. zudo-react excludes async COMPONENTS; the top-level await lives in the router so pages are fine, nested async components are not.
  - REACTIVE STRUCTURE IS NEEDED BY REAL COMPONENTS. zudo-react v1 supports reactive text/attributes only and defers conditional regions and keyed lists (handoff 03 s3, s10). The shipped template's theme toggle swaps an svg subtree on state (`isDark ? <>...</> : <path/>`), and the docs playgrounds render diagnostics lists and result panels from state (`.map(` 35 occurrences / 32 files across all tsx, most static, the playground ones reactive). Either ship Show/For-style primitives before migrating these, or rewrite each to static structure plus reactive `hidden`. The template is what `npm create zfb` produces, so it sets the public idiom.
  - FORM OWNERSHIP IN THE DOCS PLAYGROUNDS. 20 `value={` and 17 `checked={` controlled bindings with onInput/onChange across 5 files map onto the proposed `modelValue`/`modelChecked`, which v1 limits to text input, textarea and checkbox; select and radio are explicitly deferred. The playground option rows need auditing for select/radio use before the migration is sized. The custom hook `use-wasm-module.ts` (last-started-run-wins, dispose on unmount) has to become scope-owned activation/cleanup, and zudo-react v1 deliberately has no general `effect()`.
  - SINGLE RUNTIME IDENTITY ACROSS STAGED COPIES. zfb stages node_modules through symlinks, real copies, embedded-vendor extraction and per-package `.pnpm` layouts; two tests exist specifically because a duplicated Preact instance broke hooks/context (build_package_routes.rs:415, :2210, plus bundler.rs:7686 comment about 'two Preact options objects'). Signals have the same failure mode: a signal created by one copy of zudo-react is a plain object to another copy, so `{count}` would render as text or throw. The risk is higher than before because zudo-react is FIRST-PARTY and reachable three ways at once: packages/zudo-react in the workspace, the embedded vendor extraction, and a consumer's installed copy.
  - EMBED PATH ASSUMES SCOPED PACKAGES AND .ts FILES ONLY. `embed_runtime` writes under `$OUT_DIR/vendor/@takazudo/` and `copy_ts_src` copies only `*.ts` (crates/zfb/build.rs:832-913). The handoff proposes the unscoped specifier `zudo-react` with subpaths `/jsx-runtime`, `/jsx-dev-runtime`, `/server`, `/client`. Either the package is scoped (`@takazudo/zudo-react`) or the embed layout gains an unscoped destination; and the package must contain no `.tsx` and resolve its subpaths through `exports` pointing at `src/*.ts`, as the two existing packages do. Both bundlers also carry `--alias:zfb=@takazudo/zfb` (bundler.rs:12930), so an analogous bare-name alias is a design option.
  - JSX TYPE SURFACE MUST BE AUTHORED. Today `zfb check` (tsc) gets `JSX.IntrinsicElements` and child types from preact's typings via `jsxImportSource`. With preact gone, zudo-react must ship its own intrinsic-element and attribute typings including reactive-value acceptance (a signal where a string is expected) and the reserved model props. This is a large typing surface with no runtime test coverage; the required Scaffold E2E job and `crates/zfb/tests/check_command.rs` fixtures (check-good, check-tsc-fail) exercise it.
  - md-wasm IS A SEPARATELY CONSUMED PUBLIC API WITH PINNED ARTIFACTS. `compile()`'s `jsxRuntime` option is public, the options struct is deny_unknown_fields, and the emitted import specifiers are part of the documented contract (npm/README.md:622-647). Any change to emitted strings changes the compiled wasm, and the repo pins CI-measured sizes and digests (root CLAUDE.md: never refresh shipped-sizes.json from a Mac build; every file with a shipped-size table must keep its digest disclaimer). The golden parity fixtures must be regenerated from a build, which this census was not permitted to run.
  - THE DOCS SITE AND THE PUBLIC IDENTITY FIXTURE CONSUME PUBLISHED PACKAGES. docs/ and packages/zfb-ssr-identity-fixture resolve zfb 2.20.2 / zudo-doc 5.27.0 / zudo-sg 0.3.4 from the registry and execute Preact hook components from those tarballs. The repo cannot become Preact-free, and the lockfile cannot drop preact, until zudo-doc and zudo-sg are migrated and republished - which itself requires a published zudo-react-based zfb. This is a strict ordering across three repositories, not a single-PR change.

## openQuestions
  - Package identity and distribution of zudo-react: (a) unscoped `zudo-react` as the handoff sketches, (b) scoped `@takazudo/zudo-react` as an 11th lockstep published package, or (c) no separate package - subpaths of @takazudo/zfb. This decides the embed layout in build.rs, the scaffold template's dependencies, the required Scaffold E2E job, the dist-tag scripts and whether the five-lane changelog contract becomes six lanes. The handoff explicitly leaves naming and publishing unsettled.
  - After the `framework` field is deleted, should a config that still contains `framework` be a hard error? `Config` has no deny_unknown_fields (crates/zfb/src/config.rs:6250), so by default it would be silently ignored. A hard error is louder for the zudo-doc migration; silent ignore is less code.
  - md-wasm `compile()`: delete the `jsxRuntime` option outright (callers passing it then fail, because the options struct is deny_unknown_fields), or keep the key accepting a single value? The aggressive-removal direction implies delete; confirm because md-wasm has its own consumers and changelog lane.
  - Should the MDX emitter import Fragment from the same specifier as jsx/jsxs (fixing today's split), and should it stop emitting `dangerouslySetInnerHTML` in favour of whatever trusted-HTML mechanism zudo-react defines?
  - Delete `hydrateIsland` from the SSR bundle (the `__zfb_internal_hydrate.jsx` shim) and the three `BundleManifest` fields `framework`, `jsx_import_source`, `hydrate_shim_specifier`? No production reader was found for any of them; they are asserted only by tests.
  - Delete crates/zfb-islands/npm (@zfb/islands-runtime)? No importer found. It is a workspace member whose tests run in health.
  - Delete `zfb_render::Renderer` and `ModuleLoader` (library-only render path, used only by crates/zfb-render/tests) rather than port them? `SwcPipeline` itself must stay for md-wasm.
  - Keep the React-motivated V8 host shims (MessageChannel/MessagePort, microtask-backed setTimeout/clearTimeout in web_polyfills.js)? They were added for React 19's server bundle, but user SSR code or zudo-react's scheduler may now rely on setTimeout existing. Removing them is a host-contract change independent of the framework swap.
  - React-only bundler behaviours being deleted: the `main,module` main-fields default and `--conditions=worker`. Does any dependency in zudo-doc/zudo-sg resolve only because of them? The `bundle.mainFields` config knob remains as the explicit escape hatch.
  - Islands scanner export filter: keep retaining call-expression exports (`memo()`, `forwardRef()`, `lazy()`) as island candidates, and keep the `$$typeof` object branch in the generated component-shape guard? With function-only components both could be dropped; dropping them changes which exports become islands.
  - Does zudo-react provide a non-JSX element constructor? `.ts` pages without JSX syntax currently call preact's `h()` (crates/zfb/tests/page_extension_full_matrix_e2e.rs:132-242), and SDK modules call `jsx()` directly to stay `.ts`.
  - Sequencing of the docs site: accept that docs/ stays on published Preact-based packages (and preact stays in the lockfile) until zudo-doc ships, or freeze/skip the docs build during the transition? The Docs gate is a required check that fires on every lockfile change.
  - Is a third-party Preact widget behind an explicit DOM boundary something any owned consumer needs? The handoff allows it as a consumer decision; zfb would then need NO support for it, but zudo-doc's audit should confirm.
  - Release shape: this is a breaking major for at least 4 of the 5 lanes. Stable straight to `latest`, or a `next` soak while zudo-doc migrates? The repo's dist-tag rule allows `next` only while it is strictly ahead of `latest`.
