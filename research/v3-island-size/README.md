# V3 island size measurement (#3468)

For the current PR #4234 refresh and the distinction between historical and new evidence, see [the candidate checkpoint](PR4234-CHECKPOINT.md).

This directory freezes eight small consumer recipes and two measurement paths. `measure-real.mjs` invokes the actual `zfb build` binary against temporary consumer projects and inventories **every emitted JS file** in `dist`, including the hashed islands entry, shared chunks, and lazy chunks. Each pass saves the complete `dist` tree, not only HTML and JavaScript, so the guard can compare the recorded inventory with the bytes on disk. The `no-island` build is real and must emit no JavaScript. The workspace and packed runs each execute that same CLI against a consumer whose `node_modules/@takazudo/zfb`, `node_modules/@takazudo/zfb-runtime`, and `node_modules/@takazudo/zfb-slugify` point to matching workspace or packed packages; `hono` points to the exact lockfile-installed 4.12.25 dependency. `measure.mjs` independently reproduces the shared-islands esbuild flag set and generated registration semantics with a modeled entry to retain esbuild JSON metafiles and input-byte attribution. Its byte totals are _sidecar diagnostics_, not the shipped-size baseline. Neither script reads, copies, changes, or weakens the bundler's private resource metafile or stage-escape audit.

The recipes are frozen in `fixtures/`: no island; event-only button; scalar signal; Show/For; modelValue binding; a blog menu plus theme toggle; JSON API fetch; and a scalar plus theme-toggle multi-island page. They are controlled current-source recipes, not exact historical #3383 inputs. Do not label their values as reproduced v2/v3 numbers. The multi-island comparison reports the difference from scalar alone, while each page's shipped total deduplicates chunks by filename.

Dependency-graph lock fingerprint (#4187; schemaVersion 3, see [below](#dependency-fingerprint-schemaversion-3)): `lock-fingerprint.mjs` hashes only the `pnpm-lock.yaml` content that can produce measured bytes, under the policy in [LOCK-FINGERPRINT-POLICY.md](LOCK-FINGERPRINT-POLICY.md). Run `node research/v3-island-size/lock-fingerprint.mjs --explain` to print the fingerprint and its inclusion inventory.

## Native collection workflow

`.github/workflows/island-size-darwin.yml` (display name `island-size-native`) collects native island-size evidence for both platforms from one `workflow_dispatch` entry point. The `platform` input selects the lane: `darwin-arm64` (default, job `measure-darwin` on `macos-15`), `linux-x64` (job `measure-linux` on `ubuntu-24.04`), or `both`. The Linux lane mirrors the island-size recipe in `health.yml` (build, pack, two `measure-real.mjs` runs, `normalize-identity.mjs`, `check-budget.mjs --contract research/v3-island-size/decision-linux-x64.json`) but does not run `pnpm test:workspace` first, so evidence can be collected while the T1 drift guard is red. It uploads a 30-day `island-size-linux-x64-<source-sha>` artifact.

The filename stays `island-size-darwin.yml` on purpose: `gh workflow run` only accepts a workflow path already registered on the default branch, and GitHub then uses the dispatched ref's file content and declared inputs. A new workflow file would be undispatchable until it reached `main`.

```sh
gh workflow run island-size-darwin.yml --ref <branch> -f ref=<sha> -f platform=both -f enforce=false   # collect
gh workflow run island-size-darwin.yml --ref <branch> -f ref=<sha> -f platform=both -f enforce=true    # enforce
```

## Health evidence retention and replay (#4260)

The ordinary `health.yml` Linux producer can collect evidence after a workspace-test failure when native setup, the native build, the pinned size toolchain, and package staging succeeded. Cancellation stops collection. The required job retains every original test and budget failure; collecting an artifact does not turn a failed run into a pass.

Its seven-day `island-size-linux-x64` artifact contains `real-workspace/` and `real-packed/`, including saved dist bytes and normalized sidecars. Upload requires both complete eight-fixture matrices, the exact measured checkout SHA, recomputed sidecars, and unchanged raw and normalized totals. The budget must either pass or report exactly the three old-Cargo-pin diagnostics accepted by `scripts/island-size-evidence.mjs`. Changed totals (including decreases), extra failures, stale output, and incomplete evidence are refused. This is collection eligibility, not re-pin admission.

For a downloaded archive, verify its SHA-256 against GitHub's artifact digest, preserve the original ZIP, and read the measured source from both `measurement.json` files. A PR's measured source can be its synthetic merge checkout, not its head. In that measured source's checkout, use its recorded Node/zlib toolchain and call the exported `assertCompletePair(artifactDirectory, contract, measuredSourceSha)` from `scripts/island-size-evidence.mjs`, with that source's `decision-linux-x64.json`. This verifies saved bytes, normalized sidecars, fixture completeness, source identity, and unchanged totals. It does not reconstruct the omitted package tarballs or native binary, replay the full budget checker, or establish fresh runtime provenance. Retain the original job's full budget verdict separately.

A formal replay of this Linux artifact must run on a linux/x64 host (`process.platform` `linux`, `process.arch` `x64`; WSL2 on x86_64 qualifies) with the Node and zlib versions recorded in its sidecar. At the time of writing those are Node v24.14.0 and zlib `1.3.1-e00f703`; use the official Node build, which reports them. The normalized sidecar records the normalizer's own `platform` and Node/zlib versions. `assertCompletePair` recomputes it on the replay host, so a host whose platform, architecture, Node version or zlib version differs refuses with `stale or altered normalized sidecar`, even when every size matches. That includes darwin/arm64, and a different Node v24 patch release on linux/x64. On another host you can recompute totals from the saved bytes as a diagnostic, but that is not a formal replay pass and cannot replace one. Do not relabel the host platform or edit the sidecar to get a pass.

**Status, by kind of evidence.**

- Completed migration: `decision.json` is schemaVersion 2 (`gzip-identity-normalized v1`, zero allowance), migrated from a retained native artifact (see "Darwin v4.3.2 metric migration"), and the workflow generates the sidecars it needs.
- Native verification: the contract was re-pinned (`release-bump`) from a native v4.4.0 measurement (see "Darwin v4.4.0 release baseline"). - Historical evidence: the earlier stale-contract runs and measurements below are preserved as recorded.

Re-pin: `rebaseline-island-size-darwin.mjs --reason release-bump` (or `runtime-identity`) re-pins a schemaVersion 2 Darwin contract to a new package version, lock hashes and normalizer digest (runner and fixture digests must already equal the contract) taken from a downloaded native Darwin arm64 artifact. ```

`--source-sha` must equal the artifact's measured source; the script rewrites `decision.json` and appends a README section. `--reason metric-migration` remains the schemaVersion 1 to 2 conversion.

Use the evidence in this order:

1. Measure the display-only bindings source SHA with enforcement off. A mismatch against the stale Darwin contract is expected; the run still writes PASS/FAIL and the checker output tail to the step summary and uploads the complete artifact.

3. Commit the contract update at the PR head. For PR runs, the workflow derives `enforce: true` only when `research/v3-island-size/decision.json` changed in `HEAD~1`; other measurement PRs report the checker result without making the budget mismatch fail the run.
4. Review the enforced remeasurement artifact and summary. A passing strict check on the rebaselined source confirms the exact Darwin contract.

The CI commands derive output paths from `GITHUB_WORKSPACE` and run natively on GitHub's macOS runner, so they do not use the local procedure's machine-specific absolute paths or heavy-guard wrapper. CI pins Rust 1.99.0 explicitly because `rust-toolchain.toml` follows stable. Before compiling, it records free disk space, refuses to build below 8 GiB, and disables Rust dev debug info when free space is below 20 GiB; the selected profile and native binary digest are retained in runner provenance. ## Reading the measurements

`initial` is the entry and its static-import closure plus any HTML-linked JS; `later` is every other emitted JS file, including lazy imports. `all shipped` adds every emitted JS file once, so dynamic splitting cannot reduce the reported total by hiding bytes. Raw is file byte length. Gzip is Node `zlib.gzipSync` level 9, `mtime: 0`, applied to each file before summing; HTTP transfer compression may differ. The JSON reports retain every chunk hash, raw/gzip size, phase, and all-dist reproducibility inventory. The modeled metafiles preserve each input's `bytes` and each output's `bytesInOutput`; those fields describe reachability and approximate contribution after tree shaking, not independent feature savings. Inspect `structure.ts`, `forms.ts`, `diagnostics`/reporting modules, and runtime inputs across the event/signal/Show-For/model cases before proposing a carve-out. A single scalar case with `--keep-names` disabled probes the global flag's whole-bundle cost; production always keeps it enabled.

The sidecar copies the production namespace import, named/default export fallback, function and identity checks, module label, registration closure, and `mountIslands` call. It still uses a fixed valid 16-character build identity instead of the real build hash; imports fixture components through relative temporary paths instead of production's absolute staged/shadow paths; and does not run the CLI's staging, resource read-back, or final entry-hashing steps. Its module labels use the fixture project's `components/<name>.tsx` spelling, matching the CLI's project-relative label for these fixtures. The sidecar excludes client-router activation because no fixture uses it. These differences can affect exact bytes and path metadata, so compare retained modules and input contributions as diagnostic evidence only. The real CLI output remains the size authority.

`measure-real.mjs` records measurements but does not enforce thresholds. `check-budget.mjs` enforces the per-fixture ceilings in the platform contract with zero allowance: the Darwin arm64 contract (`decision.json`) and the Linux x64 contract (`decision-linux-x64.json`) both pin raw and `gzipNormalized` (schemaVersion 2, below); schemaVersion 3 keeps those ceilings and replaces the whole-file lock pin with the dependency fingerprint. This is baseline protection, not an optimization result.

## Identity-normalized gzip (schemaVersion 2, #4131)

The islands entry embeds the 16-character lowercase-hex `zudo_react_build` token. The compiler emits it at exactly two sites per bundle inside `__zfb_register` — `identity: { component, build }` and the mount closure's identity const (`crates/zfb-islands/src/esbuild.rs`) — and once per island marker in HTML as `data-zfb-build` (`packages/zfb/src/zudo-react/render-html.ts`; `packages/zfb/src/zudo-react/hydrate.ts` and `root.ts` only read `identity.build`). The token is a source digest over the consumer project including its linked `@takazudo/zfb-runtime` sources (`crates/zfb-build/src/bundler.rs`, `zudo_react_build_token_with_snapshots`), so every runtime source edit and every version bump moves it. Its fixed length keeps raw totals identical while per-file gzip drifts by a few bytes, which turned the exact actual-gzip ceiling into a token detector: equal raw length is not byte equality and never proved unchanged product code.

`normalize-identity.mjs` is an additive layer that reads a saved measurement directory and writes a versioned sidecar, `measurement.normalized.json`, next to `measurement.json`. It does not modify `measure-real.mjs`, `measure.mjs`, or any emitted byte, and the production build identity is unchanged. Its metric is named `gzip-identity-normalized`, `normalizationVersion` 1, with these rules (also embedded verbatim in every sidecar):

- Read the token from every `data-zfb-build` attribute in the saved `index.html`. All must be one identical 16-character lowercase hex value; a malformed or disagreeing attribute is rejected.
- In each emitted JS file replace only exact `build:"<that token>"` occurrences in the emitted registration identity and mount-local identity shapes, outside comments and strings, with `build:"0000000000000000"`. The placeholder has the same length, so raw totals are unchanged by construction and the normalizer refuses any replacement that changes a length.
- Site counts are checked per role and were measured on the v4.3.1 Linux x64 artifact (health run 38075998971): the islands entry carries exactly 2 sites and no other 16-hex run; shared and lazy chunks carry 0. A different count is rejected — it means the compiler-owned shape changed and needs a new normalization version, not a silent accept. Hexadecimal strings in general and properties merely named `build` are never touched.
- Any recognized compiler identity site carrying a token other than the HTML's is rejected. A dist with JavaScript but no HTML token, or an HTML token with no JavaScript, is rejected. The `no-island` dist (zero JS, no token) legitimately has zero sites.
- `gzipNormalized` is `node:zlib gzipSync level=9 mtime=0` of the normalized bytes, summed per entry/shared/lazy role exactly like actual gzip. Actual gzip is kept per chunk and per sum as transfer-size evidence and is never compared with a normalized ceiling.

The normalizer proves pass-1 and pass-2 are byte-identical, recomputes every raw length, SHA-256, and actual gzip from the saved bytes, and rejects a `measurement.json` whose claimed chunk or total values disagree with them. The sidecar records `{raw, gzip, gzipNormalized, identitySites, sha256, sha256Normalized}` per chunk, initial/later/shipped sums, the observed token, the SHA-256 of the source `measurement.json`, and runner provenance including the normalizer's own SHA-256 and the Node/zlib that compressed. Run it as `node research/v3-island-size/normalize-identity.mjs --measurement <out>/measurement.json`; `health.yml` does so for both real modes before `check-budget.mjs`.

A schemaVersion 2 contract declares `"metric": "gzip-identity-normalized"`, `"normalizationVersion": 1`, pins `normalizerSha256` like the runner hashes, and sets `allowance` and every ceiling as `{raw, gzipNormalized}`. The normalizer digest covers both `normalize-identity.mjs` and `chunk-inventory.mjs` in filename-delimited order, because both files define the measured bytes and chunk roles. `check-budget.mjs` then requires each run to carry the sidecar, verifies the sidecar's normalizer hash, source hash, and version against the contract and the checked-out normalizer, recomputes the normalized metric from the saved bytes and fails if the sidecar is stale, and compares raw and `gzipNormalized` against the zero-allowance ceilings while printing actual gzip as evidence. A metric mismatch fails loudly in both directions: a schemaVersion 1 contract given a run with a sidecar, or a schemaVersion 2 contract given a run without one, is rejected with a `metric mismatch` finding, so legacy actual-gzip ceilings and normalized measurements are never compared with each other.

`scripts/rebaseline-island-size-linux.mjs` recomputes totals from a downloaded artifact's bytes. It takes nine reasons — `--reason release-bump|metric-migration|runtime-identity|lockfile-provenance|fingerprint-migration|fingerprint-helper|cargo-producer-lock|dependency-graph|fingerprint-policy` — and writes a matching `outcome` (`release-version-stamp`, `metric-migration`, `runtime-identity-repin`, `lockfile-provenance-repin`, `fingerprint-migration`, `fingerprint-helper-repin`, `cargo-producer-lock-transition`, `dependency-graph-repin`, `fingerprint-policy`), `platformStatus`, README section, and test pins. `metric-migration` needs a schemaVersion 1 contract, `lockfile-provenance` and `fingerprint-migration` a schemaVersion 2 contract, and `release-bump` and `runtime-identity` accept schemaVersion 2 or 3. Every reason refuses a raw change; every reason but `metric-migration` also refuses a `gzipNormalized` change, because the token is normalized away and a moved normalized total is product code moving. `lockfile-provenance` (#4184) records a consumer-only `pnpm-lock.yaml` move, such as a docs registry bump: it requires the producer version, normalizer, fixture and runner digests, `Cargo.lock` and toolchain to equal the contract, and only the lock hash may move. It is Linux-only and historical; schemaVersion 3 makes such moves a non-event. `scripts/rebaseline-island-size-darwin.mjs` takes eight reasons — `metric-migration`, `release-bump`, `runtime-identity`, `fingerprint-migration`, `fingerprint-helper`, `cargo-producer-lock`, `dependency-graph` and `fingerprint-policy` — and rejects `lockfile-provenance`. `release-bump` and `runtime-identity` refuse any `Cargo.lock` movement on either script and name `cargo-producer-lock` (see "Cargo producer-lock transitions" below). `fingerprint-helper` (#4198, schemaVersion 3, either script) re-pins only the helper's own byte digest after a comment, formatting or documentation edit to `lock-fingerprint.mjs`; it proves the pinned helper at `--base-ref` and the new helper compute the same fingerprint and inventory on the real lock, so no native run is needed; a helper edit that changes the fingerprint is refused and is a policy change (#4218). It rewrites no test pins, because none pins `helperSha256`. Equal totals do not establish byte-identical product code, and the rebaseline prose does not claim that they do.

## Dependency fingerprint (schemaVersion 3)

A schemaVersion 2 contract pins the whole-file `toolchain.pnpmLockSha256`, so a docs-only or root-tooling lock bump fails both native checks although no measured byte can move. A schemaVersion 3 contract keeps the schemaVersion 2 metric, normalizer, allowance and ceilings and adds, immediately after `normalizerSha256`:

```json
"dependencyFingerprint": { "policyVersion": 1, "parser": "yaml@2.9.0", "helperSha256": "<64 hex>", "sha256": "<64 hex>" }
```

`lock-fingerprint.mjs` computes it. It hashes the pnpm environment document in full, plus the project document's global resolution settings and the dependency closure of `packages/zfb`, `packages/zfb-runtime` and `packages/zfb-slugify` (with every importer they `link:`), and their build scripts and tsconfig files. Lockstep `workspace:<version>` specifiers are normalized, so a release bump leaves the fingerprint unchanged. [LOCK-FINGERPRINT-POLICY.md](LOCK-FINGERPRINT-POLICY.md) is the authoritative selection and canonical-form specification. `helperSha256` pins the helper's own bytes, and any policy change is a `policyVersion` bump. `check-budget.mjs` compares all four keys with the checkout's fingerprint. `toolchain.pnpmLockSha256` stays required, but only as baseline provenance; it is no longer compared with the checkout.

What stays byte-exact: run provenance still carries the whole-file `pnpmLockSha256`, which must equal the checked-out `pnpm-lock.yaml`, next to `dependencyFingerprint: { policyVersion, sha256 }`, which must equal the checkout's. `Cargo.lock`, the fixture, runner and normalizer digests, the package version and the toolchain are compared exactly as in schemaVersion 2. A schemaVersion 2 contract rejects a run that carries the fingerprint, and a schemaVersion 3 contract rejects a run that lacks it.

Print the checkout's fingerprint, and with `--explain` its inclusion inventory:

```sh
node research/v3-island-size/lock-fingerprint.mjs [--explain] [--lock <pnpm-lock.yaml>] [--version <packages/zfb version>]
```

Both helpers migrate a schemaVersion 2 contract with `--reason fingerprint-migration`. The artifact must come from the merged producers, which record the fingerprint, so its own `check-budget.mjs` run against the schemaVersion 2 contract fails with a schema mismatch. The helpers record that result as evidence; they do not require it to pass. Each helper requires the artifact to describe the checkout byte-for-byte: `pnpm-lock.yaml`, `Cargo.lock`, the package version, the fixture and runner digests, and the fingerprint. The package version, normalizer, fixtures, `Cargo.lock` and toolchain must equal the contract, and every raw and `gzipNormalized` total must be unchanged. Only the runner digests (the runners now record the fingerprint) and the recorded lock hash follow the artifact. Ceilings are never edited. Run each helper from the checkout the artifact measured:

```sh
node scripts/rebaseline-island-size-linux.mjs --artifact <island-size-linux-x64 artifact dir> \
  --run-id <run-id> --job-id <job-id> --head-sha <measured 40-hex SHA> --reason fingerprint-migration
node scripts/rebaseline-island-size-darwin.mjs --artifact <island-size-darwin-arm64 artifact dir> \
  --run-id <run-id> --job-id <job-id> --artifact-id <artifact-id> \
  --artifact-expires-at <ISO timestamp> --source-sha <measured 40-hex SHA> --reason fingerprint-migration
```

After the migration, `release-bump` and `runtime-identity` re-pin a schemaVersion 3 contract and refuse any fingerprint movement. A reachable dependency change is recorded with `--reason dependency-graph` instead: it moves only `dependencyFingerprint.sha256` (plus the recorded lock hash and its evidence) from fresh native evidence on both platforms, applied together (see "Dependency-graph re-pins and paired staging" below).

Each re-pin reason may move exactly these `dependencyFingerprint` keys ([LOCK-FINGERPRINT-POLICY.md](LOCK-FINGERPRINT-POLICY.md) item 0); every other key, total and identity input is refused, and no reason has a force or ignore-provenance flag:

| Reason | May move in `dependencyFingerprint` | Native evidence | Status |
| --- | --- | --- | --- |
| `fingerprint-helper` | `helperSha256` only | none (proves the old blob at `--base-ref` is the pinned value, and old and new helper give an identical `sha256` and `--explain` inventory on the real lock) | implemented ([#4213](https://github.com/Takazudo/zudo-front-builder/issues/4213)) |
| `dependency-graph` | `sha256` only | fresh, both platforms, totals unchanged | implemented ([#4218](https://github.com/Takazudo/zudo-front-builder/issues/4218)); live identity unchanged |
| `fingerprint-policy` | `policyVersion` + `parser` + `sha256` + `helperSha256`, only together with a `policyVersion` increment of exactly one that equals the checkout helper's exported `FINGERPRINT_POLICY_VERSION` | fresh, both platforms, totals unchanged | implemented ([#4218](https://github.com/Takazudo/zudo-front-builder/issues/4218)); live policy unchanged at 1 |
| `release-bump`, `runtime-identity`, `lockfile-provenance`, `fingerprint-migration`, `cargo-producer-lock`, `cargo-internal-rewire` | none (all four keys refused) | as today (`cargo-producer-lock` and `cargo-internal-rewire`: fresh, both platforms, totals unchanged) | unchanged |

`helperSha256` is appended to the helper's result after `sha256` is computed, and run provenance carries only `{policyVersion, sha256}`, so a comment, formatting or documentation edit to `lock-fingerprint.mjs` moves only `helperSha256` and fails `check-budget.mjs` with a remediation hint. Re-pin it from either script; one run rewrites both contracts, `lock-fingerprint-inventory.json` and this README together, so commit them as one change:

```sh
node scripts/rebaseline-island-size-linux.mjs --reason fingerprint-helper --base-ref <ref whose helper the contracts pin>
```

It takes no artifact argument and runs nothing natively. It refuses a contract that is not schemaVersion 3 (`fingerprint-migration` first), contracts that disagree on `helperSha256`, a `policyVersion` or `parser` the new helper does not report (`fingerprint-policy`), a fingerprint the new helper does not reproduce on the checkout (`dependency-graph` or `fingerprint-policy`), an unchanged helper, a `--base-ref` whose helper blob is not the pinned digest, and any disagreement between the old and new helper's `sha256` or `--explain` inventory (`importers`, `snapshots`, `packages`, `sections`, `counts`). A checkout fingerprint error is reported verbatim. It prints the proof: the base ref and its commit, the old and new `helperSha256`, the unchanged `sha256`, `policyVersion`, `parser`, the inventory counts, and "no native run: helperSha256 is outside the hashed input and absent from run provenance (#4198)". A `release-bump` refuses `helperSha256` movement, so a helper re-pin lands as its own commit before a release probe.

## Dependency-graph re-pins and paired staging (#4218)

A reachable change to the pnpm dependency graph — a moved snapshot, package or importer edge the fingerprint selects — moves `dependencyFingerprint.sha256` and fails `check-budget.mjs` on both platforms even when no measured byte moves. `--reason dependency-graph` (schemaVersion 3, either script) records that move as a reviewed capability; it changes no live contract by itself. It needs a fresh artifact on each platform, and refuses everything except the fingerprint value:

- The totals refusal comes first: any raw or `gzipNormalized` change, or a fixture-set difference, is refused, exactly as for every other reason.
- Exactly `sha256` must move between the contract and the checkout's fingerprint. A moved `policyVersion`, `parser` or `helperSha256` is refused (`fingerprint-helper` for a helper-only edit, `fingerprint-policy` for a policy change, #4218); an unchanged `sha256` is refused as a no-op.
- `Cargo.lock`, the package version, the normalizer, the fixture and runner digests, the toolchain (Hono, esbuild, Node, zlib), the metric, the normalization version and the allowance must equal the contract. A Hono bump moves `toolchain.honoVersion` and is refused here; it needs its own reviewed procedure.
- Only `dependencyFingerprint.sha256`, `toolchain.pnpmLockSha256`, `outcome`, `baselineSourceSha`, `platformStatus` and `baselineEvidence` may move; an exact-key diff of the old and new contract enforces it. `baselineEvidence` records the flat `repinnedFrom` predecessor and `fingerprintTransition: {policyVersion, oldSha256, newSha256}`.
- `lock-fingerprint-inventory.json` is regenerated from the checkout's own `lock-fingerprint.mjs --explain`, whose bytes must agree with the in-process proof of the re-pinned fingerprint.

**The artifact's identity must match its checkout.** Every artifact reason requires the artifact's provenance to describe the checkout byte for byte, the fingerprint included, so an artifact measured on another checkout never re-pins a fingerprint. Measure each platform at a checkout that already carries the new graph and run both scripts from that checkout: the artifact, the checkout and the new fingerprint agree, and the old contract is what moves.

**Measured source and probe head.** The Linux script requires `--source-sha`, the source the artifact measured, and refuses an artifact whose workspace or packed `provenance.sourceSha` differs. `--head-sha` stays the probe head: when `health.yml` measured a pull request, the artifact's source is the PR's synthetic merge commit and the head is the PR head with the identical tree, and the contract records both. Both scripts also require each mode's saved `measurement.normalized.json` to cite the SHA-256 of the saved `measurement.json` and of the current normalizer and to carry results equal to a fresh normalization of the saved bytes, so a stale or edited sidecar is refused before any write.

Before approving a pair whose Linux measured source differs from its probe head, the reviewer must verify both commits and compare their trees (`git rev-parse <measured-source>^{tree} <probe-head>^{tree}`). Require equal trees, or collect both platforms at the same exact source. The CLI records and compares the supplied source identities; it does not authenticate the GitHub probe-head relationship or prove this tree equality. Preserve that comparison with the native evidence; matching fingerprint and totals alone do not prove equivalent product sources.

**Paired staging.** Each platform's re-pin is staged into one directory and applied as one change; `dependency-graph` and `fingerprint-policy` refuse to run without `--stage`, so neither platform can write the live files alone:

```sh
node scripts/rebaseline-island-size-linux.mjs --artifact <linux artifact> --run-id <run-id> --job-id <job-id> \
  --head-sha <probe head> --source-sha <measured source> --reason dependency-graph --stage <dir>
node scripts/rebaseline-island-size-darwin.mjs --artifact <darwin artifact> --run-id <run-id> --job-id <job-id> \
  --artifact-id <artifact-id> --artifact-expires-at <ISO timestamp> --source-sha <measured source> \
  --reason dependency-graph --stage <dir>
# review <dir>, then from the same checkout:
node scripts/rebaseline-island-size-linux.mjs --apply <dir>
```

`--stage <dir>` writes the contract, the budget test, this README and the inventory (and, for `fingerprint-policy`, [LOCK-FINGERPRINT-POLICY.md](LOCK-FINGERPRINT-POLICY.md)) under `<dir>` (mirroring their repository paths) and never touches the checkout; it refuses a directory that is, contains or aliases the checkout or any live destination. The second stage reads the budget test, README, inventory and policy document already staged in `<dir>`, so both platforms' test pins and README sections survive, and the staged inventory and policy document must be identical. `<dir>/stage-manifest.json` records, per destination, the SHA-256 of the live file at staging time and of the staged output, plus each run's reason, platform, source SHA, run id and artifact id. `--apply <dir>` (either script, same code, no other argument) re-validates every live destination against its staged-time hash and every staged file against its staged hash, refuses a `dependency-graph` or `fingerprint-policy` stage that lacks either platform, and only then lands every destination: each is first written to a temporary sibling file, then renamed into place. A refusal on either platform therefore applies nothing. No file is written before every validation and every rendered output succeeds; `--apply` refuses if any destination moved since staging. A failure while writing the temporary files changes nothing; only the renames can leave a mix, and a failed rename restores the destinations already renamed from their original bytes (best effort; the error names any it could not restore). Commit the applied files as one change. There is no force or ignore-provenance flag.

## Fingerprint-policy re-pins (#4218)

A change to the fingerprint's selection, classification, normalization, canonical form or parser identity is a `policyVersion` bump ([LOCK-FINGERPRINT-POLICY.md](LOCK-FINGERPRINT-POLICY.md)). `policyVersion` is inside the hashed canonical input, so a bump always moves `sha256` and, through the helper's own bytes, `helperSha256`. `--reason fingerprint-policy` (schemaVersion 3, either script) records that move as a reviewed capability; it changes no live contract by itself, and the live policy stays at 1. It takes the same artifact arguments as `dependency-graph`, including `--source-sha`, and is staged and applied in pairs the same way.

**The +1 lockstep rule.** The four `dependencyFingerprint` keys move only together, and only when the checkout's `policyVersion` is exactly the contract's plus one **and** equals the checkout helper's exported `FINGERPRINT_POLICY_VERSION`. An unchanged `policyVersion` is refused (`fingerprint-helper` for a helper-only edit, `dependency-graph` for a reachable dependency change), a step of anything but +1 is refused, and a `parser` or `helperSha256` move without a version step is refused. A parser change also bumps the root `yaml` devDependency in lockstep, because the helper refuses an installed `yaml` that differs from its `parser` identity; that moves `pnpm-lock.yaml`, which this reason records in `toolchain.pnpmLockSha256`.

**What the artifact proves, and what the checkout helper proves.** Run provenance carries only `{policyVersion, sha256}`; both must equal the checkout's. `parser` and `helperSha256` are proven against the checkout's own `lock-fingerprint.mjs` (its exported `FINGERPRINT_PARSER` and `fingerprintHelperSha256()`), not against the artifact, which does not attest them. Both scripts load that helper from the selected checkout root, so every fingerprint, exported identity and `--explain` inventory is the checkout's; in the repository itself that is the same file.

Every `dependency-graph` refusal applies unchanged: the totals and fixture set, `Cargo.lock`, the package version, the normalizer, the fixture and runner digests, the toolchain, the metric, the normalization version, the allowance, the platform, an artifact whose fingerprint is not the checkout's, `--source-sha`, and a stale or edited sidecar. Only `dependencyFingerprint.policyVersion`, `.parser`, `.sha256`, `.helperSha256`, `toolchain.pnpmLockSha256`, `outcome` (`fingerprint-policy`), `baselineSourceSha`, `platformStatus` and `baselineEvidence` may move; an exact-key diff enforces it. `baselineEvidence` records the flat `repinnedFrom` predecessor and `fingerprintPolicyTransition: {from, to}` (the old and new four-key fingerprint). Besides the contract, the budget test pins and a README section, a run regenerates `lock-fingerprint-inventory.json` from the checkout helper's `--explain` (byte-preserved) and rewrites the policy identity line of [LOCK-FINGERPRINT-POLICY.md](LOCK-FINGERPRINT-POLICY.md) to the new `policyVersion` and `parser`; a document without exactly one such line is refused before any write.

```sh
node scripts/rebaseline-island-size-linux.mjs --artifact <linux artifact> --run-id <run-id> --job-id <job-id> \
  --head-sha <probe head> --source-sha <measured source> --reason fingerprint-policy --stage <dir>
node scripts/rebaseline-island-size-darwin.mjs --artifact <darwin artifact> --run-id <run-id> --job-id <job-id> \
  --artifact-id <artifact-id> --artifact-expires-at <ISO timestamp> --source-sha <measured source> \
  --reason fingerprint-policy --stage <dir>
# review <dir>, then from the same checkout:
node scripts/rebaseline-island-size-linux.mjs --apply <dir>
```

### Future real activation

The fixture tests that accompany #4218 run `dependency-graph` against a synthetic prior graph and `fingerprint-policy` against a synthetic policy-2 copy of the helper, each in a disposable checkout; they are not a claim that a real policy transition occurred, and choice 9b (excluding the packages' test-only dependencies) remains deferred. A real `dependency-graph` or `fingerprint-policy` activation requires fresh enforced artifacts for the actual changed source on **both** platforms (Linux x64 from the `health` job's island-size step, Darwin arm64 from `island-size-darwin.yml`), both the workspace and packed matrices, every raw and `gzipNormalized` total unchanged, and an unchanged-input audit (package version, `Cargo.lock`, fixtures, runners, normalizer and toolchain equal the contracts).

The initial enforced collection may legitimately **fail** against the old fingerprint pin. Preserve that original run and its log; prove that only the permitted identity delta caused it (every other `check-budget.mjs` line clean, totals equal); independently replay the saved bytes through the CLIs; `--stage` both platforms into one directory; review it; `--apply` the paired re-pin in one commit; then obtain a final enforced success. Never relabel the original rejection as a pass, never hand-edit a bypass, and never demand a green run of the old contract before the re-pin. [LOCK-FINGERPRINT-POLICY.md](LOCK-FINGERPRINT-POLICY.md) item 11 records the same protocol.

## Cargo producer-lock transitions (#4214)

The default path remains additive-only. PR #4120 additionally authorizes one [exact non-additive #318 transition](cargo-transitions/README.md) through optional `--reviewed-cargo-transition`: its full old/new lock pair, record inventory, 14 shared replacements, nine incidental Windows edges, and producer feature review are explicit. This is structural policy authorization only. The ordinary budget checker, live platform pins, zero allowances, numerical ceilings, native platform evidence, saved-byte checks, and all other rebaseline gates remain unchanged. Current measurements remain rejected until qualifying evidence separately re-pins each platform. Held #4234 is not activated.

`Cargo.lock` is outside the pnpm fingerprint, and both contracts pin its whole-file hash in `toolchain.cargoLockSha256`. Earlier Rust-only lock moves were recorded by hand-editing that hash ([#4159](https://github.com/Takazudo/zudo-front-builder/issues/4159), [#4173](https://github.com/Takazudo/zudo-front-builder/issues/4173)), which left `platformStatus` and `baselineEvidence` describing runs measured at the previous lockfile. `--reason cargo-producer-lock` replaces that with a reviewed, evidence-bound transition for an **additive** producer-lock change, such as a new crate that the measured `zfb` binary does not link. It needs a schemaVersion 3 contract and a fresh artifact measured at the new lock on each platform, and it is not a force or ignore-provenance flag: it binds the exact old and new hashes and the exact added records.

```sh
node scripts/rebaseline-island-size-linux.mjs --artifact <island-size-linux-x64 artifact dir> \
  --run-id <run-id> --job-id <job-id> --head-sha <measured 40-hex SHA> --reason cargo-producer-lock \
  --expected-old-cargo-sha <pinned sha256> --expected-new-cargo-sha <checkout sha256> \
  --old-cargo-ref <commit whose Cargo.lock the contracts pin>[:<path>] --added-packages <name@version,...>
```

The Darwin script takes the same Cargo arguments next to its usual artifact arguments. The old lock is read from git, never from a file path: `--old-cargo-ref <ref>[:<path>]` (the path defaults to `Cargo.lock`, must be repository-relative and may not contain `..`) is resolved exactly once with `git rev-parse --verify` in the checkout being rewritten, with no fallback ref; an ambiguous branch/tag name or short SHA, or a ref that is not a commit, is refused. The object must be a blob, read with `git show <commit>:<path>`, and its raw bytes must hash to `--expected-old-cargo-sha`. `--old-cargo-lock <file>` is optional corroboration: when given, its bytes must equal that blob. A commit that resolves locally is not proof that anyone else can fetch it, so cite a commit reachable from `main`. Each refuses unless: the contract pins `--expected-old-cargo-sha` and the old blob hashes to it; the artifact's and the checkout's `Cargo.lock` both hash to `--expected-new-cargo-sha`, which differs from the old one; every `[[package]]` record of the old lock appears byte-identical in the new one, the header and any other section are unchanged, and the file splits losslessly into those parts; the added records are exactly the `--added-packages` allowlist by `name@version`, with no changed or removed record and no duplicate package identity; every raw and `gzipNormalized` total and the fixture set are unchanged; and the package version, normalizer, fixture and runner digests, `pnpm-lock.yaml` hash, dependency fingerprint and toolchain equal the contract. It writes only `toolchain.cargoLockSha256`, `outcome` (`cargo-producer-lock-transition`), `baselineSourceSha`, `platformStatus` and `baselineEvidence`, which records `cargoTransition: { oldSha, newSha, added, changed: [], removed: [], oldLockSource: { commit, path, sha256 } }` (the full 40-hex commit the blob was read from, its path and the blob's SHA-256) next to `repinnedFrom`; an exact-key diff refuses anything else. A lockfile proof does not prove unchanged producer features, so the review also diffs `cargo tree -e features` for the measured producers. `release-bump` and `runtime-identity` refuse any `Cargo.lock` movement and name this reason; a changed or removed record needs a reviewed decision instead.

Every artifact re-pin except the two migrations (`metric-migration` and `fingerprint-migration`, which record `migratedFrom` where they record a predecessor at all) records its immediate predecessor in the same flat shape on both platforms: `baselineEvidence.repinnedFrom: { schemaVersion, outcome, packageVersion, baselineSourceSha, baselineRunId, contract }`, read from the previous contract's top-level fields, never nesting its evidence. `contract` is `{ sha256 }` of the previous contract's exact bytes, plus `commit` and `path` when `git show <HEAD>:<path>` in the checkout is byte-identical to them (an explicit `--previous-contract-ref <ref>` must match instead, or the re-pin is refused). An edited or uncommitted contract records the digest only, with a notice. `baselineSourceSha` is the measured source commit; `contract.commit` is the commit that stores the previous contract file, so the two usually differ. No file is written before every validation and every rendered output succeeds.

## Cargo internal-rewire transitions (#4258)

Declaration schema 1 below retains the internal-only edge rule. The separately
bounded [schema-2 existing external edge capability](EXISTING-EXTERNAL-EDGES.md)
requires explicit edge/record evidence and unchanged external inventory and
default-producer closures. Capability implementation does not activate a transition
or change these approved contracts.

`cargo-producer-lock` admits **additions only**: every old `[[package]]` record must survive byte-identical. Extracting shared code into a new unpublished workspace crate ([#4242](https://github.com/Takazudo/zudo-front-builder/pull/4242): `zfb-js-host` takes over `zfb-render`'s direct `sha1`/`sha2` edges) also rewrites the existing `zfb-render` record, which that reason correctly refuses, and `dependency-graph` concerns the pnpm fingerprint and refuses any `Cargo.lock` movement. `--reason cargo-internal-rewire` (schemaVersion 3, either script) is the separate, bounded capability for exactly that shape; it changes no live contract by itself. It is paired and source-bound like `dependency-graph` (`--source-sha`, `--stage`, then `--apply` once both platforms are staged) and moves only `toolchain.cargoLockSha256`, `outcome`, `baselineSourceSha`, `platformStatus` and `baselineEvidence` (which records `cargoRewire`), enforced by the exact-key diff.

The transition is declared up front in a reviewed JSON file and every claim in it is checked against the actual bytes; the declaration is proposed evidence, never approval by itself:

```json
{
  "schemaVersion": 1,
  "producer": "zfb",
  "oldCargoLockSha256": "<pinned Cargo.lock sha256>",
  "newCargoLockSha256": "<checkout Cargo.lock sha256>",
  "added": [{ "id": "zfb-js-host@0.0.0", "manifest": "crates/zfb-js-host/Cargo.toml", "sha256": "<record bytes>", "dependencies": ["base64", "getrandom 0.3.4", "..."] }],
  "changed": [{ "id": "zfb-render@0.0.0", "manifest": "crates/zfb-render/Cargo.toml", "oldSha256": "<old record bytes>", "newSha256": "<new record bytes>", "removedDependencies": ["sha1", "sha2"], "addedDependencies": ["zfb-js-host"] }],
  "closure": { "added": ["zfb-js-host@0.0.0"], "changed": [] }
}
```

What the proof requires (`proveCargoInternalRewire`, shared by both scripts):

- **Whole-lockfile accounting.** The old lock is the git blob at `--old-cargo-ref <ref>[:<path>]` (resolved once, `oldLockSource: {commit, path, sha256}`), hashed as raw bytes to `--expected-old-cargo-sha`, which the contract must pin; the new lock is the checkout's, hashed to `--expected-new-cargo-sha`, which the artifact must have measured and which an optional `--new-cargo-ref` must store byte-identically (otherwise HEAD is cited when it matches, else the digest alone). The declaration binds both hashes. The header and every non-package section must be equal; every old record is paired by `name@version` and must be byte-identical unless declared `changed`; every new record must exist in the old lock unless declared `added`; a removed record, a duplicate identity, an undeclared change or addition is refused.
- **Exact record deltas.** Each `added` entry's `sha256` must equal the exact record bytes and its `dependencies` the record's list; each `changed` entry's `oldSha256`/`newSha256` must equal the old and new record bytes, every line other than the `dependencies` block must be identical, and the removed/added edge sets must equal `removedDependencies`/`addedDependencies` exactly. A changed-record `version` move changes the identity and is refused as a removal plus an addition.
- **Internal, from the manifests.** A declared record may carry no `source` and no `checksum`, and its `manifest` in the checkout must be a `[workspace] members` path (not `exclude`d) whose `[package]` has the record's `name` and `version` and an explicit `publish = false` (`version.workspace = true`, `publish.workspace = true` and registry lists are refused; no crate uses them today). A name prefix proves nothing. The exact manifest bytes are recorded as `manifestSha256`, and whenever the new lock cites a commit (explicit `--new-cargo-ref` or automatically discovered HEAD), every manifest must be byte-identical to that commit's blob (`manifestsAtCommit`), so an uncommitted manifest edit cannot admit a record. **Precondition for #4242:** `crates/zfb-render/Cargo.toml` carries no `publish` line on `main`; the rewired record is admissible only once that manifest sets `publish = false` (a manifest-only change that leaves `Cargo.lock` untouched). Every added dependency edge of a changed record must resolve unambiguously (`name`, `name version` or `name version (source)`) to a declared internal record; every edge of an added record must resolve unambiguously in the new lock.
- **Producer closures, not only lock equality.** `--old-closure` and `--new-closure` are receipts written by `scripts/record-cargo-producer-closure.mjs` (`cargo metadata --locked --filter-platform <target>`, normal and build edges from the producer, with the features Cargo enabled per package) at the old and new lock for this platform's target (`x86_64-unknown-linux-gnu` for the Linux script, `aarch64-apple-darwin` for the Darwin script; `cargo metadata` resolves either target from one Linux checkout). Each receipt must name the producer (`zfb`, the measured CLI package; no other producer is accepted), the platform target, `normal,build` edges and the lock SHA-256 it was recorded at; every row must be a record of that lock and carry that record's source (a path source for workspace records, the registry or git source otherwise). The enabled features are **operator-attested**: the tool never runs Cargo, so the receipts are reviewed evidence it cannot reproduce, and their `cargo metadata` resolution is workspace-wide (resolver 2 unifies features across members), which can differ from a lone `cargo build -p zfb`. Between them, no row may leave, no external row may join, no external row's features may move, and the rows that join or move must be exactly the declaration's `closure.added` / `closure.changed` internal ids.
- **Everything else unchanged.** Totals and fixture set (any raw or `gzipNormalized` movement, including a decrease, is refused), ceilings, allowance, metric, normalizer, fixtures, runners, toolchain, `pnpm-lock.yaml` and its dependency fingerprint, the package version, the platform, `--source-sha`, and the saved sidecars, exactly as for the other paired reasons. Only the Cargo hash moves.
- **One coherent pair.** Each staged run records, beyond the shared transition identity, `rewire: {declarationSha256, oldLockSha256, newLockSha256}`; staging the second platform and `--apply` refuse when the two runs disagree on any of them, on the transition, on the measured source, or on the reason. Platform-specific predecessor contract digests legitimately differ. A partial stage, a tampered staged file and a live destination that moved are refused as for every staged reason; `--apply` writes temporary siblings first and restores already-renamed destinations on a failed rename, without claiming multi-file crash atomicity.

The manifest reader is deliberately bounded: it strips comments outside quoted strings and refuses multiline or unterminated TOML strings anywhere in the manifest. Text inside a description or a comment cannot establish `publish = false` or workspace membership. A valid manifest using unsupported syntax is refused; extend the reader with reviewed parser coverage before using that form as admission evidence.

```sh
node scripts/record-cargo-producer-closure.mjs --producer zfb --target x86_64-unknown-linux-gnu --output <old-linux.json>   # at the pinned lock
node scripts/record-cargo-producer-closure.mjs --producer zfb --target aarch64-apple-darwin --output <old-darwin.json>     # at the pinned lock
node scripts/record-cargo-producer-closure.mjs --producer zfb --target x86_64-unknown-linux-gnu --output <new-linux.json>   # at the new lock
node scripts/record-cargo-producer-closure.mjs --producer zfb --target aarch64-apple-darwin --output <new-darwin.json>     # at the new lock
node scripts/rebaseline-island-size-linux.mjs --artifact <linux artifact> --run-id <run-id> --job-id <job-id> \
  --head-sha <probe head> --source-sha <measured source> --reason cargo-internal-rewire \
  --expected-old-cargo-sha <pinned sha256> --expected-new-cargo-sha <checkout sha256> \
  --old-cargo-ref <commit whose Cargo.lock the contracts pin>[:<path>] [--new-cargo-ref <commit storing the new lock>] \
  --rewire-declaration <declaration.json> --old-closure <old-linux.json> --new-closure <new-linux.json> --stage <dir>
node scripts/rebaseline-island-size-darwin.mjs --artifact <darwin artifact> --run-id <run-id> --job-id <job-id> \
  --artifact-id <artifact-id> --artifact-expires-at <ISO timestamp> --source-sha <measured source> \
  --reason cargo-internal-rewire --expected-old-cargo-sha <pinned sha256> --expected-new-cargo-sha <checkout sha256> \
  --old-cargo-ref <commit>[:<path>] --rewire-declaration <declaration.json> \
  --old-closure <old-darwin.json> --new-closure <new-darwin.json> --stage <dir>
# review <dir>, then from the same checkout:
node scripts/rebaseline-island-size-linux.mjs --apply <dir>
```

The accompanying tests run the reason against synthetic five-record locks in disposable git-backed checkouts (`scripts/__tests__/fixtures/cargo-internal-rewire/`); they are fixtures, not native evidence, and no live contract moved. A real activation needs fresh enforced artifacts for the actual rewired source on **both** platforms, the reviewed declaration committed with that source, the four closure receipts, the paired `--stage`/`--apply` above and a final enforced success, under the same protocol as the fingerprint reasons; the initial enforced collection may legitimately fail against the old Cargo pin and is preserved, not relabelled.
