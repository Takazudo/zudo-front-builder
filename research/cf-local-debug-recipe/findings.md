# findings.md — CF Local Debug Recipe (Wave 1 / issue #538)

**Date:** 2026-05-27  
**Machine:** WSL2, Node 24.13.1, wrangler 4.72.0, zfb 0.0.0 (main)  
**Test project:** `zfb-example-webshop` (sibling at `$HOME/repos/zfb-ex/zfb-example-webshop`)  
**Smoke-test page for markers:** `pages/index.tsx` (publicly accessible, D1-backed)  
**Marker technique:** visible text injected into the h1 heading; confirmed with `curl | grep`

---

## What worked

The simplest working recipe is two concurrent processes managed by `concurrently`:

```
npx concurrently@9 \
  --names "wrangler,watch" \
  --kill-others \
  "wrangler pages dev dist/ --port 8788" \
  "npx chokidar-cli@3 'pages/**/*.tsx' 'components/**/*.tsx' 'layouts/**/*.tsx' 'lib/**/*.ts' 'styles/**/*.css' --command 'pnpm build' --initial false --debounce 200"
```

Preceded by:

1. An initial `pnpm build` to ensure `dist/` is populated before wrangler starts.
2. `wrangler d1 migrations apply <DB_NAME> --local` (idempotent; safe to re-run).

`recipe-v1.sh` in this directory wraps both steps with preflight checks for port collision and missing `wrangler.toml`.

## Edit-to-browser latency

Measured via `date +%s.%N` at file-save and at first successful `curl | grep` hit.

| Phase | Duration |
|---|---|
| chokidar debounce | ~0.2s (configured) |
| `pnpm build` (zfb build + stable-css.mjs) | ~0.6-0.9s |
| wrangler reload after dist/ change | ~0.3s |
| **Total: edit-save to curl success** | **~1.2-1.5s** |

Five consecutive edits were measured; all fell in the 1.18-1.45s range. No outliers observed.

Cold build (dist deleted, node_modules intact) is identical to warm build at ~0.9s. `zfb build` does not maintain a file-based cache between runs for this project — each invocation re-bundles from source — so warm/cold distinction is irrelevant here.

## D1 binding behavior

D1 local state lives in `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/` as SQLite files. `zfb build` only writes to `dist/`; it does not touch `.wrangler/`. After 10+ rebuild cycles the SQLite mtime was unchanged and all product rows remained readable via `env.DB`.

A wrangler worker-reload tick (triggered by `_zfb_inner.mjs` content change) does not restart the miniflare process — it only reloads the worker module. The D1 connection is maintained across reloads. Confirmed: product queries returned correct rows immediately after each reload, with no reconnect delay.

**Caution:** if the user runs `rm -rf dist` while wrangler is running (as done accidentally during this prototype session), wrangler may enter a degraded state where subsequent rebuilds do not trigger reloads. Recipe mitigation: do NOT wipe `dist/` while wrangler is running. The recipe script runs the initial build before starting wrangler, so this should not be an issue in normal use.

## Reload semantics

**Does wrangler pages dev notice rebuilt `_worker.js` without manual restart?**

Yes, with a nuance: `_worker.js` is a static thin wrapper generated by `@takazudo/zfb-adapter-cloudflare`. Its content is byte-for-byte identical across builds (same inode, same md5). Wrangler's file watcher observes the full `dist/` directory. The dynamic content is in `_zfb_inner.mjs`, which changes on every build. Wrangler detects the `_zfb_inner.mjs` content change and reloads automatically within ~300ms:

```
Compiled Worker successfully
Reloading local server...
Local server updated and ready
```

**Do two consecutive edits both refresh?**

Yes. Five consecutive edits were tested in the same recipe session. Each edit produced a unique marker string; each marker appeared correctly in the next curl response within ~1.5s. No stale-module cache issue was observed. The chokidar debounce of 200ms prevents spurious double-builds from editor temp files.

**Caution observed (first session):** When `dist/` was wiped (`rm -rf dist`) while wrangler was running, subsequent rebuilds appeared to miss reload events. In the recipe, dist is never wiped during the loop — the build script overwrites in place — so this edge case does not arise in normal use.

## Friction points

1. **`_worker.js` is a static wrapper whose content never changes across builds.** Wrangler correctly detects `_zfb_inner.mjs` changes anyway (it watches the full dist/ tree, not just the entry file by content-hash). If wrangler ever narrows its watch to entry-point-only, reloads would silently stop. Currently not a problem.
2. **`wrangler.toml compatibility_date` warning:** wrangler 4.72.0 warns that `2026-05-01` falls outside its known range. Cosmetic only; resolved by upgrading to wrangler 4.95.0.
3. **chokidar-cli and concurrently fetched on first use:** `npx --yes` adds ~2s on first run. Adding them as `devDependencies` eliminates this.
4. **`rm -rf dist` with running wrangler:** if a developer runs the `predev` script while wrangler is active, wrangler may desync. The recipe avoids this by using `pnpm build` (not `predev`) and starting wrangler after the initial build.
5. **No single-command `package.json` script today:** the recipe requires invoking `recipe-v1.sh` or the concurrently invocation directly. Adding a `dev:cf` script resolves this.

---

## `zfb build --watch` verdict

**Userland is sufficient.**

`zfb build` completes in under 1 second for this project. The chokidar-cli + concurrently approach adds a 200ms debounce and then invokes `pnpm build`; the entire edit-to-curl round trip is ~1.2-1.5s — well within the 10-second acceptance criterion. Wrangler's built-in file watcher handles the hot-reload half automatically when `_zfb_inner.mjs` changes content.

A `zfb build --watch` flag would offer UX improvements: (a) consolidate the loop into a single process without the chokidar-cli/concurrently dependency, and (b) potentially skip the CSS post-build step (`stable-css.mjs`) when only non-CSS files change. However, neither limitation blocks the developer workflow. The complexity of adding file-watching to the zfb CLI is not justified by the current friction level. Recommend the Wave 4 webshop integration adopt the userland recipe; revisit `--watch` only if consumers report that 1-2s latency or the two-devDep requirement is a real barrier.

## Recipe shape

### Proposed `package.json` script entries

```json
{
  "scripts": {
    "dev:cf:setup": "wrangler d1 migrations apply webshop --local && pnpm build",
    "dev:cf": "pnpm dev:cf:setup && concurrently --names 'wrangler,watch' --kill-others \"wrangler pages dev dist/ --port 8788\" \"chokidar 'pages/**/*.tsx' 'components/**/*.tsx' 'layouts/**/*.tsx' 'lib/**/*.ts' 'styles/**/*.css' --command 'pnpm build' --initial false --debounce 200\""
  }
}
```

### Extra devDependencies required in consumer apps

| Package | Version | Purpose |
|---|---|---|
| `concurrently` | `^9.0.0` | Run wrangler + chokidar in one terminal; kill-others on Ctrl-C |
| `chokidar-cli` | `^3.0.0` | Watch source files and trigger `pnpm build` on change |

`wrangler` is already a devDependency in Cloudflare Pages projects.

### Single terminal or multi-pane?

**Single terminal.** With `concurrently`, both the watcher and wrangler output appear interleaved (prefixed `[wrangler]` / `[watch]`). No multi-pane setup is needed. Ctrl-C cleanly kills both processes.

### Complete recipe summary (what Wave 4 should adopt)

```bash
# One-time setup (idempotent, safe to re-run)
wrangler d1 migrations apply webshop --local
pnpm build

# Ongoing dev loop (single command after adding dev:cf script)
pnpm dev:cf
```

Which expands to running concurrently:

- `wrangler pages dev dist/ --port 8788`
- `chokidar 'pages/**/*.tsx' ... --command 'pnpm build' --debounce 200`
