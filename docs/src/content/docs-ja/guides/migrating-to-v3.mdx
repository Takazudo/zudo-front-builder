## はじめる前に

このガイドは、Tailwind CSS、Preact または React のコンポーネント、島、MDX、旧設定を使うプロジェクト向けです。v3 では旧エンジンとの連携が削除されます。互換モードや自動変換はありません。まず動作する 2.x の状態をコミットしてください。設定をプリセットパッケージから受け取る場合は、アプリより先にプリセットを更新します。プリセットに削除済みのキーが残ると、アプリ側で削除しても設定の読み込みが失敗します。

以下の確認には、v3 の `zfb` バイナリと対応する `@takazudo/zfb` パッケージを使ってください。2.x のドキュメントホストに入ったバイナリや型は、依然として 2.x の動作を表します。

## 設定

`framework: "preact"` や `framework: "react"` を含め、`framework` を削除します。残っていると次の設定エラーになります。

```text
the framework key was removed in zfb 3; delete the key. zfb now uses zudo-react.
```

`tailwind` を `wind` に置き換えます。生成ユーティリティを使わず、手書き CSS と CSS Modules だけを使う場合は、`tailwind: { enabled: false }` の代わりに `wind: false` を指定します。旧キーが残ると次のエラーになります。

```text
the tailwind key was removed in zfb 3; utilities are compiled by the built-in zudo-wind engine. Replace tailwind: { enabled: false } with wind: false, or delete the key. See the v3 migration guide
```

`wind` を省略すると、リセットが `none` でトークンのない空の v1 設定として生成が有効になります。旧テーマは復元されません。`wind` の内部オブジェクトは未知のフィールドを拒否します。各フィールドとマージ規則は [wind の設定](../zudo-wind/configuration.mdx)を参照してください。

## スタイルシート

エントリーとそのインポート先から、`@import "tailwindcss"`、preflight と utilities のインポート、および `@theme`、`@source`、`@apply`、`@utility`、`@plugin` などの Tailwind ディレクティブを削除します。`wind: false` でも、残ったディレクティブは診断 `ZW009` で失敗します。独自のセレクターと宣言は手書き CSS に、ユーティリティの値は `wind.tokens` に移します。

v3 はパレット、間隔の単位、名前付きスケール、ブレークポイントを暗黙には提供しません。`wind.reset` に `none`、`minimal-v1`、`owned-v1` から選んでください。既定は `none` です。新しい basic-blog の雛形は `owned-v1` を選び、パレットと `spacingUnit` を宣言し、記事のリスト表示を手書き CSS で戻しています。リセットを選ぶ際は見出し、リスト、境界線、フォームを目視確認してください。

```ts
import { defineConfig } from "zfb/config";

export default defineConfig({
  wind: {
    spec: 1,
    reset: "owned-v1",
    tokens: {
      spacingUnit: "0.25rem",
      colors: { accent: "var(--color-accent)" },
    },
    breakpoints: { sm: { minWidthPx: 640 } },
    dark: { attribute: "data-theme", value: "dark" },
  },
});
```

スタイルシートに `--color-accent` を宣言し、使うユーティリティに必要なトークンを追加します。未知の通常クラスは手書きクラスの文字列として残ります。一方、認識された無効なユーティリティや必須トークンの欠落は、厳密な入力元では診断されます。ユーティリティ言語とリセットは Tailwind と異なります。ディレクティブ、バリアント、トークン、未対応の構文は [Tailwind からの移行表](../zudo-wind/coming-from-tailwind.mdx)を参照してください。

## コンポーネントと島

`tsconfig.json` で `compilerOptions.jsx` を `react-jsx`、`compilerOptions.jsxImportSource` を `@takazudo/zfb/zudo-react` にします。使用中の `@takazudo/zfb` と `@takazudo/zfb-runtime` は残します。旧 zfb エンジンのためだけに追加していた `preact`、`react`、`react-dom`、`@types/react`、`@types/react-dom` は削除します。ランタイムは独立パッケージではなく、`@takazudo/zfb/zudo-react` から提供されます。

```json
{
  "compilerOptions": {
    "jsx": "react-jsx",
    "jsxImportSource": "@takazudo/zfb/zudo-react"
  }
}
```

hook を使うコンポーネントは、セットアップ時に一度実行される zudo-react コンポーネントへ書き換えます。書き込み可能な状態とフォームのモデルには `signal()`、読み取り専用の派生値には `computed()`、ライフサイクルには `getScope()` と `scope.effect()`、条件付き領域とキー付き領域には `Show` と `For` を使います。読み取り専用または computed の signal は書き込み可能なモデルにできません。JSX では `class`、`for`、`style={{ "background-color": "red" }}` のような HTML/CSS の表記と、ネイティブの `on:click` リスナーを使います。React 式の props とブランドのない要素オブジェクトは、zudo-react の JSX または `h()` に置き換えます。`rawHtml` は信頼できる HTML に限り、children と併用できません。変換例は [Preact hooks からの移行表](../zudo-react/coming-from-preact-hooks.mdx)を参照してください。

`<Island>` は引き続きコンポーネントを包むビルド時の要素です。ただし受け渡しは厳密になります。子コンポーネントは 1 つ、props は JSON、識別情報はソーススキャナーと一致する必要があります。手書きのラッパーにも完全で有効なメタデータが必要です。ハイドレーションは一致するサーバーのマークアップを採用し、不一致の島は個別に失敗します。SSR を省略するルートは `data-when` で起動を調整し、クライアントで正常にマウントした後にフォールバックを置き換えます。フォームは明示的な書き込み可能モデルを使い、select は単一選択のみで、ハイドレーション時は DOM の値が優先されるため、動作を確認してください。[島のガイド](../concepts/islands.mdx)も参照してください。

## MDX と md-wasm

`@takazudo/zfb-md-wasm` の `compile()` と `renderHtml()` のオプションは `jsxRuntime` を受け付けなくなりました。`react` や `preact` を選ぶ代わりに、このフィールドを削除してください。型付き API は拒否し、JSON の検証では `jsxRuntime` を示す未知フィールドのエラーになります。コンパイル済み MDX は Fragment を `@takazudo/zfb/zudo-react/jsx-runtime` からインポートします。出力をバンドルする側でこのサブパスを解決し、旧エンジンへエイリアスしないようにします。

## CLI と環境変数

スクリプトと CI から `ZFB_TAILWIND_BIN` と `ZFB_TAILWIND_OXIDE_WARMUP` を削除します。Tailwind の同梱バイナリとピンは削除されました。`zfb css` は単独の CSS コマンドとして残り、zudo-wind でコンパイルします。明示的な `--source` 入力も引き続き使えます。`zfb wind explain <candidate>` は一つの候補を説明し、`zfb wind audit` はプロジェクト内の候補を調べます。build と dev は `.tsx`、`.ts`、`.jsx`、`.js`、`.mdx`、`.md` をスキャンし、単独コマンドの明示的なソースには `.html` と `.mjs` も指定できます。

`zfb --version` はリリースバージョンと `embedded esbuild` のバージョンを表示し、Tailwind の行は表示しません。移行中のエラーの調査には [wind の診断ガイド](../zudo-wind/diagnostics-and-tools.mdx)を使ってください。

## クラスやコンポーネントを配布するパッケージ

以前、配布した safelist に依存していたパッケージは、完全な候補をバージョン付き JSON マニフェストとして配布してください。利用側は producer のキーを付けてファイルを宣言します。異なる producer はプリセットとアプリのマージ後も保持されます。すべてのエントリーが厳密に検証され、利用側で必要なトークンを設定する必要があります。マニフェストはトークンを定義できず、自動発見もされません。

```json
{
  "schemaVersion": 1,
  "specVersion": 1,
  "producer": "widgets",
  "candidates": ["group", "p-0", "hover:bg-accent"]
}
```

```ts
wind: {
  manifests: { widgets: { path: "./node_modules/widgets/wind.json" } },
  tokens: { colors: { accent: "#2563eb" } },
}
```

配布するコンポーネントは `@takazudo/zfb/zudo-react` からインポートし、同じ JSX import source を使ってください。zfb 利用者向けに Preact や React の JSX runtime import を配布しないでください。マニフェストの検証と探索ルートは [ソースと候補](../zudo-wind/sources-and-candidates.mdx)を参照してください。

## チェックリスト

1. 設定プリセットを先に更新し、対応する v3 パッケージとバイナリを導入します。`zfb --version` と `package.json` を確認します。
2. `framework` を削除し、`tailwind` を `wind` または `wind: false` に置き換えます。`zfb check` で削除済みキーと無効な内部データを確認します。
3. Tailwind のインポートとディレクティブを削除し、トークンとリセットを設定します。プロジェクトの入出力パスを指定して `zfb css --input <entry.css> --output <output.css>` を実行します。
4. JSX import source、依存関係、コンポーネント、島、フォームモデルを変更します。`zfb check` を実行し、型エラーを修正します。
5. md-wasm 呼び出しから `jsxRuntime` を削除し、コンパイル済み出力の利用側を更新します。パッケージの TypeScript チェックを実行します。
6. 動的に組み立てる有限のクラスを完全なリテラルかマニフェストに置き換えます。CI または pre-push のチェックとして `zfb wind audit --fail-on error` を使い、代表的なクラスに対して `zfb wind explain <candidate>` を実行します。
7. ビルドスクリプトから Tailwind の環境変数を削除します。`zfb build` を実行し、主要ページ、島、フォーム、スタイルをブラウザーで比較します。
