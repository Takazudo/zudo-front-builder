## はじめる前に

このガイドは、Tailwind CSS、Preact または React のコンポーネント、島、MDX、旧設定を使うプロジェクト向けです。v3 では旧エンジンとの連携が削除されます。互換モードや自動変換はありません。まず動作する 2.x の状態をコミットしてください。設定をプリセットパッケージから受け取る場合は、アプリより先にプリセットを更新します。プリセットに削除済みのキーが残ると、アプリ側で削除しても設定の読み込みが失敗します。

以下の確認には、v3 の `zfb` バイナリと対応する `@takazudo/zfb` パッケージを使ってください。2.x のドキュメントホストに入ったバイナリや型は、依然として 2.x の動作を表します。

## 設定

`framework: "preact"` や `framework: "react"` を含め、`framework` を削除します。残っていると次の設定エラーになります。

```text
the framework key was removed in zfb 3; delete the key. zfb now uses zudo-react.
```

`tailwind` を `wind` に置き換えます。生成ユーティリティを使わず、手書き CSS と CSS Modules だけを使う場合は、`tailwind: { enabled: false }` の代わりに `wind: false` を指定します。旧キーが残ると次のエラーになります。

```text
the tailwind key was removed in zfb 3; utilities are compiled by the built-in zudo-wind engine. Replace tailwind: { enabled: false } with wind: false, or delete the key. See the v3 migration guide
```

`wind` を省略すると、リセットが `none` でトークンのない空の v1 設定として生成が有効になります。旧テーマは復元されません。`wind` の内部オブジェクトは未知のフィールドを拒否します。各フィールドとマージ規則は [wind の設定](../zudo-wind/configuration.mdx)を参照してください。

## スタイルシート

エントリーとそのインポート先から、`@import "tailwindcss"`、preflight と utilities のインポート、および `@theme`、`@source`、`@apply`、`@utility`、`@plugin` などの Tailwind ディレクティブを削除します。`wind: false` でも、残ったディレクティブは診断 `ZW009` で失敗します。1 回の実行で、残ったディレクティブをすべて `file:line:column` 付きで列挙します。独自のセレクターと宣言は手書き CSS に、ユーティリティの値は `wind.tokens` に移します。

v3 はパレット、間隔の単位、名前付きスケール、ブレークポイントを暗黙には提供しません。`wind.reset` に `none`、`minimal-v1`、`owned-v1` から選んでください。既定は `none` です。新しい basic-blog の雛形は `owned-v1` を選び、パレットと `spacingUnit` を宣言し、記事のリスト表示を手書き CSS で戻しています。リセットを選ぶ際は見出し、リスト、境界線、フォームに加え、`html` と `code`/`pre` のフォントスタック、`sub`/`sup`、`::placeholder`、`::file-selector-button`、`[hidden]` を確認してください。これらを含まないページのピクセル差分では差を検出できません。[Tailwind preflight との違い](../zudo-wind/coming-from-tailwind.mdx#リセット-tailwind-preflight-との違い)も参照してください。

```ts
import { defineConfig } from "zfb/config";

export default defineConfig({
  wind: {
    spec: 1,
    reset: "owned-v1",
    tokens: {
      spacingUnit: "0.25rem",
      colors: { accent: "var(--color-accent)" },
    },
    breakpoints: { sm: { minWidthPx: 640 } },
    dark: { attribute: "data-theme", value: "dark" },
  },
});
```

スタイルシートに `--color-accent` を宣言し、使うユーティリティに必要なトークンを追加します。`site-header` のようにクラス位置の名前がどのユーティリティ基部にも一致しなければ、通常のクラステキストとして残ります。カタログの基部から始まる名前は最長一致する基部で検証されるため、色またはフォントサイズのトークンがなければ `text-link` は ZW006 になります。CSS が候補全体を所有する場合は `wind.authoredClasses: { "text-link": true }` に予約します。完全一致するとユーティリティの検証、診断、CSS 生成が抑止されます。それ以外の場合はユーティリティの綴りを直すか不足トークンを宣言します。ユーティリティ言語とリセットは Tailwind と異なります。ディレクティブ、バリアント、トークン、未対応の構文は [Tailwind からの移行表](../zudo-wind/coming-from-tailwind.mdx)を参照してください。

BEM の `card__title` や snake_case の `card_title` のようにアンダースコアを使う手書きの名前は、`card-title` と同じく通常のクラステキストです。`line-clamp-2`、`contents`、`container` など zudo-wind が実装しない Tailwind ユーティリティは ZW014 の警告になり、代わりに CSS で書くべき宣言を示します。これでビルドを失敗させるには `wind.strict: true` を設定します。`const` や条件分岐に置いたクラス文字列も、`class` 属性に届けば直接書いたクラスと同じく検査されるため、そこにある未対応のユーティリティもビルドを失敗させます。[診断とツール](../zudo-wind/diagnostics-and-tools.mdx)を参照してください。

## コンポーネントと島

`zfb build` と `zfb dev` はページ、コンポーネント、アイランドの JSX を、自動変換と `jsxImportSource: "@takazudo/zfb/zudo-react"` で常にコンパイルします。プロジェクトの `tsconfig.json` は不要で、その `jsx` と `jsxImportSource` の設定も無視されます。ただし、ファイル単位の `@jsxImportSource` pragma はそのファイルの build 変換を上書きできます。`zfb check`、エディター、TypeScript によるテストファイルの型検査で同じランタイムの JSX 型を使うには、`tsconfig.json` で `compilerOptions.jsx` を `react-jsx`、`compilerOptions.jsxImportSource` を `@takazudo/zfb/zudo-react` にします。テストランナーの JSX 変換は、ランナーがこの設定を tsconfig から読むよう構成されていない限り、別途設定してください。使用中の `@takazudo/zfb` と `@takazudo/zfb-runtime` は残します。旧 zfb エンジンのためだけに追加していた `preact`、`react`、`react-dom`、`@types/react`、`@types/react-dom` は削除します。ランタイムは独立パッケージではなく、`@takazudo/zfb/zudo-react` から提供されます。

```json
{
  "compilerOptions": {
    "jsx": "react-jsx",
    "jsxImportSource": "@takazudo/zfb/zudo-react"
  }
}
```

`/** @jsxImportSource preact */` または `/** @jsxImportSource react */` というファイル単位の pragma が残っていないか、たとえば `grep -rln "@jsxImportSource" src pages components` で探し、zudo-react が描画するコンポーネントから削除します。ファイル単位の pragma は build で使う import source への唯一の上書きですが、React や Preact の指定によってそれらのレンダラーがサポートされるわけではありません。Preact が未インストールなら、Preact の pragma によってビルドが `Could not resolve "preact/jsx-runtime"` で失敗します。Preact がウィジェットの peer dependency などとして残っている場合は、静的描画が `ZR_CHILD` 診断で失敗します。どちらの失敗の前にも、`zfb build` と `zfb dev` は、ページやページが import するモジュールにあるこうした pragma ごとに、プロジェクトのファイル、行、列を示す `zfb warn:` 行を表示します。この警告は表示するだけで、終了ステータスは変わりません。依存パッケージ内のファイルは対象外なので、[サードパーティウィジェットの埋め込み](../concepts/islands.mdx#サードパーティウィジェットの埋め込み)のように DOM ホストの背後へ遅延マウントする Preact のウィジェットパッケージは、警告なしでビルドできます。`zfb check` はページ以外の authored `.tsx` / `.jsx` も調べ、`--skip-tsc` でも ZB005 を警告します。依存パッケージ、生成出力、スクラッチ領域は対象外で、警告だけでは check は失敗しません。

hook を使うコンポーネントは、セットアップ時に一度実行される zudo-react コンポーネントへ書き換えます。書き込み可能な状態とフォームのモデルには `signal()`、読み取り専用の派生値には `computed()`、ライフサイクルには `getScope()` と `scope.effect()`、条件付き領域とキー付き領域には `Show` と `For` を使います。読み取り専用または computed の signal は書き込み可能なモデルにできません。JSX では `class`、`for`、`style={{ "background-color": "red" }}` のような HTML/CSS の表記と、ネイティブの `on:click` リスナーを使います。React 式の props とブランドのない要素オブジェクトは、zudo-react の JSX または `h()` に置き換えます。`rawHtml` は信頼できる内容に限り、children と併用できません。`<script>` と `<style>` のテキストの子は拒否されるため、信頼できる静的文字列を `<style rawHtml={CSS} />` または `<script rawHtml={JS} />` に渡すか、子を持たない外部 `<script src="/assets/app.js" />` を使います。この raw-text の文字列はそのまま出力され、エスケープもサニタイズもされません。この規則は `<title>` と `<textarea>` には当てはまらず、通常のテキストの子を受け取ります。変換例は [Preact hooks からの移行表](../zudo-react/coming-from-preact-hooks.mdx)を参照してください。

標準的な HTML/SVG マークアップは、TypeScript、サーバーレンダリング、ハイドレーション、新規マウントで共有する有限の語彙に従います。`<meta property="og:title">` の Open Graph メタデータ、`<link rel="preload" as="font">` の preload リンク、外部の `<script defer>`、SVG の `use`/`href` は通常の JSX で直接記述できます。これらの対応属性に `rawHtml` の回避策は不要です。未知の属性名と React 式の表記は引き続きエラーになり、カスタム要素の属性は文字列のみです。値の分類と SVG 名前空間の詳細は[コンポーネントと JSX](../zudo-react/components-and-jsx.mdx)を参照してください。

移行時に `.mdx` と `.md` ファイルの手書き raw HTML テーブルを確認してください。raw HTML の `<table><tr>…` は `ZR_PARSER_CONTEXT: table > tr` で失敗するため、各行を明示した `<tbody>` で囲みます。この規則は両方の形式の raw HTML に適用されます。GFM のパイプテーブルは別の形式で、Markdown コンパイラーがすでに `<thead>` と `<tbody>` を出力するため変更は不要です。構造規則の詳細は[テーブルと select の子要素](../zudo-react/components-and-jsx.mdx#テーブルと-select-の子要素)を参照してください。

ビルドや dev のレンダリングが React 形式の綴りを拒否すると、代わりに使う綴りを示し、JSX であれば要素を記述したファイル、行、列も示します。事前に `zfb check` を実行する必要はありません。この位置と、構造上の文脈や生成されたバンドルのスタックとの違いは、[サーバーレンダリング](../zudo-react/server-rendering.mdx)の「レンダリング失敗の読み方」を参照してください。

`<Island>` は引き続きコンポーネントを包むビルド時の要素です。ただし受け渡しは厳密になります。子コンポーネントは 1 つ、props は JSON、識別情報はソーススキャナーと一致する必要があります。手書きのラッパーにも完全で有効なメタデータが必要です。ハイドレーションは一致するサーバーのマークアップを採用し、不一致の島は個別に失敗します。SSR を省略するルートは `data-when` で起動を調整し、クライアントで正常にマウントした後にフォールバックを置き換えます。フォームは明示的な書き込み可能モデルを使い、select は単一選択のみで、ハイドレーション時は DOM の値が優先されるため、動作を確認してください。[島のガイド](../concepts/islands.mdx)も参照してください。

### 任意の島 prop

任意の島 prop では、自身が持つ列挙可能な文字列キーのデータプロパティで、値が `undefined` のものは SSR と JSON transport の前に再帰的に省略されます。配列内のレコードも同じです。サーバーコンポーネントとクライアントには同じキーで正規化した props が渡るため、`Object.hasOwn` の結果は一致します。明示的な `null` はプロパティとして保持されます。

レコードプロパティの省略は v2 と同じ動作です。配列は厳密で、undefined の要素や穴は値に自動変換せずエラーになります。配列要素を存在させたままにする場合は `null` を使ってください。

~~~ts
import { serializeProps } from "@takazudo/zfb/zudo-react/server";

serializeProps({
  currentSlug: undefined,
  nodes: [{ slug: "a", description: undefined }, { slug: "b", description: null }],
});
// {"nodes":[{"slug":"a"},{"slug":"b","description":null}]}
~~~

詳細は[サーバーレンダリング](../zudo-react/server-rendering.mdx)を参照してください。

zudo-react のクライアントランタイムについて、Preact と同じバンドルサイズになる保証はなく、固定のバイト数予算もまだ決まっていません。別のフォローアップで、本番用アイランドの出力を測定し、安全に測定できる最適化を評価したうえで、その結果から回帰予算を決めます。この作業は v3 への移行を妨げません。このガイドではプロジェクト固有のサイズを保証しません。

## MDX と md-wasm

`@takazudo/zfb-md-wasm` の `compile()` と `renderHtml()` のオプションは `jsxRuntime` を受け付けなくなりました。`react` や `preact` を選ぶ代わりに、このフィールドを削除してください。型付き API は拒否し、JSON の検証では `jsxRuntime` を示す未知フィールドのエラーになります。コンパイル済み MDX は Fragment を `@takazudo/zfb/zudo-react/jsx-runtime` からインポートします。出力をバンドルする側でこのサブパスを解決し、旧エンジンへエイリアスしないようにします。

## CLI と環境変数

スクリプトと CI から `ZFB_TAILWIND_BIN` と `ZFB_TAILWIND_OXIDE_WARMUP` を削除します。Tailwind の同梱バイナリとピンは削除されました。`zfb css` は単独の CSS コマンドとして残り、zudo-wind でコンパイルします。明示的な `--source` 入力も引き続き使えます。`node_modules` や `dist` 内のパッケージファイルも、プロジェクトの設定済み出力ディレクトリの外なら指定できます。ただし、設定済みの `outDir`、`--output` のパス、zfb のスクラッチルート内の一致ファイルは除外されます。すべて除外されると `zfb css` は `ZW010` エラーで失敗し、一部だけ除外されると `ZW010` 警告を出して残りを走査します。[CLI のソース規則](../api/cli.mdx#zfb-css)を参照してください。`zfb wind explain <candidate>` は一つの候補を説明し、`zfb wind audit` はプロジェクト内の候補を調べます。build と dev は `.tsx`、`.ts`、`.jsx`、`.js`、`.mdx`、`.md` をスキャンし、単独コマンドの明示的なソースには `.html` と `.mjs` も指定できます。

`zfb --version` はリリースバージョンと `embedded esbuild` のバージョンを表示し、Tailwind の行は表示しません。移行中のエラーの調査には [wind の診断ガイド](../zudo-wind/diagnostics-and-tools.mdx)を使ってください。

## クラスやコンポーネントを配布するパッケージ

以前、配布した safelist に依存していたパッケージは、完全な候補をバージョン付き JSON マニフェストとして配布してください。利用側は producer のキーを付けてファイルを宣言します。異なる producer はプリセットとアプリのマージ後も保持されます。すべてのエントリーが厳密に検証され、利用側で必要なトークンを設定する必要があります。マニフェストはトークンを定義できず、自動発見もされません。手作業で管理せず、`zfb wind manifest --producer <id> --output <file> --config <利用側の config>` で生成してください。[`zfb wind manifest`](../api/cli.mdx#zfb-wind-manifest) を参照してください。

```json
{
  "schemaVersion": 1,
  "specVersion": 1,
  "producer": "widgets",
  "candidates": ["group", "p-0", "hover:bg-accent"]
}
```

```ts
import { defineConfig } from "zfb/config";

export default defineConfig({
  wind: {
    manifests: { widgets: { path: "widgets/wind.json" } },
    tokens: { colors: { accent: "#2563eb" } },
  },
});
```

`widgets` パッケージは `./wind.json` を export する必要があります。bare specifier はパッケージの exports から解決され、`./` で始まるパスは宣言した config のディレクトリ（プリセット由来ならそのプリセットパッケージ）を基準に解決されます。[マニフェストパスの解決](../zudo-wind/configuration.mdx#wind-キー-マニフェストパスの解決)を参照してください。

配布するコンポーネントは `@takazudo/zfb/zudo-react` からインポートし、同じ JSX import source を使ってください。zudo-react が描画するコンポーネントには Preact や React の JSX runtime import を含めないでください。独自フレームワークを持つ不透明な自己マウント型ウィジェットは、島から遅延読み込みできます。[サードパーティウィジェットの埋め込み](../concepts/islands.mdx#サードパーティウィジェットの埋め込み)を参照してください。マニフェストの検証と探索ルートは [ソースと候補](../zudo-wind/sources-and-candidates.mdx)を参照してください。

## チェックリスト

1. 設定プリセットを先に更新し、対応する v3 パッケージとバイナリを導入します。`zfb --version` と `package.json` を確認します。
2. `framework` を削除し、`tailwind` を `wind` または `wind: false` に置き換えます。`zfb check` で削除済みキーと無効な内部データを確認します。
3. Tailwind のインポートとディレクティブを削除し、トークンとリセットを設定したうえで、代表的なページの `html` と `code`/`pre` のフォントスタック、`sub`/`sup`、`::placeholder`、`::file-selector-button`、`[hidden]` を確認します。プロジェクトの入出力パスを指定して `zfb css --input <entry.css> --output <output.css>` を実行します。
4. `zfb check`、エディター、テストファイルの型検査用に tsconfig の JSX 設定を合わせ、必要に応じてテストランナーの JSX 変換を別途設定します。ファイル単位の `@jsxImportSource` pragma を削除し、依存関係、コンポーネント、島、フォームモデルを更新します。`zfb check` を実行し、型エラーを修正します。
5. md-wasm 呼び出しから `jsxRuntime` を削除し、コンパイル済み出力の利用側を更新します。パッケージの TypeScript チェックを実行します。
6. 動的に組み立てる有限のクラスを完全なリテラルかマニフェストに置き換えます。CI または pre-push のチェックとして `zfb wind audit --fail-on error` を使い、代表的なクラスに対して `zfb wind explain <candidate>` を実行します。多数の候補を調べるときは、`zfb wind audit --json --severity warning` と `zfb wind explain --stdin --json` で、機械可読な結果を 1 回のプロセスで得られます。
7. ビルドスクリプトから Tailwind の環境変数を削除します。`zfb build` を実行し、主要ページ、島、フォーム、スタイルをブラウザーで比較します。
