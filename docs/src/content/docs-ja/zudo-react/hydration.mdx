## 島の内容をハイドレートする

クライアントエントリは **@takazudo/zfb/zudo-react/client** です。**hydrate** は、渡された島のラッパー内にある既存の子 DOM を引き継ぎます。子の記述、ラッパー要素、クライアントバンドルが期待するコンポーネントとビルドの識別子を受け取ります。zfb が出力した島では、ラッパー自体を zfb が所有します。

~~~tsx
import { hydrate, parseProps } from "@takazudo/zfb/zudo-react/client";

function Counter({ label }: { label: string }) {
  return <p>{label}</p>;
}

const wrapper = document.querySelector("[data-zfb-island='Counter']");
if (wrapper instanceof Element) {
  const component = wrapper.getAttribute("data-zfb-island");
  const build = wrapper.getAttribute("data-zfb-build");
  const json = wrapper.getAttribute("data-props");
  if (component === "Counter" && build && json !== null) {
    const identity = { component, build };
    const props = parseProps(json);
    if (typeof props.label === "string") {
      hydrate(<Counter label={props.label} />, wrapper, { identity });
    }
  }
}
~~~

zfb と連携したアプリケーションでは、島の境界がこのメタデータを読み取って検証します。クライアント側の境界を自分で所有する場合に hydrate や mount を直接呼びます。スケジュールと永続化については [zfb の島のガイド](../architecture/islands.mdx)を、外部のホストで必要な準備については [zfb サイトの外で zudo-react を使う](./overview.mdx#zfb-サイトの外で-zudo-react-を使う)を参照してください。

## 引き継ぎには事前検証がある

ハイドレーションはコンポーネントのセットアップより前に、接続されたラッパー、識別子、転送形式、キャンセル状態、ルートの重複を検証します。仮のスコープツリーを一つ作り、各コンポーネントを一度呼びます。その後、DOM の変更、ref の設定、リスナーの追加をせずに既存ノードを検査します。

事前検証に成功した後、ランタイムはキャンセルと接続を再確認し、既存ノードにバインディングを付け、ref を設定し、生きたフォーム値を同期してから有効化を始めます。更新を同期するためにコンポーネントを再実行しません。

プロトコルは動的なテキスト、コンポーネントの範囲、Fragment、条件分岐、リスト、不透明な raw HTML に、対応するローカルのコメント領域を使います。マーカーが存在するのは島のサブツリー内だけです。zfb が生成した島では、ラッパー要素と data-zfb-island 属性を zfb が所有します。呼び出し元が所有する mount では、ラッパーはホストの所有物です。サーバーレンダリングが出力したマーカーを保ってください。

## 識別子とサーバー側 props の検査

コンポーネント名、ビルドの識別子、転送形式のバージョン、ランタイムプロトコルはセットアップ前に検査されます。hydrate または mount に渡す RootOptions の識別子はラッパーと一致しなければなりません。古いバンドルや一致しないラッパーでは、島またはマウントするルートは有効化されません。

zfb が出力した島をハイドレートするときは、data-props が存在し、有効な JSON レコードでなければなりません。**parseProps** は不正な JSON、最上位の配列やスカラー、入れ子にある禁止キーを拒否します。転送によって記述、signal、クラスインスタンスが復元されることはありません。リアクティブな状態はコンポーネントのセットアップ内で作り直してください。クライアントから直接 mount する場合、props はメモリ上で渡し、data-props は読みません。詳しくは下の「自分で所有するホストから mount する」を参照してください。

zfb の島の境界には、登録済みの同期的な関数コンポーネントが一つ必要です。複数の子、ホスト要素の子、入れ子の島、空でない children prop は島の props として転送できないため拒否されます。再帰的に空の配列と空の値は許可され、省略されます。

## 不一致なら有効化しない

事前検証では、解析済みの構造、名前空間、範囲の識別子、期待するテキスト、フォームコントロールの形を比較します。生の HTML ソースは比較しないため、属性の順番、引用符の形式、同等の文字参照の表記は解析後には影響しません。通常の属性は引き継ぎ時に保持され、不一致の判定には使われません。その後のリアクティブな書き込みではバインディングが所有する値が適用されます。ラッパーの識別子とフォームの形は厳密に検査され、type、multiple、radio の name/value、option の value、フォームとの関連付けも対象です。

通常のテキスト比較では HTML の改行を正規化し、比較時に限って ASCII の HTML 空白の連続を一つにまとめ、両端の ASCII スペースを除きます。NBSP やほかの Unicode 空白は保たれます。整形済みテキストは HTML の改行を正規化した後、厳密に比較します。動的テキスト領域の外にある空白だけのテキストノードは無視されます。raw HTML の内容は不透明です。明示的な ErrorBoundary 領域の外では、表記を合わせるだけのために既存の要素や空でないテキストを作り直すことはありません。

どのモデルにも書き込む前に、フォームコントロールを読み取ります。変更済みの値、checked 状態、選択範囲、フォーカスはハイドレーションの不一致になりません。有効化時にブラウザの現在値が優先される仕組みはフォームガイドで説明します。

ZR_HYDRATION_MISMATCH、ZR_IDENTITY、ZR_PROPS、ZR_UNSUPPORTED_POSITION、ZR_DUPLICATE_ROOT、ZR_CANCELLED などの失敗では診断を報告して null を返します。事前検証の失敗時、サーバー DOM とユーザーの状態は変わりません。ハイドレーションが黙って mount に切り替わることはありません。該当する島は不活性のままで、分離されたほかのルートは続行できます。

診断にはコンポーネント、DOM パス、段階、期待値と実際の値の要約、プロトコル、ビルドを含みます。デフォルトでは props 全体、raw HTML、入力値、秘密情報は含みません。

## 境界のハイドレーション

ErrorBoundary は、明示的に置き換えられるローカルな領域です。ハイドレーション中、クライアントは新たにレンダリングを試み、境界の内側だけを置き換える準備をします。サーバーとクライアントの両方が成功した場合でも内側は作り直されるため、サーバー DOM の同一性、フォーカス、選択範囲、ハイドレーション前に行われた編集は保持されません。領域の外にある要素と状態は、通常の引き継ぎに従います。

| サーバーの結果 | クライアントの試行 | ハイドレート後の境界 |
| --- | --- | --- |
| 正常なサブツリー | 失敗 | クライアントの fallback |
| fallback | 失敗 | クライアントの fallback |
| fallback | 成功 | 新しい正常なクライアントのサブツリー |
| 正常なサブツリー | 成功 | 新しい正常なクライアントのサブツリー |

境界の対になったマーカーは、ローカルな番号の名前空間を持ちます。失敗した試行や成功した試行の子孫の数によって、後続の兄弟のマーカーがずれることはありません。ハイドレーションはサーバーの内容を破棄する前に、マーカーの文法、入れ子、名前空間の所有、識別子の重複を検証します。不正なマーカーと入れ子の島は、引き続きルート全体の失敗になります。置き換えはルート全体が事前検証を通過するまで待つため、後続の兄弟の不一致やキャンセルがあればサーバー DOM はそのまま残ります。

新しく作られた境界内のフォームコントロールは、クライアントのモデルから初期化されます。保持される兄弟のコントロールは、変更済みの値を含めて通常のハイドレーションの意味に従います。新しいコントロールと保持されるコントロールでモデルを共有している場合は、保持されるコントロールの現在値が優先されます。新旧が混在する radio グループでは、保持される選択肢がチェックされていればそれが優先され、そうでなければモデルが選んだ新しい選択肢が選択されたままになります。フォームグループの検証は引き続きルート全体で実行され、特定の境界に帰属させるのではなく診断として扱われます。

ErrorBoundary は、コメント領域が保たれるフローの位置でだけ使ってください。Show や For と同じく、select、option、title、テーブル構造の文脈の中では使えません。セットアップ、リセット、エラーの各段階については、[スコープとライフサイクル](./scopes-and-lifecycle.mdx)と、英語版の [Local subtree recovery](/docs/zudo-react/scopes-and-lifecycle/#local-subtree-recovery) を参照してください。

## HTML パーサーの文脈を守る

table と select の構造規則は、島のない静的サーバーレンダリングにも適用されます。パーサーが構造を決める要素には、許可された組み込み要素を直接置きます。たとえば tbody には tr、select には option または optgroup、optgroup には option を置きます。コンポーネントや Fragment をこれらの位置の代わりにはできません。table 構造には tbody を明示し、option のラベルは静的なスカラー文字列にしてください。島の中でコメント区切りの動的領域を使えるのも、HTML 解析後にその位置が保たれる場所だけです。そのため table、tbody、tr のようなテーブル構造上の階層や、select、optgroup、option の内部では使えません。

title の内容は静的なスカラーテキストです。textarea の内容はフォームアダプターが扱います。島の中では template は使えません。script と style で使えるのは、[コンポーネントと JSX](./components-and-jsx.mdx)の制約に従う静的な rawHtml だけです。パーサーに依存する noscript、xmp、noembed、noframes、plaintext では、ハイドレートされる内容と rawHtml は引き続き拒否されます。子を持たない `iframe` のシェルは使えますが、`src` または `srcdoc` から読み込まれる文書はブラウザーが所有し、ハイドレーションの対象外です。`srcdoc` はアプリケーションが信頼する入力であり、サニタイズされません。iframe に JSX の子や `rawHtml` を渡したり、iframe 要素のフォールバック子ノードやその中のハイドレーションマーカーを入れたりしないでください。未対応の構造はブラウザーパースによる修復に頼らず、要素、島、パスを示す診断で失敗します。

## mount はクライアントレンダリング

**mount** は同じ子の記述と識別子の検査を使いますが、サーバーの子を引き継がず新しい DOM を作ります。呼び出し元が境界を所有する場合は、以下のようにルートコンポーネントを直接 mount します。zfb が生成した skip-SSR の島では、zfb が load、idle、visible、media のスケジュールとキャンセル規則を適用します。その後ランタイムは DOM の外で新しいサブツリーを構築・検証し、有効化前に fallback を一度に置き換えます。セットアップや検証に失敗したら fallback は残ります。スケジュール用 API が使えない場合は即時の fallback を使います。

## 自分で所有するホストから mount する

アプリケーション自身がクライアント専用の境界を所有し、**mount** を直接呼ぶ場合はこの手順を使います。ホスト側でラッパーを作り、接続してから mount します。この直接呼び出しはコンポーネントを zfb の静的な島スキャナーに登録しません。スキャナーで検出するサーバー側の島は、引き続き zfb の連携と JSON/1 の props 転送を使います。

クライアント専用の mount では、ラッパーに次の4属性を設定します。ホスト側で空でない安定したビルド文字列を選んでください。zudo-react はこの値を `RootOptions.identity.build` と等値比較するだけで、スキャナーレジストリから検索しません。

~~~tsx
import { h, type Child } from "@takazudo/zfb/zudo-react";
import { mount, type RootHandle } from "@takazudo/zfb/zudo-react/client";

function PreviewChrome(props: { onSelect: () => void; slot: Child }) {
  return h(
    "nav",
    null,
    h("button", { "on:click": props.onSelect, children: "Select" }),
    props.slot,
  );
}

const identity = { component: PreviewChrome.name, build: "preview-frame-v1" };
const host = document.createElement("div");
host.setAttribute("data-zfb-island-skip-ssr", identity.component);
host.setAttribute("data-zfb-transport", "json/1");
host.setAttribute("data-zfb-protocol", "zudo-react/1");
host.setAttribute("data-zfb-build", identity.build);
document.body.append(host); // mount requires a connected root

const props = {
  onSelect: () => console.log("selected"),
  slot: h("span", { children: "Provided by the host" }),
};

function mountPreview(): RootHandle | null {
  const root = mount(h(PreviewChrome, props), host, {
    identity,
    report(diagnostic) {
      console.error(`[zudo-react] ${diagnostic.code}`, diagnostic);
    },
  });
  if (root === null) {
    host.replaceChildren(document.createTextNode("Preview unavailable."));
    return null;
  }
  return root;
}

let root: RootHandle | null = null;
function resume() {
  if (root && !root.disposed) return;
  root = mountPreview();
}
function pause() {
  root?.dispose(); // stop listeners and scopes; keep the current DOM
}
function stop() {
  root?.unmount(); // dispose and remove the rendered subtree
  root = null;
  host.remove();
}

resume();
// The host may call pause() and resume() as its own lifecycle changes.
// Call stop() before removing the host permanently.
~~~

ルートの子は名前付き関数コンポーネントを一つにします。その `displayName ?? name` は `identity.component` と一致する必要があります。`h` に渡す props はメモリ上にあるため、コールバックや `slot` のような子の記述を `data-props` や JSON シリアライズに通す必要はありません。`report` コールバックには構造化された診断が渡されます。mount が失敗すると `null` を返すため、ルートが有効だと扱う前に結果を確認してください。`dispose()` はスコープとリスナーを停止しますが、現在の DOM は残します。同じ接続済みラッパーに再度 mount するとそのサブツリーを置き換えます。`unmount()` はさらにそのサブツリーを削除します。

### ホストが受け持つこと

直接の mount には zfb の島の連携が一切付かないため、次の各段階は呼び出し側が受け持ちます。

- **JSX の変換。** 自動 JSX ランタイムと、インポート元 `@takazudo/zfb/zudo-react` でコンポーネントをコンパイルします。あるいは、この例のように `h` で記述を組み立てます。
- **ラッパー。** ラッパーを作り、上の 4 つの属性を設定し、`mount` を呼ぶ前にドキュメントへ接続します。
- **識別子。** コンポーネント名とビルド文字列がラッパーの属性と一致する識別子を渡します。
- **失敗。** `null` の結果は「マウントされていない」として扱い、独自の fallback を表示します。診断は `report` コールバックに渡されます。
- **ライフサイクル。** DOM を残したままリスナーとスコープを止めるには `dispose()`、サブツリーも削除するには `unmount()` を呼び、境界が完全になくなるときはラッパーを取り除きます。
- **スケジュール。** いつマウントするかを決めます。load、idle、visible、media のタイミングは zfb が生成した島のものであり、直接の呼び出しには適用されません。不要になったマウントをキャンセルするには、`RootOptions.signal` に `AbortSignal` を渡します。

代わりにサーバーで描画された HTML を引き継ぐ場合は `hydrate` を呼びます。このときラッパーは skip-SSR マーカーではなく `data-zfb-island` を持ち、ホストはサーバーが描画に使ったのと同じ props を渡します。[島の内容をハイドレートする](#島の内容をハイドレートする)の例では、それを `data-props` から `parseProps` で読み取っています。`hydrate` はラッパーの識別子を検査しますが、`data-props` を自分では読みません。
