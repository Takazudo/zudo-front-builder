## 現在の所有者を取得する

同期的なコンポーネントのセットアップ中、または Show や For のファクトリ内で **getScope** を呼び、その関数をレンダリングしている所有者に作業を登録します。セットアップ中に直接呼んだヘルパーは同じ所有者を共有し、独立したスコープは作りません。

~~~tsx
import type { ReadonlySignal } from "@takazudo/zfb/zudo-react";
import { getScope, signal } from "@takazudo/zfb/zudo-react";

function Clock() {
  const scope = getScope();
  const now = signal(Date.now());

  scope.onActivate(() => {
    const timer = window.setInterval(() => {
      now.value = Date.now();
    }, 1000);

    return () => window.clearInterval(timer);
  });

  return <time>{now}</time>;
}
~~~

getScope はセットアップ専用です。現在のレンダリング所有者がいない場所で呼ぶと ZR_NO_SCOPE が発生します。await を越えて所有者は維持されないため、非同期セットアップには対応しません。純粋な SDK コンストラクターは記述を作るだけなので、スコープなしでも呼べます。

## セットアップと有効化を分ける

同期的なリソースのクリーンアップは **onCleanup** に登録します。ブラウザだけで行う起動処理は **onActivate** に登録し、そのコールバックから同期的なクリーンアップを返すこともできます。追跡されるブラウザの effect は **effect** に登録します。

~~~tsx
function PageTitle({ title }: { title: ReadonlySignal<string> }) {
  const scope = getScope();

  scope.effect(() => {
    document.title = title.value;
  });

  return <h1>{title}</h1>;
}
~~~

有効化コールバックはブラウザでのみ、DOM のコミット後に実行されます。レンダラーはすべての ref をコールバックより前に設定します。子スコープは親より先に有効化され、兄弟は出力順、一つのスコープ内のコールバックは登録順に進みます。すべての有効化コールバックが終わった後、スケジューラーの最初の effect 段階で effect が始まります。サーバーではブラウザの有効化も effect も実行されません。

effect はコールバック中に読み取った値を追跡します。再実行前には前回のクリーンアップが追跡なしで実行されます。最後のクリーンアップはスコープの破棄時に実行されます。effect が例外を投げると報告され、古い依存関係は解除されますが、ほかの effect は続行します。

有効化に失敗すると、ランタイムはそのルートのリソースを破棄して失敗を報告します。すでに外部の状態を変えたユーザーコードは自分でクリーンアップを用意する必要があります。ランタイムは任意の副作用を取り消せません。

Promise を返すクリーンアップは無効です。クリーンアップコールバックは同期的で、スコープが有効な間に登録する必要があります。後で非同期処理を行うコールバックは提供される abort signal を使い、結果を反映する前に状態を確認してください。

## 破棄しても DOM は削除されない

スコープを破棄すると、所有者を無効にし、signal を abort し、キューにあるジョブを止め、子スコープを破棄します。ノードがまだ存在する間に登録の逆順でクリーンアップを実行し、最後に ref をクリアします。クリーンアップ中にエラーが起きても報告して続行します。破棄した作業は再び有効化できません。

マウント済みルートの **dispose** はランタイムのリソースを解放しますが、ラッパーとその DOM は残します。**unmount** は破棄に加え、そのハンドルが所有するノードを削除し、ラッパーは残します。zfb はラッパーの内容を自分で置き換える前に破棄を使います。ルートの削除や保留中のトリガーの取り消しで、以後の有効化を防げます。

クライアントのルートハンドルは identity と破棄状態を公開します。hydrate は既存のノードを引き継ぎ、mount は新しい子 DOM を作ります。どちらも想定される失敗を報告して null を返し、部分的に有効なハンドルは返しません。zfb はルートごとにエラーを分離するため、一つの島が壊れてもほかのルートの処理は続きます。

サーバーレンダリングは一時的なスコープグラフを所有し、エラーの場合も含め、レンダリング終了時に必ず破棄します。リクエスト固有の可変状態はモジュールレベルの変数ではなくレンダリング内に置いてください。

## ローカルな部分ツリーの回復

内容の準備やレンダリングで失敗する可能性があるコンポーネントを ErrorBoundary で囲みます。その領域をフォールバックで置き換え、兄弟要素はマウント済みで操作できる状態に保ちます。通常のコンポーネント内の try/catch で未実行の描画記述を返しても、レンダラーが後で実行する子孫のエラーは捕捉できません。

~~~tsx
import { ErrorBoundary, signal } from "@takazudo/zfb/zudo-react";

function EditorPreview() {
  const revision = signal(0);

  return (
    <main>
      <ErrorBoundary
        resetKey={revision}
        children={() => <DocumentPreview />}
        fallback={(error, reset) => (
          <button type="button" on:click={() => reset()}>
            プレビューに失敗しました。再試行
          </button>
        )}
      />
      <EditorToolbar />
    </main>
  );
}
~~~

プレビューの入力を変更した後で revision を更新するか、フォールバックの reset コールバックを使います。children と fallback はファクトリで、Show の分岐の所有方式と同じです。どちらのファクトリでも、同期セットアップ中に getScope を使えます。リセットはコミットキューで新たな試行を実行し、保留中の複数の要求はまとめられます。resetKey の変更は Object.is で比較し、失敗した内容だけでなく正常な内容もリセットします。セットアップ中にシグナルを読むだけでは、境界はそのシグナルを購読しません。境界が破棄されると reset コールバックは何もしなくなります。

失敗した試行のスコープは、フォールバックの描画前に破棄され、切り離されます。クリーンアップ、リスナー、ref、購読、キュー内の処理はその試行に属し、再試行では新しいリソースを作ります。正常な兄弟要素は自身のスコープと DOM を保持します。クリーンアップのエラーは診断として残りますが、残りのクリーンアップを妨げません。アンマウントでは現在の試行またはフォールバックを破棄します。フォールバックは外側の回復所有者の下で描画されるため、そのエラーは外へ伝わります。未処理のエラーでは、既存のルートやスケジューラーの診断と元のエラー詳細が保持されます。

| 段階 | 回復の挙動 |
| --- | --- |
| 子孫の同期コンポーネントセットアップ、children ファクトリ、通常のノードごとの描画検証 | 最も近い ErrorBoundary |
| レンダラーがスケジュールする Show/For のソース読み取り、キー関数、新しい分岐や項目の描画 | 最も近い ErrorBoundary |
| リアクティブなテキスト、属性、スタイル、通常の rawHtml の描画 | 最も近い ErrorBoundary |
| 境界の再試行の準備 | この境界。フォールバックの失敗は外へ伝わる |
| コントロールをまたぐモデル／ラジオグループの検査や、サーバーの最終ラジオ検証を含む、フォーム全体の検証 | 既存のルート所有の検証。グループは境界をまたぎ得る |
| イベントハンドラー、effect、有効化コールバック、クリーンアップ、非同期の reject | 既存の処理。ErrorBoundary は捕捉しない |
| 島の識別子、props の転送、入れ子の島、予約済み rawHtml、不正なプロトコル／範囲マーカー | 整合性の失敗。フォールバックで隠さない |

同期コンポーネントが promise を返すのは不正な描画結果です。その検証エラーを捕捉しても、後から起きる promise の reject を監視したり回復したりはしません。アプリケーション側で非同期エラーを明示的に処理してください。境界は外部に対する任意の副作用を巻き戻しません。

サーバーレンダリングでは、失敗した試行の途中までの HTML を捨て、レンダラーの内部管理状態を戻してからフォールバックを描画します。ハイドレーションでは周囲の兄弟要素を引き継ぎつつ、境界の内側を常にクライアントの試行から作り直します。サーバーとクライアントの両方が正常な場合も同じで、境界内のフォーム編集やノードの同一性は保持されません。編集可能なコントロールを置く前に、[境界のハイドレーション](./hydration.mdx#境界のハイドレーション)を確認してください。
