zfb は、ユーザーが TypeScript と JSX を書く静的サイトフレームワークです。フレームワーク自体は Rust です。このページではその理由を説明します。

## パフォーマンス

Rust はルート走査、依存関係の管理、コンテンツ処理、ファイル I/O を担います。ネイティブ Rolldown が JavaScript のモジュールグラフを変換・バンドルし、組み込み V8 がユーザーページを実行して zudo-react がレンダリングします。完全な TypeScript 型チェックは別で、`zfb check` が **`tsc --noEmit`** をサブプロセスとして呼び、ネイティブのルート／スキーマ検査も実行します。Rust が TypeScript の型チェックまで実装しているわけではありません。

dev では保存をウォッチャーが受け、グラフが影響ページを選び、lazy レンダリングによりリクエストまで処理を遅らせられます。ブラウザのリロードイベントは WebSocket `/__zfb/reload/ws` を使い、SSE `/__zfb/reload` はツール向けに残ります。レンダラーに関わる編集では、バンドルの再構築と新しい V8 ホストの起動が必要になることもあります。これらは設計上の境界であり、普遍的なレイテンシやメモリ量の保証ではありません。条件のないミリ秒単位や 2,000 ページの計測値に頼らず、実際のプロジェクトとマシンで測定してください。

## メモリ安全性と構造化されたエラー

Rust のコンパイラは、use-after-free、データ競合、null 参照をコンパイル時に排除します。ビルドは `dist/` を書き込んでいる途中でセグフォルトしません。ウォッチャーは保存のバーストが重なってもパニックしません。退屈な勝利、いったん手にすると気づかなくなる類のものです。

目に見える勝利はエラーの質です。zfb は `anyhow` を端から端まで使うため、すべてのエラーはチェーンとして CLI に届きます。直接の失敗、失敗した操作、ファイルパス、より高レベルの意図です。TSX のコンパイルエラーは、ファイル・行・列・それを引き起こした操作を示します — 汎用的な「build failed」ではありません。

## 適合する並行性

ビルドオーケストレーターは、HTTP リスナーをブロックすることなく Rust 側の bookkeeping、ファイル I/O、dev サーバーの処理を実行できます。リクエスト処理、ファイル配信、WebSocket／SSE ブロードキャストは tokio 上にあり、重いレンダーディスパッチはその async 境界から隔離されています。

ページレンダリング自体は今日 Rayon で並列化されていません。ユーザー TSX は、ビルド時 SSG と dev 側の `prerender = false` ディスパッチのどちらでも、単一の組み込み V8 isolate スレッドを通って実行されます。並行性の利点は、1 回のビルドで複数ページレンダリングを並列実行することではなく、その isolate と残りの Rust パイプラインの周囲に明確な境界があることです。

## 配布

CLI エンジンはネイティブ実行ファイルです。npm の `@takazudo/zfb` 配布には TypeScript SDK も含まれ、slug ヘルパーの依存パッケージと、対応する実行ファイルを届ける optional なプラットフォームキャリアパッケージを宣言しています。インストールして監査すべき実際の `node_modules` 依存ツリーがあり、エンジンが単一バイナリでも SDK の依存関係が消えるわけではありません。スタンドアロンのバイナリインストールも別の選択肢です。[インストール](../getting-started/installation.mdx)を参照してください。

再現可能なツール環境のためにパッケージバージョンと lockfile を固定します。静的デプロイが配信するのは HTML／CSS／ブラウザアセットで、Cloudflare アダプターはリクエスト時 SSR 用の Worker モジュールを追加します。どちらも CLI 実行ファイルを本番ランタイムとして出荷しません。デスクトップ／ローカルサーバーの組み込みでは、その実行ファイルを明示的に配布する選択もできます。

## 正直な反論: ビルドコスト

zfb のワークスペースのコールド `cargo build` にはネイティブ／V8 依存の準備も含まれます（`v8` クレートは `zfb-js-host` 経由で取り込まれます）。以前から記載されていたワークスペース全体の 15–30 分という値は、現在の direct ホストのベンチマークでも所要時間の保証でもありません。ツールチェーン、プラットフォーム、キャッシュされた成果物に依存し、増分ビルドでは処理を再利用できます。このコストは受け入れられています。Tauri での配布はエンドユーザーのマシンに Node 依存のない単一バイナリを必要とし、V8 をバイナリに組み込むことがその制約を満たす唯一の方法だからです。完全な理由は [JS runtime](./js-runtime.mdx) を参照してください。

zfb は `zfb-render` のデフォルトで有効な `direct-v8` cargo フィーチャーの背後で V8 のビルドをゲートします。このフィーチャーは `zfb-js-host` の direct V8 ホストを選びます（[JS runtime](./js-runtime.mdx#現在のデフォルトと実験) を参照）。`--no-default-features` では V8 なしでビルドされます。JavaScript のレンダリングを必要としないクレートは V8 を一切引き込みません。コントリビューターは `zfb-content` などを V8 ホストのコンパイルなしでビルド／テストできます。所要時間はツールチェーンとキャッシュに依存します。エンドユーザーはこのコストを支払いません — プリビルドのバイナリをインストールするからです。

このゲートは、リンクされた `zfb` バイナリそのものにとってはタダの昼食ではありません。V8 が成果物を支配します。`deno_core` のホストを使っていた時期の計測では、バンドルされた `v8` rlib はそれ自体で約 169 MiB、残りの `deno_*` ツリーがさらに約 13 MiB を加え、V8 オフの `zfb` はストリップ後で V8 オンの出荷バイナリより約 82 MiB 小さくなりました。`deno_*` クレートは #4395 でなくなりましたが、direct V8 ホストについてこれらの数値は再計測していません。今日のところ、その軽いバイナリは `zfb-render` ライブラリの V8 なしの利用者にとってのみ有用です — SSG レンダリングがユーザーのページを動かすために V8 を必要とするため、V8 なしの `zfb` ビルドステップはまだありません。このフィーチャーは、将来の出荷経路（Tauri サイドカー、スタンドアロン SSR サーバー、`cargo install` によるデプロイ）がワークスペースを再設計せずに小さい成果物をオプトインできるよう配線されています。

## JS ベースの代替との比較

Vite、Next、Astro、SvelteKit — すべて優れたツールです。zfb の賭けは異なるものであり、あらゆる方向で優れているわけではありません。**もしフレームワークが Rust で、ユーザーのコードだけが JS / TS だったら？** というものです。

これは処理の置き場所を変えます。ネイティブ Rolldown は引き続き JavaScript のモジュールグラフを走査し、npm SDK にも依存関係があります。Rust はネイティブの調整層と自身のメモリ／並行性に関する言語上の保証を提供し、JavaScript の実行は V8 ホストが担当します。エラーには `anyhow` を通じて一貫したコンテキストの連鎖が付きます。

コストは、フレームワークのネイティブ言語における小さめのプラグインエコシステムと、コントリビューターにとっての長めの初回ビルドです。zfb は両方を意図的に支払います。設計の狙いが、ビルドに邪魔されたくないユーザーだからです。

膨大なプラグインエコシステムと、何年もかけて磨かれたホットリロードの体験を備えた JS ネイティブのフレームワークが欲しいなら、そうしたツールは存在します。フレームワークが速いバイナリの中に消え去り、リビルドが何も起きなかったかのように感じられることを望むなら、それこそが zfb の目的です。
