zfb は、それぞれが 1 つの役割を担う小さな Rust クレート群として作られています。このページは、
「どのクレートが何を、どの順序で行うか」というレベルでパイプライン全体をめぐるツアーです。
個々の部品に深入りすることなくメンタルマップを得るのに十分な内容です。

## クレート、順番に

1. **CLI** — `crates/zfb`。コマンドライン引数をパースし、`zfb.config.{ts,json}` をロードし、`dev`・`build`・`preview` のいずれかのコマンドにディスパッチします。
2. **Router** — `crates/zfb-router`。`pages/` をスキャンしてルートテーブルを生成します。[ルーティング](./routing.mdx) を参照してください。
3. **Watcher** — `crates/zfb-watcher`。dev モード専用。デフォルトでは `pages/`・`content/`・`components/`・`layouts/`・`styles/`・`data/`・`src/`、そして設定ファイルを監視し、加えて設定された各コレクションの path がデフォルトのルートの外にある場合と、絶対パスの `extraWatchPaths` がある場合はそれも監視します。`public/` は意図的に監視 **しません** — 静的アセットはリクエスト時にディスクからライブで配信されるため、リビルドを必要とせず、ウォッチャーにもブートにも流れ込みません（[静的アセット](./static-assets.mdx#dev-prod-の一致) を参照）。変更イベントのストリームを発行します。
4. **Dependency graph** — `crates/zfb-graph`。ページとソースの依存関係を追跡します。ウォッチャーが変更を報告すると、グラフは「どのページをリビルドする必要があるか」という 1 つの問いに答えます。
5. **Build orchestrator** — `crates/zfb-build`。ページ単位の作業を調整し、個々の生成テキストファイルに `atomic_write_string` を使います。出力ツリー全体をトランザクションとして置き換える仕組みではありません。
6. **バンドルとレンダリング** — `crates/zfb-build` がページとコンパイル済み MDX をステージし、ネイティブ Rolldown（`crates/zfb-bundler`）で TSX/JSX の変換とバンドルを行います。生成された `createPageRouter` アプリケーションは `default { fetch }` を公開し、組み込み V8 ホストがそれを実行して zudo-react がページを HTML にレンダリングします。コレクションモジュールはコンテンツブリッジ経由で `entry.Content` として公開されます（[MDX コンポーネント](./mdx-components.mdx)を参照）。`crates/zfb-render` には引き続きホストのインターフェースとライブラリ向けの SWC 変換 API があり、SWC はソース解析にも使われますが、`RenderHost::call_default` が CLI ビルド共通の実行経路というわけではありません。
7. **CSS pipeline** — `crates/zfb-css`。zudo-wind のユーティリティをコンパイルし、必要に応じて lightningcss で手書き CSS を処理します。[スタイリング](./styling.mdx)を参照してください。
8. **Islands pipeline** — `crates/zfb-islands`。`"use client"` コンポーネントをスキャンし、それらすべてをネイティブの Rolldown バンドラー経由で単一の共有 ESM モジュールにバンドルします。加えて、動的 `import()` 呼び出しのためのコード分割チャンクも生成します。[Islands](./islands.mdx) を参照してください。同じクレートが `.client.*` のクライアントスクリプトのエントリを検出し、それぞれを独立にバンドルします（`crates/zfb-islands/src/client_scripts.rs` の `discover_client_scripts` と `build_production_client_scripts`）。[クライアントスクリプト](../guides/client-scripts.mdx) を参照してください。
9. **Server** — `crates/zfb-server`。CLI の開発用サーバーを提供します。axum ベースの HTTP サーバーがページキャッシュと静的ファイルを配信し、ブラウザーのリロードイベントには WebSocket `/__zfb/reload/ws` を使います（ツール向け SSE `/__zfb/reload` も残っています）。イベント種別は [dev モードのライフサイクル](./dev-mode-lifecycle.mdx)を参照してください。Rust ホストは別途[埋め込み API](../guides/embed-as-library.mdx)を使えますが、最小のビルダーは CLI のコンパイラ、監視、プラグイン、JS SSR パイプラインを起動しません。

## 本番: `zfb build`

`zfb build` はパイプラインを一度だけ実行し、完全なサイトを `outDir` に書き出します。

CLI → Router → Graph → Build orchestrator → Renderer → CSS pipeline → Islands pipeline。

ウォッチャーと dev サーバーは関与しません。プリレンダリング対象のすべてのページがレンダリングされ、すべての CSS
バンドルが生成され、すべての島がバンドルされ、その結果が `dist/`（または `outDir`
が指す場所）に配置されます。コマンドは `preBuild` より前に出力ディレクトリを空にしてから、新しい出力を書き込みます。中断や失敗で出力が不完全になることはあり、個々のアトミック書き込みは以前の完全な `dist/` を保持しません。ホストのデプロイ機構を使い、正常終了したビルドだけを公開してください。`prerender = false` の
ルートについては、zfb がそれらのルートに絞った 2 回目のバンドルを実行し、アダプタが静的 HTML の代わりに
そのバンドルを Worker モジュールとして包みます。その出力が
どう構成されるかは [Worker 上の SSR（アダプターモード）](./ssr-on-a-worker.mdx) を
参照してください。

## 開発: `zfb dev`

`zfb dev` は `zfb build` と同じパイプラインを長命のループとして実行し、加えてウォッチャーと
サーバーを動かします。

CLI → Router → Watcher → Build orchestrator → Renderer → CSS pipeline → Islands pipeline → Server。

ウォッチャーが変更を報告すると、依存グラフが影響を受けるページを選び、オーケストレーターは
それらだけをリビルドし、サーバーは WebSocket チャネル経由でリロードイベントをブロードキャストします。
ブラウザは自動的に再接続してリロードします。

## プレビュー: `zfb preview`

`zfb preview` には 2 つのモードがあります。デフォルト（adapter 未設定、または `adapter: "none"`）
では、既存の `dist/` ディレクトリを `:4321` で静的ファイルとして配信します。レンダリングも
ウォッチングもリビルドもありません。デプロイ前に本番ビルドをローカルで確認できるように
存在しています。プロジェクトが Cloudflare アダプタ（`adapter: "@takazudo/zfb-adapter-cloudflare"`）
を設定している場合は、代わりに `wrangler dev` に処理を委譲します。これにより出力された
`dist/_worker.js` がローカルで実行され、`prerender = false` のルートは静的ファイルとしてではなく、
実際の Worker ランタイムを通してレンダリングされます。

## なぜ分割するのか

クレートの境界は偶然ではありません。ルーティングはレンダリングとは別の問題であり、レンダリングは
ウォッチングとは別、ウォッチングは配信とは別です。これらを分割することで、各クレートは単体で
テストできるくらい小さく保たれ、dev ループは本番経路に触れることなく最適化（インクリメンタル
リビルド、ページキャッシュ、部分的な CSS 抽出）を差し込めます。より踏み込んだ理由付けは
[ビルドエンジン](../architecture/build-engine.mdx) にあります。
