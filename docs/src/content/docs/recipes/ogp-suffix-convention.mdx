## When to reach for this

You have content-heavy pages — blog posts, recipes, docs — and you want Open Graph metadata (title, description, image) to live in a sibling file rather than crammed into the page module. This keeps the page module focused on rendering, lets OGP copy diverge from the article copy without surgery, and gives you one place to look when an OG card renders wrong.

## The convention

For every `pages/<slug>.tsx` (or `pages/blog/[slug].tsx`) that wants OGP metadata, add a sibling `pages/<slug>__og.tsx` that exports an `og` object. The page imports the sibling and renders the metadata into its `<head>`:

```tsx title="pages/blog/hello-world.tsx"
import og from "./hello-world__og";

export default function Page() {
  return (
    <html lang="en">
      <head>
        <meta charSet="utf-8" />
        <title>Hello, world</title>
        <meta property="og:title" content={og.title} />
        <meta property="og:description" content={og.description} />
        <meta property="og:image" content={og.image} />
        <meta name="twitter:card" content="summary_large_image" />
      </head>
      <body>{/* article body */}</body>
    </html>
  );
}
```

```tsx title="pages/blog/hello-world__og.tsx"
// product-specific: __og siblings are NOT routes — the suffix is a project
// convention that the consuming page imports. Don't add a default export.
const og = {
  title: "Hello, world",
  description: "The first post on the blog. A nervous wave.",
  image: "https://example.com/og/hello-world.png",
};

export default og;
```

The `__og` file does not need to be a route — it has no default export of its own, only a named export consumed by the article. zfb's page-resolution treats it as a regular module under the project root.

## Why a filename suffix instead of a frontmatter field

zfb pages don't have a single frontmatter contract — TSX pages export `frontmatter` literals (see [Non-HTML pages](/docs/concepts/non-html-pages)) and MDX pages have YAML frontmatter. Putting OGP fields in either place means the metadata is forever next to the page's own title/description and has to diverge gracefully when product wants different copy on Twitter than on the page.

A sibling module sidesteps that: the page exports what the page is, the sibling exports what social previews say.

## Sharing OG card images

If multiple posts share a generic OG image, point them at the same URL — Preact does no de-duplication, but the OG image is fetched by social-card crawlers from the URL, so a single hosted asset is fine.

If you want **dynamic** OG images (per-post PNG), pair this recipe with the [sitemap recipe](/docs/recipes/sitemap-from-ctx-routes)'s pattern: a `postBuild` plugin that iterates `ctx.routes`, generates a PNG per route via your image library of choice, and writes it under `dist/og/<slug>.png`. The `__og` sibling then references that path.

## Listing all OG cards

In a `postBuild` plugin, scanning the route manifest for `__og` siblings doesn't work directly — they aren't routes. Instead, scan the source tree for `__og.tsx` files in `preBuild` and stash the list in a virtual module if you need it elsewhere; see the [`virtual:metadata-db` recipe](/docs/recipes/virtual-metadata-db) for the pattern.
