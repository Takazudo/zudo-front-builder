zfb's Markdown story lives in the `zfb-content` Rust crate: parse the
file, highlight code blocks server-side with syntect, and hand each entry
back as both a raw `body` string and a ready-to-render `Content`
component. This page documents what is configurable from the
content-consumer side.

## The pipeline today

When zfb reads a Markdown file from a content collection it does three
things:

1. Splits front matter using a `gray-matter`-style `---` separator.
2. Parses the front matter into `entry.data` against the schema you
   declared in `zfb.config`.
3. Compiles the body as CommonMark plus the GitHub-Flavored Markdown
   extensions (tables, task lists, strikethrough, autolinks) into a JSX
   module. The raw markdown source is preserved on `entry.body`; the
   compiled JSX is reachable via `entry.Content`.

That pair is what your TSX page receives. There is no per-page hook to
intercept the parse — extension happens at the engine level via the
`MdastVisitor` / `HastVisitor` traits described below.

## Rendering Markdown in a page

The standard pattern is to receive a content entry through `paths()` and
render its `Content` component:

```tsx
import { getCollection } from "zfb/content";

export async function paths() {
  const posts = await getCollection("blog");
  return posts.map((post) => ({
    params: { slug: post.slug },
    props: { post },
  }));
}

export default function PostPage({ post }) {
  return (
    <article className="prose">
      <post.Content />
    </article>
  );
}
```

`entry.Content` is the JSX component zfb compiles from your Markdown — it
renders MDX-aware output including syntect-highlighted code blocks and
any custom directives you have registered. If you only need the raw
markdown source (for example, to compute a summary or feed an RSS
generator), reach for `entry.body` instead.

## What is customisable

- **Front-matter schema** — every collection can declare its own field
  types in `zfb.config`. Schema mismatches fail the build.
- **GFM features** — enabled by default; tables, task lists,
  strikethrough, and autolinks are all on.
- **HTML wrapping** — fully under your control. `entry.Content` is a
  JSX component; wrap, slot, and style it however you like.
- **`.mdx` entries** — content collections accept `.md`, `.mdx`, and
  `.tsx` files side by side. MDX entries compile to JSX modules; see
  [MDX Components](/concepts/mdx-components).
- **Custom directives** — `:::name` (container), `::name[label]`
  (leaf), and `:name[label]` (text) directive shapes are supported
  by the engine and register against a runtime
  [`DirectiveRegistry`](/concepts/custom-directives). The six built-in
  admonitions (`:::note`, `:::tip`, `:::info`, `:::warning`,
  `:::danger`, `:::details`) ship through that registry; your project
  or framework adds its own directives the same way.
- **Syntax highlighting** — `SyntectPlugin` highlights fenced code
  blocks server-side at build time. See
  [Syntax Highlighting](/guides/syntax-highlighting) for theme
  customisation options.
- **Engine-side plugin chain** — `zfb-content` exposes
  `MdastVisitor` and `HastVisitor` traits and a default plugin chain
  via `Pipeline::with_defaults()`. New rewrites (custom code-block
  treatment, link normalisation, heading anchors, etc.) ship as Rust
  visitors. See
  [Extending the Markdown Pipeline](/guides/extending-the-markdown-pipeline)
  for the engine-extender path.

## Extension points

The `plugins: []` field in `zfb.config` is the build-orchestration
plugin system. Each registered plugin exposes three optional hooks —
`preBuild`, `postBuild`, and `devMiddleware` — for tasks like emitting
extra files alongside the build, running post-build verification, or
adding routes to the dev server. Plugins do **not** participate in
Markdown rendering: the parse and visitor chain run inside the Rust
engine and never call back into npm-installed plugins.

Markdown-pipeline customisation lives in-tree as `MdastVisitor` /
`HastVisitor` implementations on the engine side. Wire them either into
`Pipeline::with_defaults()` for site-wide behaviour or into a
project-specific pipeline for per-context overrides. If your site needs
an engine-level rewrite that does not fit the directive registry, write
a visitor and add it in-tree — the
[engine extension guide](/guides/extending-the-markdown-pipeline)
walks through the surface.

<Tip>

  When in doubt, render the body and style it. Most "I want to customize
  Markdown" requests turn out to be styling questions that CSS solves.

</Tip>

## Table of Contents (TOC)

zfb ships a `remark-toc`-equivalent as an opt-in hast visitor. When enabled,
it scans the rendered heading tree for a heading whose text matches a
configured anchor string (default `"TOC"`, case-insensitive) and inserts a
nested `<ul>/<li>` list of the **subsequent** headings as the next sibling.

Because the visitor runs in the **hast phase after `HeadingLinksPlugin`**, it
reads the final deduplicated `id` attributes that plugin already placed on
every `<h2>`–`<h6>`. Links in the generated list are guaranteed to match the
rendered anchor IDs — including documents that repeat the same heading text
(e.g. multiple "Overview" sections), where `HeadingLinksPlugin` produces
`overview`, `overview-1`, `overview-2`, …

To enable, add a `toc` key inside the `markdown` block in `zfb.config.ts`:

```ts
import { defineConfig } from "zfb/config";

export default defineConfig({
  markdown: {
    toc: {
      heading: "TOC",   // optional; default "TOC" (case-insensitive)
      maxDepth: 2,       // optional; default 2 (h2 + h3)
## External links

The `markdown.externalLinks` option automatically adds `target` and `rel`
attributes to links whose destination is outside your site.

```ts
// zfb.config.ts
export default defineConfig({
  markdown: {
    externalLinks: {
      target: "_blank",
      rel: ["noopener", "noreferrer"],
    },
  },
});
```

Then place a heading with that text anywhere in your Markdown body:

```md
## TOC

## Introduction

### Getting started

## Advanced usage
```

zfb inserts the TOC list immediately after the `## TOC` heading:

```html
<h2 id="toc">TOC …</h2>
<ul>
  <li><a href="#introduction">Introduction</a>
    <ul>
      <li><a href="#getting-started">Getting started</a></li>
    </ul>
  </li>
  <li><a href="#advanced-usage">Advanced usage</a></li>
</ul>
<h2 id="introduction">Introduction …</h2>
…
```

### Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `heading` | `string` | `"TOC"` | Heading text that triggers insertion (case-insensitive). |
| `maxDepth` | `number` | `2` | Levels to include from `<h2>`. `1` → h2 only, `2` → h2+h3, `3` → h2–h4, max `5`. |

Omitting the `toc` key entirely leaves the build byte-for-byte identical —
no visitor is registered and no output changes.
An href is treated as **external** when it is an absolute `http:` or
`https:` URL and its origin differs from your site's origin (determined
by the top-level `site` config option, once configured). When `site` is
absent, any absolute HTTP/HTTPS URL is treated as external.

`mailto:`, `tel:`, and other non-HTTP(S) schemes are always left
unchanged. Relative paths (`/internal/`, `./page.mdx`, `#anchor`) are
always internal.

**Merging with existing `rel`** — if an `<a>` element already carries a
`rel` attribute, the configured tokens are merged in (deduplicated,
case-insensitive). Existing tokens appear first, so author intent is
preserved.

**Omitting `externalLinks`** keeps the rendered output byte-for-byte
identical to the pre-feature behaviour — no extra attributes are emitted.

<Note>

  Same-origin classification depends on the `site` config option
  (introduced separately). Until `site` is configured, every absolute
  HTTP/HTTPS URL is treated as external.

</Note>
