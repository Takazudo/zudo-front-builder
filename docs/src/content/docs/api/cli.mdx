## Overview

The `zfb` binary exposes seven top-level commands for the full development lifecycle:

```
zfb new    — scaffold a new project from a template
zfb dev    — local development server with live reload
zfb build  — production build
zfb css    — compile a CSS entrypoint without building the site
zfb wind   — inspect utility candidates and source usage
zfb preview — serve a previously built site
zfb check  — typecheck and validate content-collection schemas
```

Run `zfb --help` or `zfb <command> --help` to see the generated help text directly.

## `zfb new`

Scaffold a new project from a built-in template.

```sh
zfb new <name> [--template <template>]
```

### Arguments

| Name | Type | Required | Description |
|---|---|---|---|
| `name` | positional | yes | Name of the new project. Used as the destination directory. |
| `--template` | string | no | Template to scaffold from. Default: `basic-blog`. |

### Templates

v0 ships two templates, both baked into the binary at compile time from `crates/zfb/templates/`:

- `basic-blog` (default) — full-featured blog scaffold with `package.json`; `zfb new` runs `pnpm install` for it automatically when pnpm is on `PATH`.
- `node-free` — ships no `package.json` and skips the post-scaffold `pnpm install` step entirely, for projects run with no Node/pnpm on `PATH`. See [Markdown and HTML Pages](../concepts/md-html-pages.mdx) for the `.md`/`.html` page-authoring surface, and [Install without Node](../install/node-free.mdx) for installing the `zfb` binary itself without Node.

### Example

```sh
zfb new my-site
zfb new my-site --template basic-blog
zfb new my-site --template node-free
```

## `zfb dev`

Start the local development server with live reload.

```sh
zfb dev [--port <port>] [--host [<host>]]
        [--scratch-dir <path>] [--define <KEY=EXPR>]...
```

### Flags

| Flag | Type | Default | Description |
|---|---|---|---|
| `--port` | u16 | `3000`* | Port to bind the dev server to. |
| `--host` | string | `localhost`* | Host interface to bind to. Bare `--host` (no value) is a shortcut for `0.0.0.0`. |
| `--scratch-dir` | path | `ZFB_SCRATCH_DIR` / `.zfb-build` | Give this dev server its own directory for zfb's generated artifacts. Under a scratch dir, dev ignores the prebuilt output directory. See [Scratch dirs](#scratch-dirs). |
| `--define` | `KEY=EXPR`, repeatable | none | Add an esbuild define for this invocation, overriding `bundle.define` per key. See [Per-invocation defines](#per-invocation-defines). |

\* Falls back through: CLI flag → `port`/`host` in `zfb.config.json` → built-in default.

### Lazy rendering

The dev server defaults to **lazy rendering**: changed routes are marked stale and re-rendered on the first request rather than immediately on every file change. This keeps the inner loop fast for large sites.

To restore the pre-lazy behavior and re-render every affected route eagerly on each file change, set `ZFB_DEV_EAGER=1`.

### Environment variables

| Variable | Values | Description |
|---|---|---|
| `ZFB_DEV_EAGER` | `1` | Disable lazy dev rendering. Re-renders every affected route eagerly on each file change. |
| `ZFB_LAZY_DEV_RENDER` | `0` or `1` | Precise override of the lazy dev-render switch. `1` forces lazy; `0` forces eager. Takes precedence over `ZFB_DEV_EAGER` when both are set. |
| `ZFB_DEV_BOOT_LAZY` | `1` | Legacy seed-based fast boot: use prebuilt `dist/` and render routes on their first request. Without a servable seed this explicit mode falls back to eager startup. Requires lazy rendering. Omit the variable for the default seedless lazy startup. |
| `ZFB_DEV_BOOT_LAZY` | `cold` (default) | Seedless lazy startup: prepare the renderer and required assets, then render each route on request. Unrequested pages do not delay early file edits. Before the renderer is available, routes without a fallback return the dev 404 with live reload; a prebuilt `dist/` can still supply a fallback. Each process uses a fresh HTML output directory, so previous-session dev HTML is never served. Set `0` or `false` for eager all-page startup, or `ZFB_DEV_EAGER=1` to disable lazy rendering entirely. |
| `ZFB_DEV_DEFER_BUNDLE` | `0` | Opt out of the boot-lazy bundle deferral (either variant): build the renderer before bind (no SSR-only 404 window) at the cost of a slower first-accept. On by default when boot-lazy is active. |
| `ZFB_DEV_TIMING` | `1` or `true` | Emit per-tick timing lines for dev-mode profiling. Off by default. |
| `ZFB_KEEP_SHADOW_SESSION` | `1` or `true` | Keep the dev server's persistent shadow tempdir on disk instead of deleting it when the process exits — for inspecting the generated shadow tree (injected-route shims, resolved `node_modules` layout). The kept path is logged once at shutdown. A later `zfb dev` boot with the flag unset reaps a previously-kept dir once it passes an internal age floor, so keep the flag exported for the whole debugging session, not just the boot that created the dir. See `ZFB_KEEP_BUILD_SHADOW` under [`zfb build`](#zfb-build) for the production-build counterpart — a different tempdir class with no such reap. Off by default. |

### Example

```sh
# Default — binds localhost:3000
zfb dev

# Custom port
zfb dev --port 8080

# Expose to the LAN (0.0.0.0)
zfb dev --host

# Explicit host
zfb dev --host 192.168.1.10 --port 4321
```

## `zfb build`

Build the project for production. Emits static HTML (and, when an adapter is configured, a server entry) to the output directory.

```sh
zfb build [--outdir <dir>] [--minify-html | --no-minify-html]
          [--strict-broken | --no-strict-broken]
          [--emit-render-artifacts | --no-emit-render-artifacts]
          [--scratch-dir <path>] [--define <KEY=EXPR>]...
```

### Flags

| Flag | Type | Default | Description |
|---|---|---|---|
| `--outdir` | path | config / `dist` | Output directory for the production build. Overrides config `outDir`; when both are absent, uses `dist`. |
| `--minify-html` | boolean flag | config/default | Enable production HTML minification for this build. Overrides `minifyHtml: false` or an omitted config value. |
| `--no-minify-html` | boolean flag | config/default | Disable production HTML minification for this build. Overrides `minifyHtml: true` from config or presets. |
| `--strict-broken` | boolean flag | config/default | Fail this build (non-zero exit) when markdown link validation finds a broken link. Overrides `strictBrokenLinks: false` or an omitted config value. On a project with no `linkValidation` config at all, it force-enables link validation with its defaults rather than doing nothing. |
| `--no-strict-broken` | boolean flag | config/default | Do not fail this build on broken links. Overrides `strictBrokenLinks: true` from config or presets. Disables the top-level strict overlay only — a `linkValidation` block that explicitly sets `failOnBroken: true` stays in effect. |
| `--emit-render-artifacts` | boolean flag | config/default | Write a JSON render artifact under `__zfb/render/` for every markdown/MDX-backed HTML route whose page renders exactly one top-level content region. Overrides `emitRenderArtifacts: false` or an omitted config value. |
| `--no-emit-render-artifacts` | boolean flag | config/default | Do not write render artifacts for this build. Overrides `emitRenderArtifacts: true` from config or presets. |
| `--scratch-dir` | path | `ZFB_SCRATCH_DIR` / `.zfb-build` | Give this build its own directory for zfb's generated artifacts. The output directory is still shared. See [Scratch dirs](#scratch-dirs). |
| `--define` | `KEY=EXPR`, repeatable | none | Add an esbuild define for this build, overriding `bundle.define` per key. See [Per-invocation defines](#per-invocation-defines). |

HTML minification is off by default unless `minifyHtml: true` is set or `--minify-html` is passed. It runs inside zfb's Rust post-processing pipeline and does not spawn a Node.js minifier subprocess. The first version is conservative: rendered HTML pages are candidates, source `.html` passthrough pages remain verbatim, and non-HTML outputs are skipped.

Strict broken-link gating is likewise off by default. `--strict-broken` and `--no-strict-broken` conflict — passing both is an error — and either one overrides the `strictBrokenLinks` config field, which in turn overrides the `false` default. Both flags affect `zfb build` only; `zfb dev` never sees the strict overlay and keeps whatever link-validation behavior your own `linkValidation` config gives it. See [Link validation — Strict mode](../markdown-features/link-validation.mdx) for the full behavior, including how this differs from `resolveMarkdownLinks.onBrokenLinks`.

Render-artifact export is likewise off by default. `--emit-render-artifacts` and `--no-emit-render-artifacts` conflict — passing both is an error — and either one overrides the `emitRenderArtifacts` config field, which in turn overrides the `false` default. Both flags affect `zfb build` only; `zfb dev` never writes render artifacts. See [Render artifacts](../concepts/render-artifacts.mdx) for the full JSON contract, the region rule, and which routes participate.

### Environment variables

| Variable | Values | Description |
|---|---|---|
| `ZFB_KEEP_BUILD_SHADOW` | `1` or `true` | Leave this build's shadow tempdirs on disk after the process exits — on a failing build too — instead of deleting them, for inspecting the generated shadow tree (injected-route shims, resolved `node_modules` layout) without an external polling harness. Covers exactly three tempdir classes: the bundler's shadow root, its exact-`node_modules` isolation root, and the package-routes overlay (only allocated when the project registers package routes). Each kept path is printed once to stderr, naming its role. Other `zfb build` temp producers (config loading, islands/esbuild, CSS, plugin resolution) are **not** covered. A kept dir is never auto-reaped — cleaning it up is your responsibility (contrast `ZFB_KEEP_SHADOW_SESSION` under [`zfb dev`](#zfb-dev), which a later boot eventually reaps). `zfb dev` is entirely unaffected by this flag, even where it happens to share an allocator with `zfb build`. Off by default. |

### Example

```sh
zfb build
zfb build --outdir public
zfb build --minify-html
zfb build --no-minify-html
zfb build --strict-broken
zfb build --no-strict-broken
zfb build --emit-render-artifacts
zfb build --no-emit-render-artifacts
zfb build --scratch-dir .zfb-build/ci --define __ORIGIN__='"https://www.example.com"'
```

## `zfb css`

Compile one CSS entrypoint with zudo-wind and zfb's authored-CSS processing, without discovering routes, rendering pages, bundling application code, or starting the plugin host.

```sh
zfb css --input <entry.css> --output <compiled.css>
        [--project-root <dir>]
        [--source <glob> ...]
        [--no-auto-source]
        [--code-highlight-mode <class|inline>]
        [--no-default-highlight-styles]
```

### Flags

| Flag | Type | Default | Description |
|---|---|---|---|
| `--input` | path | required | CSS entrypoint. Relative paths resolve from the current working directory. |
| `--output` | path | required | Destination CSS file. Relative paths resolve from the current working directory. It must not resolve to the same file as the input. |
| `--project-root` | path | current working directory | Root used to load `zfb.config` and resolve `--source` globs. A relative path itself resolves from the current working directory. |
| `--source` | glob, repeatable | none | Explicit zudo-wind candidate source, resolved from `--project-root`. Each glob must match at least one file. Matches under the configured `outDir`, at the `--output` path, or under zfb scratch roots are excluded. A declaration whose matches are all excluded fails with a `ZW010` error; a partially excluded declaration reports a `ZW010` warning and keeps its accepted matches. Caller order is preserved; exact duplicates use their first occurrence. The standalone command accepts `.html` and `.mjs` sources as well as the build/dev source extensions. |
| `--no-auto-source` | boolean flag | `false` | Omit the command's conventional source-plan roots. Explicit `--source` values and the configured syntax-highlight role classes remain active. |
| `--code-highlight-mode` | `class` or `inline` | config/default | Override `codeHighlight.mode` when deciding whether to include zfb's framework syntax-highlight CSS. Other `codeHighlight` settings, including `classPrefix` and `roleClasses`, still come from config. |
| `--no-default-highlight-styles` | boolean flag | `false` | Suppress zfb's built-in class-mode `zfb-hi.css` stylesheet. This also overrides `codeHighlight.defaultStylesheet: true`. |

### Example

A project config supplies the utility values, and a source glob finds candidates in the project tree. This example also imports a CSS subpath exposed by an installed package's `exports` map (`@example/design-system`):

```ts
import { defineConfig } from "zfb/config";

export default defineConfig({
  wind: {
    tokens: {
      spacingUnit: "0.25rem",
      colors: {
        brand: "oklch(0.65 0.2 250)",
      },
      radii: {
        card: "0.5rem",
      },
    },
    authoredClasses: {
      example: true,
    },
    manifests: {
      "design-system": { path: "@example/design-system/wind.json" },
    },
  },
});
```

The installed package exposes `./base.css` and `./wind.json`. Its `dist/wind.json` contains:

```json
{
  "schemaVersion": 1,
  "specVersion": 1,
  "producer": "design-system",
  "candidates": ["bg-brand", "p-4", "rounded-card"]
}
```

Those package candidates use tokens configured by the project.

```tsx
export function ExampleCard() {
  return <article className="example flex p-4 bg-brand rounded-card">Example</article>;
}
```

The entry uses only authored CSS and `@import`; it has no Tailwind directives:

```css
@import "@example/design-system/base.css";

.example {
  border: 1px solid var(--zw-color-brand);
}
```

Run the command from the project root. The glob scans this project's source files; the configured manifest adds the design-system package's candidates:

```sh
zfb css \
  --input src/styles/entry.css \
  --output dist/app.css \
  --project-root . \
  --source 'src/**/*.{tsx,ts,jsx,js}' \
  --no-auto-source
```

The `@import` paths resolve as authored CSS. zudo-wind gets utility values from `zfb.config.ts`, local candidates from `--source`, and package candidates from `wind.manifests`.

### Notes

- **Sources follow the configured source plan.** `--source` supplies explicit inputs; `--no-auto-source` omits the command's conventional roots while preserving explicit inputs and the classes configured in `codeHighlight.roleClasses`. Conventional discovery skips `node_modules`, `dist`, `build`, `target`, `.git`, `.cache`, `.turbo`, `.next`, `.vercel`, `.zfb-build`, and `.zfb`; declare a package source root explicitly with `--source`, or publish its candidates through `wind.manifests`. The consuming project's configured `outDir`, the `--output` path, and zfb scratch roots stay excluded. If every match from an explicit `--source` is under one of those output roots, `zfb css` reports a `ZW010` error; if only some matches are excluded, it reports a `ZW010` warning and scans the accepted files. For example, `--source 'dist/**/*.tsx'` reports an error when `dist` is the configured `outDir`. Build and dev scan `.tsx`, `.ts`, `.jsx`, `.js`, `.mdx`, and `.md` by default; standalone explicit inputs can also use `.html` and `.mjs`. See [Sources and candidates](../zudo-wind/sources-and-candidates.mdx) for source-plan details.
- **Output is deterministic and replaced atomically.** The same entry, config, and ordered source set produce timestamp-, sourcemap-, and temporary-path-free bytes. A successful compile atomically replaces `--output`; a failed compile leaves any existing output untouched.
- **This is a global-CSS-only command.** CSS Modules are not discovered or processed. Package-attributed `url()` assets that would require companion files are rejected in v1 with a non-zero exit instead of being emitted beside the stylesheet.
- **Config use is narrow.** When present, `zfb.config.json` or `zfb.config.ts` supplies wind tokens, reset, sources, and syntax-highlighting settings such as `classPrefix` and `roleClasses`; CLI highlight flags override the corresponding mode/stylesheet choice. `wind: false` disables wind generation while authored CSS and highlight processing continue. An omitted key uses the empty enabled wind config.
- **V1 wind output is not minified.** Generated wind CSS uses the fixed printer described in [Cascade and reset](../zudo-wind/cascade-and-reset.mdx).

## `zfb wind`

Use `zfb wind explain` to inspect how a candidate is parsed, resolved, and emitted. The explanation includes its catalog entry, token bindings, declarations, selector, conditions, and ordering data.

Use `zfb wind audit` to review ordinary class-position names, missing or unused utilities, dynamic class fragments, and property conflicts within a single class-list literal. An exact `authoredClasses` match and `group`/`peer` markers are excluded. With `wind: false`, explain reports generation disabled and audit returns an empty candidate report.

```sh
zfb wind audit [--project-root <path>] [--fail-on error|warning]
```

A complete audit exits with status 0 by default, including when it reports error-severity findings; in that case stderr suggests `--fail-on error`. Invalid configuration or a source scan failure exits nonzero. Use `--fail-on error` to exit nonzero when the report contains error-severity diagnostics, or `--fail-on warning` to include warnings. `auditInfo` findings never trigger either threshold. With `wind: false`, the generation-disabled report exits with status 0.

These commands inspect the configured project; they do not execute application code to discover class candidates. See [Diagnostics and tools](../zudo-wind/diagnostics-and-tools.mdx) for outcome and origin details.

## `zfb preview`

Serve a previously built site locally. Run `zfb build` first.

```sh
zfb preview [--port <port>] [--host [<host>]] [--outdir <dir>]
            [--scratch-dir <path>]
```

In static mode (no adapter, or `adapter: "none"`), `zfb preview` also runs the SAME two request-time layers `zfb dev` does, ahead of the plain static-file waterfall: a plugin's `previewMiddleware` registrations, then `public/_redirects` (see [Static Assets — `_redirects`](../concepts/static-assets.mdx#_redirects-—-redirect-rewrite-rules)). A plugin claiming a URL always wins over a `_redirects` rule for that same URL.

Only `GET`/`HEAD` requests reach the `_redirects` matcher — mirrors real Workers Static Assets, which only ever probes the asset layer (and therefore `_redirects`) for those two methods. Any other method either reaches a plugin handler (which accepts every method) or 405s; a rule that would otherwise fire for `GET /old-page` never fires for `POST /old-page`.

<Note title="_redirects and a custom `base`">

Static preview serves whatever `zfb build` emitted under the selected output directory, and does not know about your project's `base` prefix — it has no prefix-stripping layer of its own. So `_redirects` rule *sources* are matched against the **full request path**, exactly as written in the file — they are never rewritten to add or strip a `base` prefix. `zfb dev` mirrors that matching shape even though its router is mounted under `base`. If `zfb.config.ts` sets `base: "/pj/site/"`, a rule meant to redirect `/pj/site/old-page` must be written with the prefix included (`/pj/site/old-page /pj/site/new-page 301`), not as `/old-page /new-page 301`.

</Note>

When `zfb.config.json`'s `adapter` field names a supported adapter (e.g. `@takazudo/zfb-adapter-cloudflare`), `zfb preview` hands off to `wrangler dev` instead of zfb's own static server — the output directory selected from `--outdir` or config `outDir` then only pre-checks that the directory exists, since wrangler's own config controls what it actually serves. See [SSR and Cloudflare Bindings](../guides/ssr-and-cloudflare-bindings.mdx).

Adapter preview runs a pre-flight `pnpm exec wrangler --version` check before handing off, treating zfb's tested baseline as the **minimum supported version**: an older wrangler aborts with upgrade guidance, while an equal or newer one proceeds (newer versions print an info line, or a warning on an untested major). Set `ZFB_SKIP_WRANGLER_VERSION_CHECK=1` only as a temporary escape hatch (e.g. if wrangler's version output format changes).

<Caution title="Adapter mode: zfb serves nothing">

Under adapter mode, `wrangler dev` serves the whole site — zfb never boots its own router, and no plugin host is spawned to check for `previewMiddleware` at all. `_redirects` still works there, but it's `wrangler`/Workers Static Assets honouring the file natively, not zfb's `_redirects` engine. A `previewMiddleware` registration has no wrangler equivalent and simply does not run under adapter-mode preview — if your project has plugins configured, `zfb preview` prints a one-time warning to that effect before handing off.

</Caution>

### Stopping an adapter-mode preview

In an interactive terminal, zfb hands the terminal to `wrangler dev`, so Wrangler's hotkeys and Ctrl+C work as usual. When zfb receives SIGINT, SIGTERM, or SIGHUP, it forwards that signal to the entire `wrangler dev` process tree it started (pnpm → node → wrangler → workerd), which runs in its own process group. zfb waits up to 5 seconds for the tree to stop, then force-kills anything still running. This frees the preview `--port`.

After a signal, zfb exits without an error banner using `128 + signal`: 130 for SIGINT, 143 for SIGTERM, or 129 for SIGHUP. If `wrangler dev` fails on its own, zfb instead reports `wrangler dev exited with status …` and exits with status 1.

SIGKILL sent to zfb cannot be intercepted, so zfb cannot clean up the process tree in that case. A signal sent only to an outer wrapper that does not forward it, such as the PID of `pnpm exec zfb preview …`, never reaches zfb; scripts should stop the zfb process itself. Process-tree cleanup is not yet implemented on Windows.

### Flags

| Flag | Type | Default | Description |
|---|---|---|---|
| `--port` | u16 | `4321`* | Port to bind the preview server to. |
| `--host` | string | `localhost`* | Host interface to bind to. Bare `--host` (no value) is a shortcut for `0.0.0.0`. |
| `--outdir` | path | config / `dist` | Directory to serve the built artifacts from. Overrides config `outDir`; when both are absent, uses `dist`. |
| `--scratch-dir` | path | `ZFB_SCRATCH_DIR` / `.zfb-build` | Validate and lock a scratch dir for this preview. zfb writes nothing of its own there; plugins get its `plugins/` child as `ctx.scratchDir`. `--define` is not accepted, because preview bundles nothing. See [Scratch dirs](#scratch-dirs). |

\* Falls back through: CLI flag → `port`/`host` in `zfb.config.json` → built-in default.

Output-directory precedence is likewise CLI `--outdir` → config `outDir` → built-in `dist`.

### Example

```sh
zfb build && zfb preview
zfb preview --port 8080
zfb preview --host --outdir public
```

## `zfb check`

Typecheck the project and validate content-collection frontmatter against their schemas.

```sh
zfb check [--skip-tsc] [--scratch-dir <path>] [--define <KEY=EXPR>]...
```

This command runs two checks:

1. **TypeScript** — invokes `tsc --noEmit` as a subprocess. Catches type errors in `zfb.config.ts`, collection schemas, and `src/`.
2. **Collection schema validation** — validates every collection entry's frontmatter against the JSON Schema declared in each collection's `schema` field in `zfb.config.json`/`zfb.config.ts`. The build itself does not validate frontmatter, so this is the enforcement gate.

Either failure mode exits with a non-zero code.

### Flags

| Flag | Type | Default | Description |
|---|---|---|---|
| `--skip-tsc` | bool | `false` | Skip the `tsc --noEmit` subprocess. Schema validation still runs. Useful when TypeScript is not installed or for schema-only CI lanes. |
| `--scratch-dir` | path | `ZFB_SCRATCH_DIR` / `.zfb-build` | Validate and lock a scratch dir. `check` writes nothing into it; the flag exists so one argument list or one exported `ZFB_SCRATCH_DIR` works for every command. See [Scratch dirs](#scratch-dirs). |
| `--define` | `KEY=EXPR`, repeatable | none | Validated only. The value does not reach `tsc`. See [Per-invocation defines](#per-invocation-defines). |

### Example

```sh
# Full check — tsc + schema validation
zfb check

# Schema-only (skip tsc)
zfb check --skip-tsc
```

<Tip>

`zfb check` is the recommended way to validate content collections in CI. Wire it after `zfb build` to catch frontmatter violations that the build silently ignores.

</Tip>

## Scratch dirs

By default, every command writes its generated artifacts to fixed locations in the project: the bundle and dev files under `<root>/.zfb-build/`, and the dev server's dependency graph at `<root>/.zfb/graph.bin`. Two commands running at the same time in one checkout therefore share those files. A `zfb build` can overwrite the bundle a running `zfb dev` is serving, and two dev servers overwrite each other's bundle and persisted dependency graph. `--scratch-dir <PATH>` gives one invocation its own directory for these artifacts, so concurrent commands stay apart. Give **each** concurrent command its own scratch dir.

```sh
# Two dev servers and a build in one checkout, each with its own scratch dir
zfb dev --port 3000 --scratch-dir .zfb-build/dev-main
zfb dev --port 3001 --scratch-dir .zfb-build/dev-preview
zfb build --scratch-dir .zfb-build/build

# The same through the environment
ZFB_SCRATCH_DIR=.zfb-build/dev-preview zfb dev --port 3001
```

### Selecting a scratch dir

- `--scratch-dir` is accepted by `zfb dev`, `zfb build`, `zfb check`, and `zfb preview`.
- The flag wins over the `ZFB_SCRATCH_DIR` environment variable. An empty or whitespace-only `ZFB_SCRATCH_DIR` counts as unset.
- A relative path resolves against the current working directory, which is the project root. zfb creates the directory if it is missing, but only after the path passes the rules below.
- With neither the flag nor the variable, zfb uses the default `<root>/.zfb-build/` layout exactly as before. It takes no lock and creates nothing extra.

### Where to put it

The recommended location is `<root>/.zfb-build/<name>`. The scaffold templates already gitignore `.zfb-build/`, and every zfb source walker already skips it.

Inside the project, a scratch dir must sit **strictly under** `.zfb-build/`. Any other in-project location is rejected. A location outside the project, such as `/tmp/zfb-dev-main`, is allowed as long as it passes the same rules.

Each of these locations is a hard error. The message names the rule tag and the paths involved:

| Tag | Rejected location |
|---|---|
| `R1` | The project root itself, or any ancestor of it. |
| `R2` | An in-project path that is not strictly under `.zfb-build/`, including `.zfb-build` itself. Also any path below `.zfb-build/` with a component named `dev-pages`, `dev-assets`, `watcher-liveness-probe`, or `plugins`, because those are the default layout's own directories. |
| `R3` | A path that overlaps the command's output directory (`--outdir`, else config `outDir`) in either direction: inside it, or containing it. |
| `R4` | A path that overlaps `publicDir` in either direction. |
| `R5` | A path that overlaps an authored watch root in either direction. Watch roots are the default roots (`pages`, `content`, `components`, `layouts`, `styles`, `data`, `src`, and the `zfb.config.*` files), content collection directories, and `extraWatchPaths`. |
| `R6` | A path nested inside another scratch dir, which is any directory above it that holds a `.zfb-scratch.lock`. Also a path with a component that zfb's own temp cleanup deletes: one starting with `zfb-shadow-session-`, or one named `watcher-liveness-probe` or `zfb-dev-watcher-liveness-probe`. |

zfb compares paths after resolving symlinks, so a symlinked alias does not get past a rule. The rules are checked once before the directory is created and again on the created directory. zfb does **not** detect the reverse of `R6`: claiming a directory that already contains another scratch dir. Keep scratch dirs as siblings, such as `.zfb-build/dev-main` next to `.zfb-build/build`, rather than nesting them.

### Ownership and locking

While a command runs, it holds an exclusive lock on `<scratch>/.zfb-scratch.lock`:

- **A second command on the same dir fails fast.** It exits with an error saying that the scratch dir is in use by another zfb process. It never waits and never shares the directory.
- **The lock file marks the directory as zfb's.** A later command may reuse a directory that has this file. An empty directory is also accepted. A non-empty directory without the lock file is refused, so a typo like `--scratch-dir ~/Documents` cannot write build artifacts into your own files.
- **The lock needs a local filesystem.** If the filesystem does not support advisory locks, the command fails instead of running without exclusivity.

<Warning title="zfb never deletes a scratch dir">

zfb never removes a scratch dir and never reaps old ones. The lock file stays in place after the command exits. Delete scratch dirs you no longer need yourself, after every command using them has stopped.

</Warning>

### What lives inside

| Entry | Written by |
|---|---|
| `.zfb-scratch.lock` | Every command that uses the scratch dir. |
| `bundle.mjs` (and its source map and assets) | `zfb dev` and `zfb build`. |
| `bundle-runtime.mjs` | `zfb build` with a deploy adapter configured (the bundle the adapter receives). |
| `dev-pages/`, `dev-assets/` | `zfb dev`. |
| `graph.bin` | `zfb dev` (the persisted dependency graph; the default layout keeps it at `.zfb/graph.bin` instead). |
| `watcher-liveness-probe/` | `zfb dev`. |
| `plugins/` | Plugins, through `ctx.scratchDir`. zfb does not create it. See [Plugins](../concepts/plugins.mdx#scratch-space-for-intermediates). |

`zfb check` and `zfb preview` write nothing of their own into a scratch dir. They only validate and lock it. Plugins that run under `zfb preview` still receive `ctx.scratchDir` and may write there.

### `zfb dev` ignores the prebuilt output directory

Under a scratch dir, `zfb dev` never reads the output directory. A previous `zfb build` may have used different defines or a different state, so dev does not trust it:

- no prebuilt HTML is served before a route's first render;
- no `/assets/*` fallback to the output directory;
- no boot-lazy seed, so `ZFB_DEV_BOOT_LAZY=1` falls back to the eager startup render.

Dev logs one info line saying so:

```text
scratch dir in use (<scratch>): ignoring prebuilt <outDir> — no dist/ fallback for HTML or /assets
```

Without a scratch dir, dev behaves exactly as before.

### What stays shared on purpose

A scratch dir isolates zfb's own generated artifacts. These stay shared between concurrent commands by design:

- **The output directory.** Two `zfb build` runs with the same output directory still overwrite each other. Pass a different `--outdir` to each one.
- **Temp files that are already per-process.** esbuild entry, tsconfig, and virtual-module temp files in the project root, shadow sessions, and config-loader temp dirs each get a unique name per process, so they do not collide.
- **A user tsconfig's `.tsbuildinfo`.** When your tsconfig turns on `incremental` or `composite`, `zfb check` runs `tsc` with your settings unchanged, so tsc writes that file where your tsconfig says.
- **The `.zfb/` staging directory.** Project code imports from it, so it cannot move.
- **Plugin-owned directories.** A plugin that writes to its own project-root directory (for example `.zudo-doc/`) is still shared between concurrent commands. Plugin isolation requires the plugin to adopt `ctx.scratchDir`. See [Plugins](../concepts/plugins.mdx#scratch-space-for-intermediates).

## Per-invocation defines

`--define KEY=EXPR` adds an esbuild define substitution for one invocation, on top of the config's [`bundle.define`](./define-config.mdx#bundle-settings-bundle-define). Use it to build or serve the same checkout with different values, for example a different origin per environment, without editing `zfb.config.ts`.

```sh
zfb build --define __ORIGIN__='"https://www.example.com"'
zfb dev --scratch-dir .zfb-build/dev-preview \
  --define __ORIGIN__='"https://preview.example.com"' \
  --define __FEATURE_X__=true
```

- **Commands.** `--define` is repeatable and accepted by `zfb dev`, `zfb build`, and `zfb check`. `zfb preview` rejects it, because preview serves already-built output and bundles nothing.
- **Values are raw esbuild expressions**, exactly like `bundle.define`. A string needs its own inner quotes: `--define __ORIGIN__='"https://a.example"'`. The shell's single quotes keep the inner double quotes intact. The flag splits on the first `=`, so the expression itself may contain `=`.
- **Merge.** The CLI values are merged per key over `bundle.define`, and the CLI wins. When the same key is repeated, the last occurrence wins, so a script can append an override to a shared argument list. Plugins see the merged map in `ctx.config.bundle.define`.
- **Errors.** A value with no `=`, an empty key, or an empty expression is a CLI usage error. So is a reserved key: `import.meta.env.PROD`, `import.meta.env.DEV`, or `process.env.NODE_ENV`. zfb does not check key syntax any further; esbuild reports an invalid key at bundle time, the same as for `bundle.define`.
- **Security.** The warning on `bundle.define` applies here too: every value ends up in browser bundles, so never pass secrets.

### `--define` with `zfb check`

`zfb check` validates and merges `--define` values, and then does not use them. They never reach `tsc`, which has no concept of defines. Declare the global's type in a `.d.ts` file that your tsconfig includes:

```ts
// components/zfb-env.d.ts
declare const __ORIGIN__: string;
```

Accepting the flag on `check` lets one argument list serve `dev`, `build`, and `check`, and a malformed value fails `check` instead of passing it and failing the build later.

### Defines are part of the build identity

The effective define map is part of the build identity that zfb stamps into server-rendered island markup and into the island bundles. SSR output and islands built with different defines never hydrate each other: an island whose identity does not match fails with a `ZR_IDENTITY` error instead of hydrating silently with the wrong values.

The identity also includes project source files, excluding files matched by the project's own `.gitignore` files, hidden directories, and build or scratch output. zfb still includes its known first-party staging paths, such as `.zudo-doc/routes-src`, even when they are hidden or ignored. Linked local packages, plugin aliases, virtual modules, and the effective define map also feed the identity. This is a file-selection policy, not a calculation of the exact reachable module graph. A gitignored file imported directly by your code is outside the identity; remove such generated inputs from `.gitignore` and track them, or regenerate them deterministically.

Neither the checkout path nor the scratch dir location affects the identity or the emitted bundles. With the same commit, lockfile, and build options, local and CI builds produce byte-identical `dist/` output. Leftover tool output such as `test-results/` changes neither the identity nor the bundle bytes when it is gitignored.

<Tip>

When a dev server uses a different `--define` than your last `zfb build`, give it a `--scratch-dir` too. Under a scratch dir, dev ignores the prebuilt output directory, so it never serves pages built with the other define. The scratch dir also keeps its bundle apart from any concurrent build.

</Tip>

## Environment variables

The following environment variables affect `zfb` globally (not specific to one subcommand):

| Variable | Default | Description |
|---|---|---|
| `ZFB_DEV_EAGER` | unset | Set to `1` to disable lazy dev rendering in `zfb dev`. Re-renders every affected route eagerly on each file change. |
| `ZFB_LAZY_DEV_RENDER` | unset | Set to `0` or `1` for precise control over the lazy dev-render switch. Takes precedence over `ZFB_DEV_EAGER` when both are set. |
| `ZFB_DEV_BOOT_LAZY` | `cold` | Default seedless lazy startup renders each route on request, so eager rendering of unrelated pages does not block edits after `ready`. Explicit `0`/`false` restores eager startup; `1` retains legacy seed-based mode. Requires lazy rendering. |
| `ZFB_DEV_DEFER_BUNDLE` | unset | Set to `0` to opt out of the boot-lazy bundle deferral (either variant; build the renderer before bind instead of after the first request). On by default when boot-lazy is active. |
| `ZFB_DEV_TIMING` | unset | Set to `1` or `true` to print dev-mode phase timings for each file-change tick. |
| `ZFB_PLUGIN_HOOK_TIMEOUT` | `120` (seconds) | Maximum time (in seconds) any single plugin hook reply is awaited before the plugin host is force-killed and the build fails. Precedence: `pluginHookTimeoutSecs` in config > this env var > 120s built-in default. |
| `ZFB_ESBUILD_BIN` | unset | Absolute path to an esbuild binary. Used by the bundler, islands compiler, tests, and TypeScript config loading (`zfb.config.ts`) when an embedded/staged esbuild binary is unavailable or should be overridden. |
| `ZFB_DEBUG_SNAPSHOT` | unset | Set to `1` or `true` to log the content snapshot's entry count and serialized byte size to stderr during `zfb build`, for monitoring V8 memory pressure on large sites. See [Incremental Rebuild](../concepts/incremental-rebuild.mdx). |
| `ZFB_SKIP_WRANGLER_VERSION_CHECK` | unset | Set to `1`, `true`, or `yes` to bypass the `zfb preview` adapter-mode wrangler minimum-version gate. Intended for temporary release-engineering use. |
| `ZFB_SCRATCH_DIR` | unset | Scratch dir for `zfb dev`, `zfb build`, `zfb check`, and `zfb preview` when `--scratch-dir` is not passed. An empty or whitespace-only value counts as unset. See [Scratch dirs](#scratch-dirs). |

<Note>

`ZFB_PLUGIN_HOOK_TIMEOUT` can also be set via `pluginHookTimeoutSecs` in [defineConfig](./define-config.mdx). The config field takes precedence over the environment variable.

</Note>
