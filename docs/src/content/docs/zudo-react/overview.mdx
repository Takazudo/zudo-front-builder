## What zudo-react provides

zudo-react is the JSX runtime shipped inside **@takazudo/zfb**. It gives components a small, explicit model: a component function runs once for each rendered instance, signals carry changing values, and the renderer updates bound DOM without calling the component again.

The runtime is not a React or Preact compatibility layer. It has no hooks, context, portals, class components, or general tree reconciliation. JSX describes work for zudo-react; it does not make the runtime behave like React.

## Configure JSX

Install a zfb package version that includes zudo-react. `zfb build` and `zfb dev` compile page, component, and island JSX with the automatic transform and the fixed import source `@takazudo/zfb/zudo-react`, even when the project has no `tsconfig.json`; they ignore `jsx` and `jsxImportSource` in the project's `tsconfig.json`. A per-file `@jsxImportSource` pragma can override the build transform for that file, but a React or Preact pragma does not add support for those renderers. Set the following options in `tsconfig.json` so `zfb check`, editors, and TypeScript checks of test files use the same runtime's JSX types. Configure test-runner transforms separately in the runner's config.

~~~json
{
  "compilerOptions": {
    "jsx": "react-jsx",
    "jsxImportSource": "@takazudo/zfb/zudo-react"
  }
}
~~~

The compiler resolves the production helpers from **@takazudo/zfb/zudo-react/jsx-runtime**. Development transforms use **@takazudo/zfb/zudo-react/jsx-dev-runtime**. Both are package subpaths; zudo-react is not a separate package.

The TypeScript step in a full `zfb check` requires a project `tsconfig.json`; `zfb check --skip-tsc` skips that step and still runs the other checks. See [`zfb check`](../api/cli.mdx).

Import runtime values from the core entry:

~~~tsx
import { computed, signal } from "@takazudo/zfb/zudo-react";
~~~

## A component runs once

Make a signal during setup and pass the signal itself to JSX. The event changes its value; the text binding updates on the next scheduled flush.

~~~tsx
import { signal } from "@takazudo/zfb/zudo-react";

function Counter() {
  const count = signal(0);

  return (
    <button on:click={() => { count.value += 1; }}>
      Clicked {count} times
    </button>
  );
}
~~~

The component function is called once when this instance is rendered. A later count change updates the text slot and does not call Counter again. Each mounted instance gets its own setup and scope.

Passing a signal creates a live binding. Reading its value while JSX is being created takes a snapshot:

~~~tsx
<p>{count}</p>
<p>{count.value}</p>
~~~

In this example, the first child is reactive. The second child is the number read during setup and stays that number. This rule also applies when values are passed through component props.

## Use zudo-react outside a zfb site

zudo-react is not a separate npm package. It ships inside **@takazudo/zfb**, so a host that is not a zfb site, such as an application built with another bundler, a test runner, or a Node script, installs `@takazudo/zfb` and imports these public subpaths:

| Subpath | What it provides |
| --- | --- |
| `@takazudo/zfb/zudo-react` | The core entry: `signal`, `computed`, `h`, `Fragment`, `Show`, `For`, `ErrorBoundary`, `batch`, `flush`, `getScope` |
| `@takazudo/zfb/zudo-react/jsx-runtime` | The automatic JSX transform target for production builds |
| `@takazudo/zfb/zudo-react/jsx-dev-runtime` | The automatic JSX transform target for development builds |
| `@takazudo/zfb/zudo-react/server` | `renderToString`, `islandRoot`, `serializeProps` |
| `@takazudo/zfb/zudo-react/client` | `hydrate`, `mount`, `parseProps` |
| `@takazudo/zfb/zudo-react/testing` | `createIslandTest` and `withIslandTestContext` |

Inside a zfb site, `zfb build` and `zfb dev` transform JSX, register island boundaries, schedule hydration, and carry props from server to client. An external host does not get those steps; it owns them:

- **JSX transformation.** Configure the host's own transform with the automatic runtime and `@takazudo/zfb/zudo-react` as the JSX import source. Elements created by another JSX runtime are not zudo-react descriptions.
- **The mount boundary and its lifecycle.** The host creates and connects the wrapper element, calls `mount` or `hydrate` from `@takazudo/zfb/zudo-react/client` with an identity that matches the wrapper, handles a `null` result, and calls `dispose()` or `unmount()` when it removes the boundary. See [Mount from a host you own](./hydration.mdx#mount-from-a-host-you-own).
- **Server rendering, when used.** `renderToString` from `@takazudo/zfb/zudo-react/server` renders HTML anywhere. Rendering SDK `<Island>` boundaries outside a zfb build needs extra identity setup; see [Rendering Islands outside a zfb build](./server-rendering.mdx#rendering-islands-outside-a-zfb-build).

Components keep the same contract everywhere: `class` and `on:click` attributes, signals created during setup, and a setup function that runs once.
