## Migrate in a short pass

The docs site hosting this guide still uses Tailwind for its own chrome. This checklist and its compiled samples describe zudo-wind v1 in your project.

1. Remove Tailwind imports and engine directives from the entry stylesheet and its imports. Keep ordinary authored CSS and <code>@layer</code>.
2. Move engine values into the top-level <code>wind</code> key. Set <code>spec</code>, choose a reset, and configure the tokens and breakpoints your candidates use.
3. Keep finite candidates in source, use <code>safelist</code> for app candidates absent from source, and publish package candidates through a versioned manifest.
4. Audit the build plan. Fix supported candidates, reserve exact authored names, and replace or implement foreign utilities before enabling strict mode.

~~~ts
import { defineConfig } from "zfb/config";

export default defineConfig({
  wind: {
    spec: 1,
    reset: "owned-v1",
    strict: false,
    tokens: {
      spacingUnit: "0.25rem",
      colors: { panel: "var(--app-panel)" }
    },
    breakpoints: { sm: { minWidthPx: 640 } }
  }
});
~~~

Declare referenced custom properties in authored CSS. Then audit and explain the complete candidates:

~~~sh
zfb wind audit --plan build
zfb wind explain --config zfb.config.ts bg-panel
zfb wind audit --plan build --fail-on warning
~~~

<Details title="Technical reference">

## What changes in one minute

- zudo-wind is a versioned utility language. V1 is identified by `spec: 1`; familiar spellings do not promise compatibility with another engine.
- There are no utility plugins. The accepted catalog is closed for each language version.
- Configuration is data in the top-level `wind` key of `zfb.config.ts` or `zfb.config.json`. CSS directives do not configure the engine.
- No palette, spacing unit, named scale, breakpoint, font, radius, shadow, or named easing token is supplied implicitly. Transition utilities use `ease` by default; set `wind.defaultTransitionTimingFunction` to choose another project default.
- The source scanner needs complete class candidates. A prefix joined to a runtime value does not become a utility.
- A project class with no matching utility root stays ordinary class text. A name that starts with a catalog root is resolved against the longest matching root and validated as a utility, so missing tokens receive diagnostics. Reserve a complete authored candidate with `wind.authoredClasses` when CSS owns a name that overlaps a utility root.
- Keep declarations and selectors outside the catalog in authored CSS or CSS Modules.

## Directives

Wind configuration and candidate discovery live outside CSS. Remove Tailwind-only directives when migrating a stylesheet. If one remains in the entry sheet or any imported sheet, zfb reports ZW009 with its spelling and source location and fails the pass, even when `wind: false` disables utility generation.

| Tailwind construct | zudo-wind disposition |
| --- | --- |
| `@import "tailwindcss"` | Remove it. Wind supplies its own layer prelude and emits the selected reset, configured tokens, and resolved utilities. A remaining Tailwind import is a ZW009 error. |
| `@import "tailwindcss/preflight"` | Remove it and choose an explicit `wind.reset`. The reset choices are listed below; an import left behind is a ZW009 error. |
| `@import "tailwindcss/utilities"` | Remove it. Utilities are generated from complete candidates and the closed catalog; a remaining import is a ZW009 error. |
| `@tailwind base`, `@tailwind components`, or `@tailwind utilities` | There is no CSS expansion directive. Choose a reset and write component rules in authored CSS; use complete candidates for catalog utilities. A leftover directive is a ZW009 error. |
| `@theme` | Put validated values in `wind.tokens`. Keep CSS-only properties as ordinary custom properties in authored CSS, then point tokens at those properties when a utility needs them. |
| `@source` | CSS does not select scan roots. zfb's source plan owns scanned files and package roots; see [Sources and candidates](./sources-and-candidates.mdx). |
| `@source inline(...)` | Use an owner-keyed `wind.safelist` array for app-owned candidates. Put package-owned candidates in an explicit versioned `wind.manifests` file filtered to complete v1 utilities or markers; every manifest entry is strict, so an invalid or unknown entry fails. There is no pattern, brace expansion, or runtime interpolation syntax. |
| `@source not(...)` | There is no CSS negation directive. Use the source plan's root and exclusion rules; see [Sources and candidates](./sources-and-candidates.mdx). |
| `@custom-variant` | Only the built-in `dark` variant is configurable. Set its attribute and value under `wind.dark`; write other selector conditions in authored CSS. |
| `@apply` | There is no directive that expands utility names into declarations. Put declarations in the authored selector that needs them. |
| `@utility` | Custom utilities do not extend the language. Define a class in authored CSS and, if its exact complete candidate appears in markup, reserve that spelling with `wind.authoredClasses`. |
| `@variant` | There is no stylesheet variant-expansion directive. Use a supported complete candidate in markup or write the selector and condition in authored CSS. |
| `@plugin` | Plugins are not loaded. Use the built-in catalog or authored CSS. |
| `@config` | Move configuration data to the project's `wind` key; CSS does not load a utility config file. |
| `@reference` | There is no utility reference import for stylesheet expansion. Keep CSS Modules and global CSS authored, and configure utility values under `wind.tokens`. |

The scanner also rejects the legacy declaration-value functions `theme()`, `--spacing()`, `--alpha()`, and `--value()` with ZW009. It ignores comments and string contents. Ordinary `@layer` statements and CSS imports that explicitly name a layer remain valid. See [Diagnostics and tools](./diagnostics-and-tools.mdx) for the error contract.

## Configuration

The old top-level `tailwind` key has no zudo-wind meaning. A leftover key is a hard configuration error with a named migration message. Replace it with `wind`. A missing `wind` key enables the empty v1 configuration after cutover; that means generation is enabled, reset is `none`, and the token maps start empty.

~~~ts
import { defineConfig } from "zfb/config";

export default defineConfig({
  wind: {
    spec: 1,
    reset: "owned-v1",
    defaultTransitionTimingFunction: "cubic-bezier(0.4, 0, 0.2, 1)",
    tokens: {
      spacingUnit: "0.25rem",
      colors: { panel: "var(--app-panel)" }
    },
    breakpoints: {
      sm: { minWidthPx: 640 }
    },
    dark: { attribute: "data-theme", value: "dark" }
  }
});
~~~

The old opt-out `tailwind: { enabled: false }` becomes `wind: false`. That disables wind generation, token validation, manifest loading, and candidate scanning. Authored global CSS, CSS Modules, and syntax highlighting still run, and the leftover-directive check still runs. For all fields and merge rules, see [Configuration](./configuration.mdx).

## Theme and tokens

V1 ships no color palette or spacing scale. It also supplies no named sizes, font families or weights, font sizes, line heights, tracking, radii, shadows, z-index values, easing values, or breakpoints. The constants `0`, `px`, and catalog keywords do not imply a theme.

Move the values that utilities need into `wind.tokens`. Numeric spacing such as `p-4` multiplies the configured `spacingUnit`; named values come from their family map. For example, this binds both color utilities to a project-owned property:

~~~json
{
  "wind": {
    "tokens": {
      "spacingUnit": "0.25rem",
      "colors": {
        "panel": "var(--app-panel)"
      }
    }
  }
}
~~~

~~~css
:root {
  --app-panel: #f4f1ec;
}
~~~

Then `bg-panel` and `text-panel` resolve from `colors.panel`. Token entries are validated data, not executable CSS or JavaScript. A referenced custom property remains authored CSS; the generated token variable points to it. Missing tokens and missing numeric spacing units are reported at strict candidate origins instead of being repaired with defaults. See [Tokens](./tokens.mdx) for the supported maps and value rules.

Uppercase `DEFAULT` is invalid. Use the lowercase key `default` only in maps that define that meaning: `radii.default` supplies bare `rounded`, and `shadows.default` supplies bare `shadow`. It is not a fallback for colors or spacing.

## Reset

The default `reset` is `none`, which emits no reset declarations. Select a reset for the assumptions a page makes about browser defaults.

| Reset | Relevant behavior |
| --- | --- |
| `none` | No reset bytes. Lists, heading sizes, border defaults, and controls keep the browser's normal styles unless authored CSS changes them. |
| `minimal-v1` | Sets border-box sizing, removes the body margin, and makes form controls inherit the font. It does not remove list markers or normalize heading sizes. |
| `owned-v1` | Sets border-box sizing and clears margins, padding, and default border width while making borders solid. It removes list markers, gives headings inherited size and weight, and normalizes control fonts and button backgrounds. |

With `owned-v1`, add list markers back where the design calls for them; the scaffold's `.prose` rules explicitly restore disc and decimal lists. Headings do not retain browser heading sizes, so set them in authored CSS or with configured font-size utilities. Bare border utilities set their own solid border under every reset choice. Controls inherit font styling, and the reset leaves native focus outlines and appearance alone. Wind utilities are unlayered and, by default, follow authored global CSS: they beat normal declarations in named layers, while an unlayered authored rule can still win by specificity or later order. See [Utility placement and ties](#utility-placement-and-ties) for the opposite order. The reset is an explicit zudo-wind choice, not a promise to reproduce another preflight byte for byte. See [Cascade and reset](./cascade-and-reset.mdx) for the complete declarations and layer order.

### Differences from Tailwind preflight

The baseline is **Tailwind CSS 4.2.0 preflight vs `owned-v1`**. The earlier recipe migrations were measured in Chromium 147 and 151 and WebKit 26.4. The supplemental #3451 fixture ran in Chromium 151 and WebKit 26.5 at 375px and 1280px; neither matrix is exhaustive. In the measured projects, Tailwind's theme resolves `--default-font-family` from `--font-sans` and `--default-mono-font-family` from `--font-mono`.

| Selector | Tailwind 4.2.0 preflight | `owned-v1` and effect |
| --- | --- | --- |
| `html` font family | Theme `--default-font-family` / `--font-sans` | Fixed `ui-sans-serif, system-ui, sans-serif`; descendants can inherit another face. |
| `html` tap highlight | `-webkit-tap-highlight-color: transparent` | No rule; the browser's tap color is inherited by everything. |
| `code, kbd, samp, pre` font family | Theme `--default-mono-font-family` / `--font-mono` | Fixed `ui-monospace, SFMono-Regular, Menlo, monospace`; macOS screenshots can hide a change when both stacks resolve to Menlo. |
| `small` | `font-size: 80%` | No rule; the UA size applies. |
| `sub, sup` | `font-size: 75%; line-height: 0; position: relative; vertical-align: baseline`, with `sub { bottom: -0.25em }` and `sup { top: -0.5em }` | No rules; the line box can grow and shift layout. |
| `hr` | `color: inherit` | No color rule; the UA color can affect the border. |
| `button`, button/reset/submit inputs | `appearance: button` | No appearance rule; native appearance can differ. |
| `button, input, select, optgroup, textarea` | `border-radius: 0; background-color: transparent; opacity: 1` | `owned-v1` already uses transparent backgrounds for buttons and button-type inputs; a text input keeps its UA white background in Chromium. Add the common-control rule below to match these declarations. |
| `::placeholder` | `opacity: 1` and, in supported browsers, `color: color-mix(in oklab, currentcolor 50%, transparent)` | No rule; UA placeholder color and opacity apply (grey in measured Chromium). |
| `::file-selector-button` | Borderless, transparent, inherited text styling, 4px end margin, `appearance: button` | No pseudo-element rule; the native bevelled file button remains. |
| `[hidden]:where(:not([hidden="until-found"]))` | `display: none !important` | Only the UA hidden rule applies; a display utility can make an element with `hidden` visible silently. |

The original **0 differing elements** result was limited to its fixture: it omitted a standalone text input, `abbr[title]`, `progress`, and `:-moz-focusring`. The #3451 fixture found one difference before the common-control rule below: the text input had the UA white background under `owned-v1` and a transparent background under Tailwind. After adding the rule, every standard computed-style property on the fixture elements and both pseudo-elements matched in Chromium 151 and WebKit 26.5 at both widths; all four screenshot pairs were pixel-identical. Chromium also retained a visible keyboard focus ring on the link after tabbing to it. This matrix still does not cover every control, font installation, or platform. A per-element `getComputedStyle` diff does not inspect `::placeholder` or `::file-selector-button`; query each explicitly and compare pixels where appearance matters.

For projects that want these measured preflight behaviors, add the following to authored CSS. Replace the sample font stacks with your project's stacks if they differ. The project must declare `--font-sans` and `--font-mono` in authored CSS, as this block does, or substitute literal stacks at both `font-family` declarations: v3 supplies no implicit theme.

~~~css
@layer base {
  :root {
    --font-sans: ui-sans-serif, system-ui, sans-serif, "Apple Color Emoji", "Segoe UI Emoji", "Segoe UI Symbol", "Noto Color Emoji";
    --font-mono: ui-monospace, SFMono-Regular, Menlo, Monaco, Consolas, "Liberation Mono", "Courier New", monospace;
  }
  html { font-family: var(--font-sans); -webkit-tap-highlight-color: transparent; }
  code, kbd, samp, pre { font-family: var(--font-mono); }
  small { font-size: 80%; }
  sub, sup { font-size: 75%; line-height: 0; position: relative; vertical-align: baseline; }
  sub { bottom: -0.25em; }
  sup { top: -0.5em; }
  hr { color: inherit; }
  button, input:where([type="button"], [type="reset"], [type="submit"]) { appearance: button; }
  button, input, select, optgroup, textarea {
    border-radius: 0;
    background-color: transparent;
    opacity: 1;
  }
  ::placeholder { opacity: 1; color: color-mix(in oklab, currentcolor 50%, transparent); }
  ::file-selector-button {
    box-sizing: border-box;
    margin: 0;
    margin-inline-end: 4px;
    padding: 0;
    border: 0 solid;
    border-radius: 0;
    background-color: transparent;
    font: inherit;
    font-feature-settings: inherit;
    font-variation-settings: inherit;
    letter-spacing: inherit;
    color: inherit;
    opacity: 1;
    appearance: button;
  }
  /* Optional: keep hidden elements hidden even when a display utility is present. */
  [hidden]:where(:not([hidden="until-found"])) { display: none !important; }
}
~~~

The common-control rule restores Tailwind's border radius, background, and opacity declarations. The file-selector rule is separate because the `button` rule does not style that pseudo-element. In the Chromium 151 image-gallery recipe, adding the measured file-selector rule removed the pixel and pseudo-element differences on both tested pages in light and dark themes. The `[hidden]` rule is optional; its `!important` overrides display utilities, as Tailwind preflight does. The [layer prelude](./cascade-and-reset.mdx) orders `zw-reset` before authored `base`, so these declarations can override the reset. Keep keyboard focus indicators and review each rule you adopt rather than pasting a broader reset blindly. Restoring reset declarations does not restore utility placement or relation-selector specificity; that migration difference is tracked in #3386.

## Variants and grammar

The table names the v1 disposition for each construct. Supported chains use the order responsive, dark, pointer, relation, state, pseudo-element, utility, with no repeated category.

| Construct | Spec disposition and rule |
| --- | --- |
| Breakpoints, including `max-*` | **Adopt changed (W02).** Configure each name with a positive integer `minWidthPx`. `sm` is a minimum-width query; `max-sm` is the exclusive range below that width. Widths are pixels and do not follow changes to the root font size. |
| `dark` | **Adopt changed (W09).** Dark mode is off until configured with an attribute and value. The condition may match the element or an ancestor and adds zero specificity. |
| State variants | **Adopt (W03).** V1 admits `hover`, `focus`, `focus-visible`, `active`, `disabled`, `checked`, `focus-within`, `open`, `first`, and `last`. Every hover condition is guarded by a hover-capability media query. |
| `first` and `last` | **Adopt (W03).** They target `:first-child` and `:last-child`, respectively. |
| `group-*` and `peer-*`, including named forms | **Adopt changed (W04).** Unnamed `group` and `peer` markers work with the admitted states; a group is an ancestor and a peer is a preceding sibling. Markers must stand alone and emit no CSS by themselves. Named markers and forms such as `group/menu` or `group-hover/menu:block` are rejected. |
| Pseudo-element variants | **Adopt (W05).** `before`, `after`, `marker`, `placeholder`, `backdrop`, and `selection` are admitted. `before` and `after` do not add a `content` declaration; author it when needed. |
| `aria-*` and `data-[...]` variants | **Reject with diagnostic (W06).** Attribute variants are ZW004. Put the selector in authored CSS. |
| Arbitrary-selector variants | **Reject with diagnostic (W07).** A selector such as `[&_a]:underline` is ZW004. Write the selector in authored CSS. |
| Stacked variants | **Adopt changed (W08).** Use at most one responsive, dark, pointer, relation, state, and pseudo-element variant, in that order. For example, `sm:dark:hover:bg-panel` is canonical when each feature and token is configured. Duplicate or out-of-order chains are diagnosed. |
| Color opacity modifier | **Adopt (W10).** A color suffix is an integer from 0 to 100 and mixes the configured color in oklab against transparent; `bg-panel/40` is valid. This modifier does not apply to spacing or sizing utilities. |
| Fractions | **Adopt changed (W11).** Positive integer ratios are accepted by eligible sizing, translate, and seven inset roots, and as aspect ratios. `w-1/2` means half the available sizing basis; `aspect-4/3` emits `aspect-ratio: 4 / 3`. Aspect numerator and denominator must each be 1–1,000,000; use an arbitrary value such as `aspect-[1.5/2.5]` for decimal parts. `left-1/2` emits `left: calc(100% * 1 / 2)`; negative inset fractions also work. A sizing or inset slash never means color opacity. |
| Transitions | **Current v1 behavior.** `transition-shadow` sets `box-shadow`, and `transition-colors` includes `outline-color`. Transition utilities except `transition-none` set a 150ms duration and use `wind.defaultTransitionTimingFunction`, which defaults to `ease`. Set it to `cubic-bezier(0.4, 0, 0.2, 1)` to keep Tailwind 4's default timing. Explicit `ease-*` utilities take precedence in the same variant bucket. |
| Arbitrary values | **Adopt changed (W12).** A supported utility root may carry a balanced bracket value that passes CSS property validation. Write spaces as underscores; an escaped underscore stays literal. Tailwind spaced `calc()` operators for you; zudo-wind does not, so write `w-[calc(100vw_-_2rem)]`, and the error suggests that spelling for `w-[calc(100vw-2rem)]`. Data-type hints such as `text-[color:var(--x)]` are not supported; use a named token for an ambiguous variable. `url()` is rejected, as are values that inject declarations or other syntax. |
| Arbitrary properties | **Reject with diagnostic (W13).** A token such as `[overflow-wrap:anywhere]` is ZW004. Write the declaration in authored CSS or a CSS Module. |
| `!important` spellings | **Reject with diagnostic (W14).** Leading and trailing forms are both rejected with ZW004. Put an intentional important declaration in authored CSS. |
| Negative utilities | **Adopt (W15).** Only catalog families that permit negatives accept the sign, with the family-defined sign applied to its value. For example, `-mt-2` is admitted while `-p-2` is invalid. |
| `space-*` and `divide-*` | **Adopt changed (W20).** The utilities target later visible direct-child siblings, filtered by the `hidden` attribute. Spacing sets the relevant margin; divide sets a solid left or top border. There are no reverse flags, and pseudo-element variants cannot combine with these child utilities. |

`pointer-coarse` and `pointer-fine` need no config. `any-pointer-*`, `motion-*`, `print`, `portrait`, and arbitrary `[@media(...)]` remain unsupported (ZW002/R04; an arbitrary selector reports ZW004/R09). `checked:`, `group-checked:`, `peer-checked:`, and `max-sm:peer-checked:visible` are admitted; `indeterminate`, `required`, and `invalid` remain unsupported. `selection:` is admitted, without creating content. The standard `focus-visible:outline focus-visible:outline-2` idiom resolves with a computed 2px outline width.

Decoration thickness/style use `decoration-<integer>`, nonnegative `decoration-[<length>]`, and exact `decoration-solid|double|dotted|dashed|wavy`. Negative and slash thickness/style forms, `decoration-auto`, and `decoration-from-font` are unsupported. Configured full color tokens take precedence over style names: `colors: { wavy: "#123456", "dotted-muted": "#123456" }` makes `decoration-wavy` and `decoration-dotted-muted/40` emit text-decoration-color. Without the token, `decoration-wavy` emits text-decoration-style. The names `solid`, `double`, `dotted`, and `dashed` were already reserved as color-token names; `wavy` was not. To get both declarations under a colliding name, author `.decorated { text-decoration-style: wavy; text-decoration-color: var(--zw-color-wavy); }` and reserve `decorated` in `wind.authoredClasses` if audit diagnoses it.

The candidate grammar balances brackets, parentheses, and quotes before splitting separators, so a colon or slash inside a bracket value is not treated as a variant or modifier separator. See [Variants](./variants.mdx), [Utility grammar](./utility-grammar.mdx), and the [utility reference](./utilities/index.mdx) for the full catalog.

## Utility placement and ties

A Tailwind v4 entry usually imports the utilities before its own CSS, so an authored rule with the same specificity as a utility won by coming later. zudo-wind places utilities after authored global CSS by default, which flips those ties:

```css
/* authored */
.card {
  color: red;
}
```

```html
<p class="card text-accent">Card</p>
```

| Setup | Order | Color |
| --- | --- | --- |
| Tailwind v4, utilities imported first | utilities, `.card` | red |
| zudo-wind default (`after-authored`) | `.card`, utilities | accent |
| zudo-wind `before-authored` | utilities, `.card` | red |

To keep Tailwind's order, set the placement:

```ts
wind: {
  utilities: { placement: "before-authored" }
}
```

The emitted stylesheet is then: the layer prelude, hoisted external imports, the highlight block, the reset and token layers, `@property` registrations, the unlayered utilities, the authored global CSS, and finally CSS Modules. Placement decides only ties of equal specificity between unlayered rules. Under either setting a more specific authored selector wins, an authored rule inside a layer loses to every utility, and an authored `!important` declaration wins. Breakpoint and dark variants add no specificity, so they follow the same tie rule. Emitting utilities into a named layer is not available.

## Relation variant specificity

Tailwind emits `group-hover:text-accent` as `.group-hover\:text-accent:is(:where(.group):hover *)`, with specificity (0,2,0). zudo-wind emits `:where(.group:hover) .group-hover\:text-accent`, with specificity (0,1,0), and `peer-*` variants likewise. Placement does not change any selector, so it does not restore that specificity. An authored (0,2,0) or (0,1,1) rule that used to lose to a group or peer state now wins under either placement:

```css
/* (0,2,0): now beats group-hover:text-accent */
.panel .title {
  color: red;
}
```

Choose one of these per rule:

- Lower the authored selector to the utility's specificity, for example `:where(.panel) .title`. The state then wins by order under the default placement.
- Move the authored rule into a layer, such as `@layer components { .panel .title { color: red; } }`, so every utility beats it.
- State the hover style in authored CSS too: `.panel:hover .title { color: var(--zw-color-accent); }`.

## Classes that used to emit nothing

Not every class-shaped string is meant to create a utility rule. A project name such as `site-header` has no matching utility root, so it remains ordinary class text in markup and wind emits no rule for it. A name such as `text-link` does match the `text` root and is validated as a utility; if its required token is missing, it receives ZW006. This strict classification preserves typo detection instead of treating every unresolved name as ordinary. A standalone `group` or `peer` marker also emits no rule, while still supplying relation metadata to matching candidates.

A Tailwind utility zudo-wind does not implement, such as `line-clamp-2`, `order-1`, `basis-1/2`, or `container`, is not treated as ordinary text. It is reported as ZW014 with the declaration to author instead, as a warning by default and an error under `wind.strict: true`. Names with underscores, such as `card__title`, remain ordinary.

| Candidate outcome | What happens |
| --- | --- |
| Resolved utility | Wind emits its rule. |
| Ordinary class or marker | A class-position name with no matching utility root remains in markup and produces no utility rule. The class can still be styled in authored CSS. |
| Recognized but invalid utility | A strict class, safelist, or manifest origin receives a diagnostic; lower-confidence source text is audit information. A missing token is not filled in automatically. |
| Malformed, unsupported, or unknown explicit utility input | The pass fails with a diagnostic. Unknown explicit safelist or manifest entries fail; unrelated class-position names remain ordinary. |

Run `zfb wind audit` to list ordinary class-position names, missing or dead utility candidates, dynamic fragments, and property conflicts within a class-list literal. Audit helps distinguish an intentionally authored class from a misspelled utility; it does not invent a replacement. To use an authored class whose name starts with a utility root, reserve the exact complete candidate spelling in `wind.authoredClasses`, for example `{ "text-link": true }`. Include the variant chain when reserving a candidate such as `hover:text-link`. A match suppresses utility validation, diagnostics, and generated CSS for that candidate at every origin. Otherwise, correct the utility spelling or declare its missing token. See [Diagnostics and tools](./diagnostics-and-tools.mdx).

ZW014 vocabulary v4 identifies logical `ms-*`/`me-*`, `ps-*`/`pe-*`, `start-*`/`end-*`, `border-s`/`border-e` for authored `margin-inline-*`, `padding-inline-*`, `inset-inline-*`, and `border-inline-*` declarations. It also identifies isolation, float, clear, `word-break`/`break-*`, transform origin, filter, backdrop-filter, text-shadow, and gradient families. Use authored CSS and reserve each exact retained class in `wind.authoredClasses`; no composed CSS is generated. Names such as `origin-story`, `float-label`, and `clear-fix` stay authored. An actual catalog/token utility resolves first. Gradient spellings include `bg-gradient-to-*`, `bg-linear-to-*`, integer-angle `bg-linear-*`, `bg-radial` and bracketed values, `bg-conic` and integer angles, and `from-*`/`via-*`/`to-*` with a declared color, `current`, `transparent`, or bracketed color/position. Author `background-image`. Bare stop percentages (`from-10%`, `via-30%`, `to-90%`) are parser-rejected; bracketed `from-[60%]` reaches ZW014.

## A worked migration

The basic-blog scaffold's callout uses actual candidates such as `my-6`, `rounded-md`, `border-l-4`, `px-4`, `py-3`, `dark:bg-sky-950/40`, and `group-hover:text-accent`. The migration table keeps these spellings. Adoption means they resolve only after the scaffold explicitly configures their tokens and variants.

The old stylesheet begins with the Tailwind import and a custom dark variant, and declares three project colors through `@theme`:

~~~css
@import "tailwindcss";
@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));

@theme {
  --color-accent: oklch(0.53 0.21 258);
  --color-code-bg: #2b303b;
  --color-code-fg: #c0c5ce;
}
~~~

The callout source supplies these tone strings:

~~~ts
tone: "border-sky-500 bg-sky-50 dark:bg-sky-950/40",
accent: "text-sky-700 dark:text-sky-300",
~~~

Remove the two Tailwind directives. Move utility values to config and keep the CSS-only theme properties authored:

~~~ts
import { defineConfig } from "zfb/config";

export default defineConfig({
  wind: {
    spec: 1,
    reset: "owned-v1",
    tokens: {
      spacingUnit: "0.25rem",
      colors: {
        accent: "var(--color-accent)",
        "sky-50": "#f0f9ff",
        "sky-300": "#7dd3fc",
        "sky-500": "#0ea5e9",
        "sky-700": "#0369a1",
        "sky-950": "#082f49"
      },
      radii: { md: "0.375rem" }
    },
    breakpoints: { sm: { minWidthPx: 640 } },
    dark: { attribute: "data-theme", value: "dark" },
    authoredClasses: { prose: true }
  }
});
~~~

This config excerpt covers the shown callout tokens. A complete scaffold config also declares every color and scale used by the remaining candidates and authored CSS; nothing fills those maps implicitly.

Merge the theme properties into the existing authored base layer, retaining its color-scheme and selection rules:

~~~css
@layer base {
  :root {
    --color-accent: oklch(0.53 0.21 258);
    --color-code-bg: #2b303b;
    --color-code-fg: #c0c5ce;
    color-scheme: light;
  }

  [data-theme="dark"] {
    --color-accent: oklch(0.79 0.13 254);
    color-scheme: dark;
  }
}
~~~

Keep the existing base and component layers; wind's prelude establishes their order. The authored `.prose` class remains in the stylesheet and is entered exactly in `authoredClasses`. Where authored CSS formerly referenced `var(--color-neutral-900)`, update it to `var(--zw-color-neutral-900)`, the emitted token variable. The configured `accent` token points back to the authored `--color-accent` property, so the theme toggle can continue changing that value. The scaffold reset is `owned-v1`; other projects still default to `none`. These are language and stylesheet changes only; the full ordered project upgrade is in [Migrating to v3](../guides/migrating-to-v3.mdx).

## What is not supported, and what to do instead

- No implicit palette or spacing scale: declare project values under `wind.tokens`.
- No shadow-color composition: `shadow-<color>` and valid `shadow-<color>/<opacity>` forms (`/0`–`/100`) do not apply `colors` tokens to a shadow. Fold the tint into a `shadows` token or author the complete `box-shadow` in CSS and reserve the class. A bare `shadow-<name>` with matching `colors` and `shadows` tokens resolves as the shadow token; slash modifiers remain unsupported. `shadow-none` and complete arbitrary values such as `shadow-[0_1px_2px_#000]` remain supported.
- No ring, animation, scale, transform-string, or arbitrary-property utility: write the declarations in authored CSS or a CSS Module.
- No attribute or arbitrary-selector variant and no named group or peer: use an authored selector.
- No plugin-defined classes or `@apply` expansion: use catalog candidates for supported utilities and keep custom declarations in CSS.
- No runtime-built candidate or regex safelist: write a finite literal map, an owner-keyed safelist, or a strict versioned package manifest.

Use the [utility reference](./utilities/index.mdx) for the v1 catalog and [Diagnostics and tools](./diagnostics-and-tools.mdx) to inspect candidates and migration errors.
