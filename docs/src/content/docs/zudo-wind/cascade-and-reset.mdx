## Choose a reset for the page

The documentation chrome still uses Tailwind CSS. These isolated samples contain compiled zudo-wind CSS and browser-native styles only.

| Reset | Choose it when | Browser defaults that remain |
| --- | --- | --- |
| <code>none</code> | Your app already owns a baseline | Heading sizes, list markers, body margin, native controls |
| <code>minimal-v1</code> | You need box sizing, a flush body, and inherited control fonts | Heading sizes, list markers, other UA styles |
| <code>owned-v1</code> | You want the compact reset zudo-wind owns | Focus outlines and native appearance |

The same HTML is compiled three times. No scaffold CSS is added, so heading, list, margin, and control differences remain visible. In your project, compile the configured entry and audit the build plan with:

~~~sh
zfb css --input src/styles.css --output dist/app.css --project-root .
zfb wind audit --plan build
~~~

## Resolve a cascade tie

Utilities are unlayered and beat normal declarations in named layers. For an unlayered authored selector and utility with equal specificity, placement decides which rule comes later:

~~~ts
wind: {
  utilities: { placement: "before-authored" }
}
~~~

The records compare an actual <code>p-4</code> rule with an authored <code>padding</code> declaration. The default puts the utility after authored global CSS; <code>before-authored</code> puts the authored rule last:

Placement changes source order, not selector specificity. <code>group-*</code> and <code>peer-*</code> keep their zudo-wind specificity; see [relation variant specificity](./coming-from-tailwind.mdx#relation-variant-specificity).

## Layer order

Whenever wind emits a reset, token, or utility rule, the generated layer prelude is:

```css
@layer zw-reset, zw-tokens, zfb-hi, base, components;
```

Wind appends authored layer-order statements after this prelude. They cannot move the five listed layers ahead of or behind one another. Other layer names follow ordinary CSS first-declaration order. Imported stylesheets are not wrapped in a layer implicitly; an explicit import layer remains valid.

The integrated stylesheet order is:

1. The generated layer prelude.
2. Hoisted external imports.
3. The highlight block in `@layer zfb-hi`.
4. Generated reset and token layers.
5. Generated `@property` registrations when needed.
6. Authored bundled CSS, with imports already handled by the bundler.
7. Unlayered generated utility rules.
8. CSS Modules output at its pipeline append position.

Items 6 and 7 trade places under `wind.utilities.placement: "before-authored"`; see [Utility placement](#utility-placement).

The prelude comes before any authored layer prefix, so authored CSS cannot replace the owned order. Wind utilities are unlayered and, by default, follow authored global rules. They therefore beat normal declarations in named layers. An unlayered authored rule with greater specificity still wins. Between an unlayered authored rule and a utility of equal specificity, the one that comes later wins: the utility by default, the authored rule under `before-authored` placement. Important declarations follow normal CSS layer rules, but there is no important modifier in the wind language.

An entirely empty wind result emits no prelude. A selected reset can emit the prelude and reset even when no candidates resolve.

## Utility placement

`wind.utilities.placement` chooses where the unlayered utility rules sit relative to authored global CSS:

```ts
wind: {
  utilities: { placement: "before-authored" }
}
```

| Value | Order of items 6 and 7 | Equal-specificity tie |
| --- | --- | --- |
| `"after-authored"` (default) | Authored global CSS, then utilities | The utility wins |
| `"before-authored"` | Utilities, then authored global CSS | The authored rule wins |

Nothing else moves. The prelude, external imports, highlight block, reset, tokens, `@property` registrations, and CSS Modules output keep their places, and no utility is wrapped in a layer. External `@import` rules are hoisted above both stages either way. The setting applies to `zfb build`, `zfb dev`, and `zfb css` alike; editing it in dev rebuilds the served stylesheet.

Placement only settles ties of equal specificity. It does not change any selector, so it does not restore the specificity of Tailwind's `group-*` and `peer-*` selectors; see [Relation variants](./coming-from-tailwind.mdx#relation-variant-specificity).

## Reset choices

For measured differences from Tailwind 4.2.0 preflight and an authored parity block, see [Differences from Tailwind preflight](./coming-from-tailwind.mdx#reset-differences-from-tailwind-preflight).

The default is `none`, which emits no reset bytes. `minimal-v1` contains exactly these declarations:

```css

*::before,
*::after {
  box-sizing: border-box;
}
body {
  margin: 0;
}
button,
input,
optgroup,
select,
textarea {
  font: inherit;
}
```

Both resets leave native focus outlines and `appearance` alone. Neither forces a display rule for `[hidden]`. Bare border utilities set a solid border themselves under every reset choice.

## Deterministic ordering

Rules sort by this ascending tuple:

```text
(responsive_rank, dark_rank, relation_rank, state_rank, pseudo_rank,
 conflict_group_rank, scope_rank, catalog_rank, raw_candidate_utf8_bytes)
```

The base responsive rank is 0. For each configured breakpoint in ascending width order, minimum ranks are `2*i + 1` and maximum ranks are `2*i + 2`, with `i` starting at zero. Dark has rank 0 or 1. Relation, state, and pseudo ranks follow the orders in [Variants](./variants.mdx). Conflict groups use catalog table order starting at 1. Scope ranks are broad 0, axis 1, and side or corner 2; single-property families use 0. Catalog subentries use their listed order, then root bytes; raw candidate UTF-8 bytes break the final tie. This is emitted source order; it does not replace selector specificity.

HTML class order has no effect. With `spacingUnit` set to `0.25rem`, every permutation of `p-4 px-2 pl-1` resolves to top and bottom `1rem`, right `0.5rem`, and left `0.25rem`. The same rule applies to margins. `gap-4 gap-x-2 gap-y-1` produces a column gap of `0.5rem` and row gap of `0.25rem`. Same-scope ties use raw candidate bytes, so `p-2` sorts after `p-10`.

## Output bytes

V1 generated CSS is not minified in development or production. There is no final stylesheet minifier. The printer uses LF, two-space indentation, one declaration per line, and a final LF. Identical inputs produce identical wind CSS in either mode; CSS Modules may still be minified separately in production.
