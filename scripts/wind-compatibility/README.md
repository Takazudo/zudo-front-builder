# Wind reference interface (v1)

This is the test-only reference boundary for [profile 1/1](../../tests/wind-compatibility/profile.json). The initial candidate is exactly `tailwindcss@4.3.2`. It is a deliberate initial target because the existing lockfile resolves `@tailwindcss/browser@4.3.2` transitively; it is **not** a historical consumer baseline. No Tailwind dependency is added to a product or workspace manifest. The checked records at `tests/wind-compatibility/reference/{accepted,reviewed-through}.json` are separate and both remain null. The profile's `referencePolicy.initialState` is immutable bootstrap policy, not live state.

Run from the repository root with Node 24:

```sh
node scripts/wind-compatibility/reference-cli.mjs plan > /tmp/wind-plan.json
node scripts/wind-compatibility/reference-cli.mjs acquire --cache /tmp/zfb-wind-reference-cache
node scripts/wind-compatibility/reference-cli.mjs probe --cache /tmp/zfb-wind-reference-cache --candidates block,hidden,p-0,mx-auto,contents
node scripts/wind-compatibility/reference-cli.mjs assess --plan /tmp/wind-plan.json --bundle /tmp/wind-deltas.json
node --test tests/wind-compatibility/reference/reference.test.mjs
```

`plan` defaults to the explicit bootstrap candidate, never `latest`. Other versions require `--candidate X.Y.Z`; `--live yes` fetches exact npm metadata, and `--catalog /path/to/complete.json` uses an already captured complete catalog. Stable is the default; `--channel prerelease` is required for prereleases. Plans state bootstrap, channel, major and prerelease transitions. A candidate must advance the accepted reference. A catalog must declare complete ordered pages, terminate with `next: null`, and contain no duplicate versions. Registry errors fail closed. Use external temporary paths for captured catalog and plans. The command writes only to stdout.

`acquire` fetches the exact tarball over HTTPS, verifies its SHA-512 SRI, registry SHA-1 when given, and the embedded `package/package.json` version before writing a content-addressed copy to `--cache`. The cache must be outside the checkout. `probe` additionally extracts only compiler `.mjs` files into that cache and executes the package's own `compile`/`build` entry using `@theme { --*: initial; } @tailwind utilities;`. It emits package, SRI, artifact digest, source status, candidates and CSS. It does not use project dependencies or insert corrective CSS. The observed upstream `v4.3.2` tag points to `056a1550721d4bf79ff732d5ab9414fa83f7064f`; registry metadata has no `gitHead`, and the tag-to-tarball link has not been independently established. `packageGitSha` therefore stays null. The planning SRI hint was independently matched by the actual tarball and the extracted version was 4.3.2 on 2026-10-06.

## Machine contracts

All objects have `schemaVersion: 1`. Unknown versions fail consumers. Paths here are canonical for #3828/#3829/#3838; per-fixture imported provenance belongs with their later fixture manifests, not in the accepted record.

| Record | Required fields and meaning |
| --- | --- |
| `reference/bootstrap.json` | Exact `package`, `version`, `channel`, `registry`, `tarball`, `integrity`, `sha1`, `verifiedAcquisition`, and `source` (`repository`, observed tag, nullable package Git SHA, status). It is a candidate only. |
| `reference/accepted.json` | `acceptedReference: null` initially. A later admitted object must carry exact package/version/channel/SRI/artifact digest, lock and toolchain identity, source status/SHA or explicit null, profile ID/version/revision/digest, and admitting evidence report ID/digest. |
| `reference/reviewed-through.json` | `reviewedThrough: null` initially. A later object carries assessed package/version/channel/SRI, disposition, plan ID and assessment/report identities. Rejection can advance this record without advancing accepted. |
| Plan output | `kind: wind-reference-plan`, exact `candidate`, `previousAccepted`, `previousReviewedThrough`, `changes`, `inputs` (SHA-256 of profile, bootstrap, both live records, lockfile, command implementations and Node runtime identity), `toolchain`, `profile`, `admission: unassessed`, and content-derived `planId`. Candidate changes, input edits, tool changes, runtime changes and stale replay invalidate the ID. |
| Assessment bundle input | Exact `planId`, `candidateVersion`, `candidateIntegrity`, `baselineMode: bootstrap-snapshot | release-delta`, `previousVersion` (`null` for bootstrap) and a bootstrap rationale when applicable, plus `changelog`, `artifacts`, `source`, `tests`. Each section has an HTTPS `source`, `sourceDigest: sha256:<digest of canonical raw page bodies>`, `complete: true`, `totalItems`, `totalPages`, and ordered `pages`. Each page has one-based `index`, `totalPages`, `truncated`, `next`, HTTPS `url`, `httpStatus: 200`, `contentType`, full raw JSON `body`, and `bodySha256`. The body must contain matching `index`, `totalPages`, `next`, `totalItems`, and `items[]`; each item has unique `id`, HTTPS `url`, nonempty full `content`, and matching `contentSha256`. The final page has `next: null`. Bootstrap requires nonempty captured content in every section; later zero-change sections require an authoritative raw response with zero total. The producer must capture **all** upstream pages and identify the upstream source; a self-declared complete flag alone is not evidence of completeness. IDs without content fail. |
| Assessment output | `kind: wind-reference-assessment`, plan/candidate/bundle identities, `status: incomplete | ready-for-comparison`, `missing`, source identity status and nullable source Git SHA, and both advancement flags `false`. Missing provenance, empty content, page/count gaps, duplicate items or truncation produce `incomplete`. `ready-for-comparison` means the four captured raw-content sections passed these structural checks; it does not independently authenticate a capture against the live source, assert CSS/browser parity or admit a baseline. A later evidence report must bind captured upstream response identities before promotion. |

For a catalog JSON input, use `{ "complete": true, "pages": [{ "index": 1, "totalPages": 1, "next": null, "items": [<exact npm package metadata objects>] }] }`. Preserve the original registry response/source identity beside any catalog snapshot. Do not claim historical changelog or source completeness from a package's version string, a summary API page, or a model-generated version comparison. If a source lacks an authoritative total or continuation marker, mark that section incomplete.

## Downstream interfaces

The future `compare` command (#3829/#3831) consumes a validated plan, the exact acquired reference identity, profile and fixture manifest digests, Wind source/catalog/config/lock identities, and per-case/per-engine raw outputs. It will emit a report with every required case and control counted exactly once, actual and expected reviewed-difference occurrences, failures and browser inputs. A source-inspected or `ready-for-comparison` record cannot substitute for that report. #3828 owns inventory and fixture expansion; #3829 owns the execution harness.

The future checked `promote` command (#3838) consumes the immutable plan, complete assessment, independently reviewed comparison report, profile revision and current live records. It must reject stale inputs, incomplete mandatory engines/cases, unexplained differences and missing source-provenance decisions. Its output is a proposed accepted transition and a separate reviewed-through transition with exact evidence IDs. Promotion is **not implemented here**; no command silently edits these records. Until that checked transition exists, both remain null and no compiler or browser parity is claimed.

`plan` and `assess` are dry runs: they read checkout inputs and write stdout only. `acquire` and `probe` write solely to the explicit cache outside the checkout, with symlink-resolved path checks. None installs into the project, advances pins, edits tracked/untracked files, or posts externally. The cache can be deleted at any time. The focused test asserts before/after checkout status and identity for `plan`; the remaining network, path and integrity errors use deterministic offline responses.
