# Wind reference interface (v1)

## Required CI routing

`.github/workflows/health.yml` keeps the existing required `health` job as the
native producer and Wind compatibility gate. Its cheap Node policy, inventory,
accounting, and mutation contracts run on every event. On a pull request,
`ci-route.mjs` compares the exact PR base with the tested checkout. Only changes
confined to root `README.md` or GitHub issue/discussion templates are an explicit
Chromium no-op; every unknown path runs the Chromium pilot and corpus. The
required health job fails if routing or selected evidence fails, is cancelled,
missing, incomplete or stale. Every main push runs the full three-engine
comparison and production shipping suite even for an otherwise irrelevant
change. A manual dispatch requires `wind_full=true` and runs the same full lane.
The required `Docs gate` remains the documentation gate; no ruleset change or
optional workflow is used for Wind admission.

The full lane compiles the real-build Rust fixture before producing the exact
current-source `zfb` Cargo artifact, then runs that retained fixture executable
without invoking Cargo again. `ci-verify.mjs` replays the pilot/corpus or full
comparison and shipping validators against raw outputs and the pinned reference
cache. `ci-gate.mjs` checks exact report membership, tested SHA, complete input
digest, profile browser versions and artifact hashes. Reports and actual browser
inputs are retained as `wind-required-health-evidence` for seven days. A green
health check is regression evidence; baseline admission remains a separate
checked promotion under #3840.

This is the test-only reference boundary for [profile 1.5](../../tests/wind-compatibility/profile.json). The initial candidate is exactly `tailwindcss@4.3.2`. It is a deliberate initial target because the existing lockfile resolves `@tailwindcss/browser@4.3.2` transitively; it is **not** a historical consumer baseline. No Tailwind dependency is added to a product or workspace manifest. The live [accepted](../../tests/wind-compatibility/reference/accepted.json) and [reviewed-through](../../tests/wind-compatibility/reference/reviewed-through.json) records are separate. The profile's `referencePolicy.initialState` is immutable bootstrap policy, not live state.

The optional Tailwind release detector is dispatch-only and has no active
schedule. It can file a deduplicated manual review issue for a newer on-track
release, but never changes the profile or reference records. See the
[release detection contract](../../tests/wind-compatibility/reference/README.md#release-detection-optional-dispatch-only)
for its statuses, dry-run behavior, secret boundary and manual review flow.

Run from the repository root with Node 24:

```sh
node scripts/wind-compatibility/reference-cli.mjs plan > /tmp/wind-plan.json
node scripts/wind-compatibility/reference-cli.mjs acquire --cache /tmp/zfb-wind-reference-cache
node scripts/wind-compatibility/reference-cli.mjs probe --cache /tmp/zfb-wind-reference-cache --candidates block,hidden,p-0,mx-auto,contents
node scripts/wind-compatibility/reference-cli.mjs assess --plan /tmp/wind-plan.json --cache /tmp/zfb-wind-reference-cache > /tmp/wind-assessment.json
node --test tests/wind-compatibility/reference/*.test.mjs
```

`plan` defaults to the explicit bootstrap candidate, never `latest`. Other versions require `--candidate X.Y.Z`; `--live yes` fetches exact npm metadata, and `--catalog /path/to/complete.json` uses an already captured complete catalog. For the bootstrap version, live/catalog metadata must match the stored package, version, SRI, tarball, SHA-1 and repository before it is normalized to the same pinned candidate with the verified artifact digest and observed tag; a mismatch fails. Plans for another version also resolve and pin its exact upstream Git tag; the tag remains a separate source observation, not an assertion that the npm artifact came from that commit. Stable is the default; `--channel prerelease` is required for prereleases on **plan, acquire and probe**. A stable version cannot be labeled prerelease. Plans state bootstrap, channel, major and prerelease transitions. A candidate must advance the accepted reference. A catalog must declare complete ordered pages with `truncated: false`, terminate with `next: null`, and contain no duplicate versions. Registry and tag errors fail closed. Use external temporary paths for captured catalog and plans. The command writes only to stdout.

`acquire` fetches the exact tarball over HTTPS, verifies its SHA-512 SRI, registry SHA-1 when given, and the embedded `package/package.json` **name and version** before writing a content-addressed copy to `--cache`. The cache must be outside the checkout. `probe` additionally extracts only compiler `.mjs` files into that cache and executes the package's own `compile`/`build` entry using `@theme { --*: initial; } @tailwind utilities;`. It emits package, SRI, artifact digest, source status, candidates and CSS. It does not use project dependencies or insert corrective CSS. The observed upstream `v4.3.2` tag points to `056a1550721d4bf79ff732d5ab9414fa83f7064f`; registry metadata has no `gitHead`, and the tag-to-tarball link has not been independently established. `packageGitSha` therefore stays null. The planning SRI hint was independently matched by the actual tarball and extracted package identity on 2026-10-06.

`assess` validates the supplied plan **against current profile, live records, command hashes, runtime, toolchain and canonical candidate metadata**. It then fetches allowlisted upstream endpoints directly. The bootstrap path reads the exact npm version metadata and SRI-verified tarball (also matching the pinned bootstrap SHA-256), the exact GitHub release body, the exact tag ref, a nontruncated recursive Git tree, and the full codeload source archive. Every archived source blob must match its Git tree SHA-1; `CHANGELOG.md` must exist. The artifact, source and test sections are derived from full archive inventories, not user-supplied item IDs. A later accepted-to-candidate assessment verifies the accepted tarball digest, reads both endpoint archives, the npm version catalog, and every GitHub release page through its `next` cursor. Missing releases, source truncation, blob mismatch, unverifiable pagination, auth/404/offline errors and more than the bounded 30-version / 20-page limit produce `incomplete`. Stable assessments cover stable versions in the range; prerelease assessments include prereleases. This is a net source/test file delta between the exact endpoints plus complete release notes for the included versions.

Each raw HTTP response is retained as `response-<sha256>` in the explicit cache outside the checkout. The assessment output lists URLs, raw digests, byte counts, content types and cache-relative filenames, with a path-independent `captureIdentity`. It records the package source SHA and tag-to-npm-artifact link as unknown/unverified unless separately established. `ready-for-comparison` means these four upstream snapshots or deltas were actually fetched, parsed and checked; it is **not** a CSS/browser compatibility result or baseline admission.

## Machine contracts

All objects have `schemaVersion: 1`. Unknown versions fail consumers. Paths here are canonical for #3828/#3829/#3838; per-fixture imported provenance belongs with their later fixture manifests, not in the accepted record.

| Record | Required fields and meaning |
| --- | --- |
| `reference/bootstrap.json` | Exact `package`, `version`, `channel`, `registry`, `tarball`, `integrity`, `sha1`, `verifiedAcquisition`, and `source` (`repository`, observed tag, nullable package Git SHA, status). It is a candidate only. |
| `reference/accepted.json` | `acceptedReference: null` initially. A later admitted object must carry exact package/version/channel/SRI/artifact digest, lock and toolchain identity, source status/SHA or explicit null, profile ID/version/revision/digest, and admitting evidence report ID/digest. |
| `reference/reviewed-through.json` | `reviewedThrough: null` initially. A later object carries assessed package/version/channel/SRI, disposition, plan ID and assessment/report identities. Rejection can advance this record without advancing accepted. |
| Plan output | `kind: wind-reference-plan`, exact `candidate`, `previousAccepted`, `previousReviewedThrough`, `changes`, `inputs` (SHA-256 of profile, bootstrap, both live records, lockfile, all command implementations and Node runtime identity), `toolchain`, `profile`, `admission: unassessed`, and content-derived `planId`. Candidate changes, input edits, tool changes, runtime changes and stale replay invalidate the ID. Rehashed schema/transition lies still fail semantic replay. |
| Assessment input | `--plan` points to the immutable plan; `--cache` is an explicit path outside the checkout. No caller-supplied delta bundle can produce upstream readiness. The tool fetches exact npm/GitHub/codeload URLs derived from the plan. |
| Assessment output | `kind: wind-reference-assessment`, `schemaVersion: 1`, plan/candidate identity, `status: incomplete | ready-for-comparison`, `findings`, `captureIdentity`, raw `captures`, four `sections` when complete, source status and nullable package Git SHA, and both advancement flags `false`. The sections carry exact release versions/body digests, artifact file changes, source file changes and test file changes. `tagToNpmArtifactLink: unverified` is explicit. |

For a catalog JSON input, use `{ "complete": true, "pages": [{ "index": 1, "totalPages": 1, "truncated": false, "next": null, "items": [<exact npm package metadata objects>] }] }`. Preserve the original registry response/source identity beside any catalog snapshot. The live assessor does not trust catalog assertions as upstream evidence; it fetches the current exact metadata again. If a source lacks an authoritative complete tree or continuation marker, assessment is incomplete.

## Downstream interfaces

The `compare` command consumes a validated plan, the exact acquired reference identity, profile and fixture manifest digests, Wind source/catalog/config/lock identities, and per-case/per-engine raw outputs. It emits a report with every required case and control counted exactly once, actual and expected reviewed-difference occurrences, failures and browser inputs. A source-inspected or `ready-for-comparison` record cannot substitute for that report.

`compare` executes the pilot and all declared corpus engines for a candidate. With an accepted reference, it executes the same Wind build against both exact reference artifacts and records per-case CSS and browser observation deltas. The candidate and accepted tarballs are checked against their exact version, SHA-512 SRI and SHA-256; future `.mjs` imports are restricted to the complete verified archive member set. A nonzero runner result with complete content-digest-bound case rows is retained as observed mismatch data. Missing rows or infrastructure failures remain incomplete. The comparison contains a content hash for every external output file. Its `testedInputs` closure includes all tracked and unignored untracked source, fixture, policy, preview page, Markdown/MDX extraction inputs and lockfiles. Only `accepted.json` and `reviewed-through.json` are excluded from their own preimage. Snapshot schema 2 records regular-file bytes and executable state, and hashes a symlink's literal target without following it outside the checkout or requiring its target to exist. Tracked target files remain separate input rows. Prior schema 1 snapshots are stale. The tested build commit and the verified checkout HEAD immediately before transition are recorded separately. The latter does not claim the future metadata commit SHA; that belongs in external CI/admission evidence. A changed tested input invalidates comparison replay, even if only the final Git commit differs.

`promote` replays the plan, upstream capture hashes, comparison report and current checkout inputs. It requires a separate `wind-reference-classification` record with exact `upstreamChanges` and `browserChanges` memberships. Each changed row carries the old/candidate values, a rationale and one of `upstream-semantic`, `upstream-default-theme`, `upstream-packaging`, `intentional-exclusion`, `local-implementation-gap` or `unexplained-drift`. A `review-only` disposition can advance `reviewed-through` without advancing accepted. `accept` rejects unexplained drift, failed mandatory comparisons, stale inputs, missing candidate inventory refresh on later upgrades and missing shipping/consumer evidence. `promote` prints a read-only proposal unless `--apply yes` is explicit. The two record files are staged and rolled back on a failed rename. No command posts externally. No live accepted or reviewed-through transition is performed by implementing these commands; #3840/#3841 own admission and rehearsal.

`verify-current` executes the accepted reference against current Wind without proposing a later version. Ordinary `plan` still requires an advancing candidate. Required CI can use `plan --candidate <accepted-version> --current yes` for a verification-only comparison bound to the exact accepted artifact; `review` and `promote` reject such plans. The corpus manifest has reviewed targeted Firefox/WebKit mappings. Future candidate inventory membership must be refreshed from the candidate compiler/source; replay of the 4.3.2 inventory cannot satisfy upgrade promotion.

Current verification re-acquires the accepted tarball and source tag, checks the npm catalog and release, and records an empty source/artifact delta. It does not invent an advancing version range. The assessment is replayed from its retained raw HTTP responses before any browser evidence is accepted.

For a retained CI artifact bundle, `promote --output <original comparison output> --artifact-root <external restored bundle>` keeps the original report bytes and IDs intact. Only paths recorded beneath the original output prefix are remapped, and every restored file must resolve physically inside the declared bundle. The four Wind binary paths in the earlier pilot/corpus reports are provenance pointers, not retained binaries; the build manifest and independent CI/build record must support their identity. The promotion writer uses an exclusive transition lock and a recovery journal for the two tracked records. Ordinary commands fail closed while a lock or journal exists. After an interrupted write, run the explicit `recover` command to restore both old record bytes, then retry the plan. Two separate filesystem paths cannot be replaced in one POSIX rename, so consume these records through the repository CLI during transitions.

`review` handles a complete upstream assessment when no comparison was attempted. Its separate `wind-upstream-review` classification must set `disposition: review-only`, `reason: upstream-only-review`, `independentCompatibility: false`, the exact plan/capture identities, a rationale, and ordered classifications for every release, artifact, source and test change in the replayed assessment. It cannot claim a failed or unsupported execution without retained executable evidence. It never changes accepted. `reviewed-through` is monotonic: a lower-version review is recorded in output but leaves the highest checked record unchanged. A later accepted candidate below an already reviewed version may still advance accepted while retaining that higher reviewed-through record.

Admission should finalize policy, catalog, docs and generated claim inputs before the tested run. The checked transition then changes only `accepted.json` and `reviewed-through.json`; documentation can read those records dynamically. Any later tracked claim/status regeneration outside those two records changes the tested input closure and requires a new verification run. The closed baseline claim remains factual until real admission evidence passes.

### Shipping evidence contract for #3837

The checked `tests/wind-compatibility/shipping/manifest.json` is required for acceptance. It has `schemaVersion: 1`, `kind: wind-shipping-manifest`, positive `revision`, a checked `fixtureRoot`, `configFiles`, and an ordered `required` array. Each row has unique `id`, exact `mode`, `engine`, `configuration`, `fixture`, `mechanism`, `expectedObservation` and Boolean `screenshotRequired`. The manifest must cover source add/edit/remove/rename, token change/removal, CSS build/dev/SSR, missing CSS detection and component state. Its bytes and the full fixture/config contents are hashed at validation time.

The producer writes `wind-shipping-consumer-evidence` schema 1 with content-derived `reportId`, `manifestDigest`, `testedSourceSha`, `testedInputsDigest`, the example `windBuild` binding used by comparison and a separate authenticated production `zfb` Cargo artifact, `toolchain`, `profileDigest`, `fixtureTreeDigest`, `configDigest`, and an ordered `results` array matching every manifest tuple exactly. Each result has `outcome: passed` and `raw.generatedCss`, `raw.servedCss`, `raw.observation` and `raw.screenshot` as `{path, sha256}` (the screenshot may be null only where the manifest allows). All raw paths are under the external output root and all hashes are re-read. Generated and served CSS hashes must agree within each applicable case; development and production modes have separate contracts. The observation JSON must contain matching `caseId`, `engine`, exact `observed` values from the checked manifest and `cssResponse: {status: 200, contentType: "text/css; charset=utf-8", sha256: <served CSS hash>}`. The producer retains generated CSS, served HTTP response bodies, observation JSON and required screenshots. The production build source, executable bytes and version, Cargo execution and dist proof are validated separately. See [shipping/README.md](../../tests/wind-compatibility/shipping/README.md) for the current execution recipe. A missing manifest or report blocks acceptance; there is no synthetic ready flag.

`plan` is a zero-write dry run. `assess`, `acquire` and `probe` write only to the explicit cache outside the checkout, with symlink-resolved path checks. None installs into the project, advances pins, edits tracked/untracked files, or posts externally. The cache can be deleted at any time. Focused tests assert before/after checkout status and identity; network, path, integrity, pagination and replay failures use deterministic offline responses.

## Compatibility inventory seed (#3828)

`tests/wind-compatibility/upstream-surface.v1.json` is a pinned extraction from the Tailwind `v4.3.2` source archive at observed tag commit `056a1550721d4bf79ff732d5ab9414fa83f7064f`. The archive SHA-256 is `1d73680e19488b19e97ea3c96722e363cc0c4fd118af546857d8703e8f0f9be3`. That tag observation does not prove the npm tarball came from the commit. The archive is retained outside the checkout by the reference collector; no upstream artifact is committed.

The extraction reads `packages/tailwindcss/src/{utilities,variants}.ts`, `src/compat/legacy-utilities.ts` and their corresponding `.test.ts` files. It records source digests and concrete test line references for selected cases. It records literal names, functional roots, five compound variants and expanded finite loop values as an independent source cross-check. `runtime-keysets.v1.json` records the exact built-in empty-theme registration domain from the SRI-verified npm compiler's `__unstable__loadDesignSystem`: 890 static names, 315 functional roots and 83 variant roots. The source extraction's misses and false candidates remain visible in `sourceCrossCheck`; it is not treated as a complete TypeScript interpreter. Every remaining source registration expression has a stable content-based site ID and an explicit extraction limit. Open token, numeric, arbitrary, custom/plugin and variant composition domains are patterns; they are not a claim that every possible class string has been enumerated. Source tests, the Wind catalog and the two hashed Wind guide records provide cross-checks, but none is treated as a complete Tailwind class list.

`tests/wind-compatibility/inventory.v1.json` has one row per runtime registered upstream name/root and a reverse row for each of the 219 current Wind catalog entries. Exact catalog mappings include `exact` names and finite `keyword` suffixes permitted by the catalog grammar/negative policy; they mean source-inspected registration only. A same-root functional family is marked `root-collision-unverified` until its grammar and configuration are reviewed. Upstream variants are mapped against `crates/zudo-wind/src/variant.rs`, including bounded state/pseudo names, configured dark/breakpoint forms and the group/peer state subset. Other variant mechanisms remain visible as unmapped. Exact display and appearance statics, bounded order and basis values, four SVG presentation forms, and `not-sr-only` have reviewed native contracts. Table layout, order arbitrary values, basis scale/token/arbitrary values, and broader SVG paint/width forms remain tracked under #3812 with authored CSS alternatives. The bounded upstream rows explicitly mark `mx-auto`, `my-auto` and mapped margin, padding, inset and scroll-margin axis families for physical/logical writing-mode review. The 15 profile cases separately carry the reviewed `mx-auto` physical/logical-axis difference, empty-theme `p-0` difference, missing default token cases and native `contents` mechanism. Named Wind tokens use `var(--zw-...)` in the `zw-tokens` layer; numeric `spacingUnit` is optional. #3372/#3386 remain deferred, #3696 documentation is completed, and #3328/#3329 own docs hosting.

Generate and validate against the existing external capture:

```sh
node scripts/wind-compatibility/inventory-cli.mjs extract /tmp/zfb-wind-reference-cache/response-1d73680e19488b19e97ea3c96722e363cc0c4fd118af546857d8703e8f0f9be3 /tmp/zfb-wind-reference-cache/response-3673da9004404d12d4672bb5d002945319c2b3dea8c13ea022fdd33a3e260e62 /tmp/zfb-wind-reference-cache/tailwindcss-4.3.2-3673da9004404d12d4672bb5d002945319c2b3dea8c13ea022fdd33a3e260e62/dist/lib.mjs
node scripts/wind-compatibility/inventory-cli.mjs validate /tmp/zfb-wind-reference-cache/response-1d73680e19488b19e97ea3c96722e363cc0c4fd118af546857d8703e8f0f9be3 /tmp/zfb-wind-reference-cache/response-3673da9004404d12d4672bb5d002945319c2b3dea8c13ea022fdd33a3e260e62 /tmp/zfb-wind-reference-cache/tailwindcss-4.3.2-3673da9004404d12d4672bb5d002945319c2b3dea8c13ea022fdd33a3e260e62/dist/lib.mjs
WIND_PINNED_SOURCE_ARCHIVE=/tmp/zfb-wind-reference-cache/response-1d73680e19488b19e97ea3c96722e363cc0c4fd118af546857d8703e8f0f9be3 node --test tests/wind-compatibility/inventory.test.mjs
```

`validate` checks upstream and Wind membership both ways, unique IDs, row counts, actual catalog mappings, source/catalog/profile/docs digests and profile case references. It replays the complete source-derived reviewed contract, including evidence, semantics, variants and configured patterns, so data-only claims cannot silently change. An added runtime registration or source literal/template registration fails until it is classified; the validator also checks the actual compiler module against the pinned npm tarball when both external paths are supplied. Extraction deliberately does not auto-accept a new reference or update evidence. Every inventory evidence record remains `source-inspected`; `reportId`, build and browser fields are null. Browser/CSS differential evidence belongs to the later harness and must identify exact case/config/source/reference/profile/report inputs. Do not summarize this seed with a single compatibility percentage.

## Differential pilot (#3829)

The strict compiler fixtures are in `tests/wind-compatibility/pilot`. Their `manifest.json` lists all 15 profile case IDs; each `case.json` supplies the same explicit candidate to both compilers. The per-case `index.html` is the browser DOM, and `observations.json` contains the side-specific computed-style and geometry probes. Extraction fixtures live in `tests/wind-compatibility/extraction`: each original HTML, TSX or MDX source goes independently to Wind's source extractor and the pinned `@tailwindcss/oxide@4.3.2` scanner. Each extraction fixture reviews the complete scanner candidate lists and emitted rule sets in `assertions.json`, including Oxide's nonutility words. The scanner's JS and platform binary are downloaded to the external cache only after exact SHA-512 and package identity verification. There is no project installation and no regex or Wind-scanner oracle for the reference side.

Build the Wind example once, then run the differential adapter with that exact Cargo artifact:

```sh
node scripts/wind-compatibility/differential-runner.mjs build-wind /tmp/zfb-wind-build.json
node scripts/wind-compatibility/differential-runner.mjs --wind-binary "$(node -p 'JSON.parse(require("fs").readFileSync("/tmp/zfb-wind-build.json")).binaryPath')" --wind-build-manifest /tmp/zfb-wind-build.json --output /tmp/zfb-wind-differential
```

The first command runs `cargo build --locked -p zudo-wind --example wind_fixture_css --message-format=json` through the workstation heavy guard, or directly in CI, and records Cargo's emitted executable path with source, reset asset, lockfile and binary hashes. The second command rejects a changed source or binary. It rechecks the exact Tailwind compiler tarball and all eight pinned JavaScript modules before import, with regular-file, symlink and cache containment checks and individual module digests in the report. It compiles a cleared default theme with only each case's explicit mapping, launches the selected full Chromium, Firefox or WebKit executable recorded in browser identity, and saves independent stylesheets and a JSON report outside the checkout. Each engine has its own browser context and same-origin served stylesheet; the adapter checks the actual CSS response bytes and retains the CSSOM selector, layer, media and declaration tree. An independent reviewed CSS tree checks exact rule, declaration, selector, media and layer order, and derives occurrence counts for case-scoped differences. It runs mutations for missing CSS, wrong declarations, wrong selectors, extra or duplicate rules, altered layers and wrong hover media. The native reset and authored CSS control is separate from the shared utility lane and probes headings, lists, borders and forms.

Each engine report lists every profile case and required control, including any missing executions. Its identity hashes all pilot, extraction and native fixture bytes, the executed adapter modules, profile and lockfile; each browser probe records its exact DOM, authored CSS, viewport and state settings. A nonzero result means a mismatch, infrastructure failure, incomplete required comparison, or browser outside the profile's Linux admission matrix. This pilot does not accept a reference version or advance `reviewed-through`; the broad corpus and matrix admission belong to later topics.

## Independent corpus (#3831)

The [corpus README](../../tests/wind-compatibility/corpus/README.md) records the exact case/control counts, pinned upstream test origins, reviewed adaptations, source license, and commands for Chromium plus targeted Firefox/WebKit. Run one full pilot per browser engine from the same integrated source and pass that engine's `pilot-${engine}/report.json` to `corpus-runner.mjs --pilot-report` while retaining the pilot's full output directory and all raw CSS/report artifacts. The corpus runner requires the same verified Wind build, current reference/scanner/browser/adapter identities, and writes a separate content-addressed report for each browser engine.
